## Findings

### C3-001 — Panic recovery sends the panic value and method name to the remote caller
- Area: D (Security) · Severity: HIGH · Effort: S
- Location: grpc/interceptors.go:43-53
- Problem: `recoverToStatus` puts the recovered value into the errorkit `Reason` (`"grpc: panic recovered in %s: %v", method, r`) and then returns `status.New(codes.Internal, appErr.Error())`. Whatever the panic carried is serialized into the `grpc-message` trailer and sent to the client. This can be a runtime error with internal details, a formatted string with secrets or hostnames, or a value from a third-party library. This is DN-20.
- Evidence: throwaway test, handler `panic("db password=hunter2 at 10.0.0.5")`, client output:
  `client sees: code=Internal msg="[ERR_SYSTEM_UNEXPECTED] grpc: panic recovered in /sdk.test.Echo/Unary: db password=hunter2 at 10.0.0.5"`.
  The full value and stack are also logged (interceptors.go:46-52). That part is correct and should stay.
- Impact: Information disclosure (STRIDE "I") to any client that can trigger a panic, including unauthenticated callers. It also tells an attacker which inputs crash which handler.
- Source: eduardo/go-grpc §2 ("no details leak") and checklist #5 ("`codes.Internal` responses never leak internal error text") · eduardo/go-error-handling §9 ("`err.Error()` in a response leaks…") · eduardo/go-security-audit "Error messages don't leak internals" · eduardo/go-api-design §8.
- Recommendation: Keep logging `appErr` with the panic value and stack. Return a fixed message to the client, e.g. `status.New(codes.Internal, "internal error")`, with an `ErrorInfo{Reason: "ERR_SYSTEM_UNEXPECTED"}` detail and optionally the errorkit error ID for correlation (see C3-015). Add a regression test that asserts the panic text is absent from `status.Convert(err).Message()`.
- Breaking: no · Needs approval: no (README "Defaults" only promises "a panic becomes `codes.Internal`, server stays up"; the message text is not part of the contract).

### C3-002 — `ToStatus` puts the errorkit `Reason` on the wire for every code, including `Internal`
- Area: D (Security) · Severity: HIGH · Effort: M
- Location: grpc/status.go:53-62 (with errorkit/error.go:90-101)
- Problem: `ToStatus` uses `appErr.Error()` (`"[CODE] reason"`) as the gRPC status message no matter which gRPC code it maps to. SDK reasons often embed the text of the underlying error: `grpc/client.go:73` (`"grpc: dial %q: %v"`), `grpc/server.go:97`, `envs/loader.go:13`, `httpserver/hertz/server.go:105`. Consumers following AGENTS.md §4 wrap library errors and return them through `ToStatus` (README "Error mapping": `return nil, sdkgrpc.ToStatus(err)`). So for `Internal`/`Unknown`-class failures, internal error text, DSN hosts, SQL errors and file paths reach remote clients.
- Evidence: throwaway test, `ToStatus(errorkit.NewError(code).With(WithReason("pq: relation \"users\" does not exist (host=db-primary.internal)")))` returned for every code, e.g.
  `ERR_DB_POSTGRES_UNAVAILABLE -> Internal msg="[ERR_DB_POSTGRES_UNAVAILABLE] pq: relation \"users\" does not exist (host=db-primary.internal)"`.
- Impact: Information disclosure on every server that follows the documented error path. The same text is often useful and harmless for 4xx-class codes (`InvalidArgument`, `NotFound`), which is why a per-class policy is needed instead of a blanket rule.
- Source: eduardo/go-grpc §2 + checklist #5 · eduardo/go-error-handling §9 ("Translate before it reaches a user") · eduardo/go-security-audit threat-model "Information disclosure: `err.Error()` in responses".
- Recommendation: For codes that map to `Internal`/`Unknown`/`DataLoss` (and optionally `Unavailable`), use a stable message, either the registered `Metadata.Description` or `"internal error"`, and keep the errorkit code and ID in `ErrorInfo`. Keep the reason for client-error classes. Alternatively, add an opt-in `ToStatusWithPolicy`/option that keeps today's behaviour, and change the default only with approval. Document the policy in README "Error mapping".
- Breaking: yes (status message text changes for server-error codes) · Needs approval: yes (grpc/README.md:70-72 promises "preserving the message").

### C3-003 — `ToStatus` maps every package-registered code to `codes.Internal` and ignores errorkit metadata
- Area: G (Public API / correctness) · Severity: HIGH · Effort: M
- Location: grpc/status.go:14-38
- Problem: `codeFor` is a fixed switch over 15 core codes. Every code registered by sibling packages through `errorkit.MustRegister` falls to `codes.Internal`. These include `ERR_AUTH_UNAUTHENTICATED`/`ERR_AUTH_UNAUTHORIZED` (httprequest/errors_codes.go:29,34), `ERR_DB_MONGO_NOT_FOUND` (mongo/errors_codes.go:32), `ERR_DB_POSTGRES_UNAVAILABLE`/`_TIMEOUT` (postgres/errors.go:13,18; `HTTPStatus` 503/504, `Retriable: true`), `ERR_NETWORK_TIMEOUT` and `ERR_EXTERNAL_SERVICE_UNAVAILABLE`. The registered `Metadata.HTTPStatus` and `Metadata.Retriable` are never consulted. The README table (grpc/README.md:76) uses the wildcard `ERR_VALIDATION*`, which suggests prefix matching that the code does not do. This is DN-23.
- Evidence: throwaway test output: `ERR_AUTH_UNAUTHENTICATED -> Internal`, `ERR_AUTH_UNAUTHORIZED -> Internal`, `ERR_DB_MONGO_NOT_FOUND -> Internal`, `ERR_DB_POSTGRES_UNAVAILABLE -> Internal`, `ERR_DB_POSTGRES_TIMEOUT -> Internal`, `ERR_NETWORK_TIMEOUT -> Internal`, `ERR_EXTERNAL_SERVICE_UNAVAILABLE -> Internal`.
- Impact: gRPC clients and service-config retry policies key on `UNAVAILABLE`, so transient DB outages that errorkit marks `Retriable` are not retried. Auth failures look like server bugs (`Internal`) instead of `Unauthenticated`/`PermissionDenied`. Not-found becomes a 5xx-class error that breaks alerting and SLOs. AGENTS.md §2.1 says retryability is data-driven through `Metadata.Retriable` and should not be reimplemented, yet this mapping discards it.
- Source: eduardo/go-grpc §2 (code semantics: `Unavailable` retryable, `Unauthenticated` vs `PermissionDenied`, `Internal` = bug) and `references/clients.md` (retry `UNAVAILABLE` only) · AGENTS.md §2.1 · eduardo/go-error-handling §9.
- Recommendation: Keep the explicit switch for the 15 core codes. For any other code, fall back to the registered metadata: map `HTTPStatus` to a gRPC code (400→InvalidArgument, 401→Unauthenticated, 403→PermissionDenied, 404→NotFound, 409→Aborted/AlreadyExists, 429→ResourceExhausted, 503→Unavailable, 504→DeadlineExceeded, other 5xx→Internal). Use `Retriable` as a tie-breaker towards `Unavailable`. Correct the README wildcard and extend the table. Add table tests for the package codes.
- Breaking: no API break; the status codes clients observe change for codes that are not listed today · Needs approval: no (the README table does not cover these codes). P3 may still classify it `approval` as a consumer-visible behaviour change.

### C3-004 — `ToStatus` turns context cancellation and deadline errors into `codes.Unknown`
- Area: B (Idiomatic Go / context) · Severity: MEDIUM · Effort: S
- Location: grpc/status.go:65
- Problem: Non-errorkit errors go through `status.Convert`, so a handler that returns `ToStatus(ctx.Err())`, or a wrapped `context.DeadlineExceeded`, reports `Unknown` instead of `DeadlineExceeded`/`Canceled`. `status.FromContextError` exists for this case.
- Evidence: throwaway test output: `context deadline exceeded -> Unknown`, `context canceled -> Unknown`.
- Impact: Clients and metrics cannot tell timeouts from unknown failures. Deadline propagation, which the go-grpc skill calls mandatory, loses its signal at the SDK boundary.
- Source: eduardo/go-grpc §3 (`status.FromContextError(err).Err()`) · eduardo/go-context §1/§3.
- Recommendation: Before `status.Convert`, check `errors.Is(err, context.DeadlineExceeded) || errors.Is(err, context.Canceled)` and return `status.FromContextError(err).Err()`. Add tests.
- Breaking: no API break; behaviour change for context errors · Needs approval: yes (grpc/README.md:84-85 documents "a plain error becomes `codes.Unknown`").

### C3-005 — Transport security silently defaults to plaintext on both client and server
- Area: D (Security) · Severity: HIGH · Effort: M
- Location: grpc/client.go:31-36, grpc/config.go:78-80, grpc/server.go:24-84 (no credentials option), grpc/README.md:93
- Problem: `Dial` installs `insecure.NewCredentials()` whenever `ClientConfig.Creds` is nil, with no warning and no explicit opt-in. `ServerConfig` has no credentials field at all. The only way to get a TLS server is `WithRawServerOptions(grpc.Creds(...))`, so the type-safe config cannot express a secure server. All examples (README quick start, tests) are plaintext.
- Evidence: client.go:31-33 `creds := cfg.Creds; if creds == nil { creds = insecure.NewCredentials() }`. Every existing round-trip test dials with `ClientConfig{}` and succeeds over plaintext (roundtrip_test.go `connect`). No `credentials.NewTLS` appears anywhere in the package.
- Impact: One forgotten field sends request bodies and metadata, including bearer tokens set by interceptors, in cleartext, and leaves the server unauthenticated, for example `Dial(ClientConfig{Target: "payments.prod:443"})`. There is no peer identity for authorization, which go-grpc §8 says should come from mTLS (`peer.FromContext`).
- Source: eduardo/go-grpc §8 + checklist #9 ("TLS (mTLS internally)") · eduardo/go-security-audit §7 and `references/auth-and-transport.md` "TLS configuration" · CWE-319.
- Recommendation: Additive, no approval needed: add `ServerConfig.Creds credentials.TransportCredentials` and wire it through `grpc.Creds`. Add an explicit `WithInsecure()` client/server option and a README warning. Breaking, needs approval: make nil credentials an error, or require the explicit insecure opt-in (a v2 candidate). Short of that, document plainly that the default is meant for meshes or sidecars that terminate mTLS.
- Breaking: additive part no; default change yes · Needs approval: yes for changing the default (grpc/README.md:93 and config.go:78-79 document "insecure" as the default).

### C3-006 — The server accepts an unbounded number of concurrent streams per connection by default
- Area: D (Security / DoS) · Severity: MEDIUM · Effort: S
- Location: grpc/config.go:45-56 (`ServerConfig`), grpc/server.go:36-49
- Problem: `ServerConfig` exposes message sizes and keepalive but not `MaxConcurrentStreams`. grpc-go's default is `math.MaxUint32` (grpc@v1.85.0 server.go:189), and each stream holds a handler goroutine plus flow-control state. Only `WithRawServerOptions(grpc.MaxConcurrentStreams(n))` limits it.
- Evidence: throwaway test, default `New(ServerConfig{Address: "bufnet"})` with a bidi handler that blocks: `2000 concurrent handler goroutines accepted on ONE connection with default config`.
- Impact: A single client, which may be unauthenticated given C3-005, can open streams until memory runs out. The README "Defaults" table does not mention it.
- Source: eduardo/go-grpc §5 ("each open stream holds a goroutine and flow-control state") · eduardo/go-security-audit threat-model "Denial of service … bounded goroutines" · eduardo/go-concurrency-review `goroutine-patterns.md` ("One goroutine per input with no limit is a self-inflicted denial of service").
- Recommendation: Add `ServerConfig.MaxConcurrentStreams uint32` (0 = gRPC default), document it in the "Defaults" table, and recommend a value (e.g. 100–1000) in the quick start. Changing the default itself needs approval.
- Breaking: no (additive) · Needs approval: no for the field; yes if the default changes.

### C3-007 — Recovery is not outermost when an interceptor is passed through `WithRawServerOptions`
- Area: C (Concurrency / stability) · Severity: MEDIUM · Effort: S
- Location: grpc/server.go:51-66, 81; grpc/options.go:75-79
- Problem: The comment at server.go:51-52 says recovery "runs outermost (so it also catches panics from user interceptors)". That holds only for `WithUnaryInterceptors`/`WithStreamInterceptors`. A consumer who passes `grpc.UnaryInterceptor(x)`/`grpc.StreamInterceptor(x)` through `WithRawServerOptions`, which the option doc invites "for anything this package does not expose directly", gets `x` prepended in front of the whole chain (grpc@v1.85.0 server.go:1208-1213). A panic in `x` is then not recovered and crashes the process.
- Evidence: throwaway test with `WithUnaryInterceptors(rec("sdk-user"))` + `WithRawServerOptions(grpc.UnaryInterceptor(rec("raw-UnaryInterceptor")))`, inspecting `runtime.Stack` in each layer:
  `order: [raw-UnaryInterceptor(recovery-on-stack=no) sdk-user(recovery-on-stack=yes) handler(recovery-on-stack=yes)]`.
- Impact: One panic in a common kind of interceptor (auth, logging) taken from another library takes down every in-flight RPC. This contradicts the README promise that the "server stays up".
- Source: eduardo/go-grpc §4 ("recovery first (outermost)") · eduardo/go-api-design §2 ("Recover MUST be outermost") · eduardo/go-concurrency-review §1 "Recover at the goroutine boundary".
- Recommendation: Document in `WithRawServerOptions` and the README that interceptors must be added with `WithUnaryInterceptors`/`WithStreamInterceptors`, because raw `grpc.UnaryInterceptor`/`StreamInterceptor` run outside recovery. Add an end-to-end test that recovery wraps user interceptors (see C3-012).
- Breaking: no · Needs approval: no.

### C3-008 — There is no client-side deadline facility, and Kitex `RPCTimeout`/`ConnectTimeout` were dropped with no replacement
- Area: G (Public API — deadlines) · Severity: MEDIUM · Effort: S
- Location: grpc/client.go:19-77, grpc/config.go:76-86, grpc/README.md:136-164, 179
- Problem: `ClientConfig` and the client options offer no default per-call timeout and no service config. The migration table (README:179) shows that `ClientConfig{Hosts, RPCTimeout, ConnectTimeout}` became `ClientConfig{Target, Keepalive, Creds, …}`, without saying how to get timeouts back. The quick start calls `client.Unary(ctx, …)` with an unspecified `ctx`. A call made with a context that has no deadline blocks until the server answers or the connection breaks.
- Evidence: grep shows no `context.WithTimeout`, `WithDefaultServiceConfig` or timeout field in `grpc/*.go` (non-test). README:179 migration row.
- Impact: A hung upstream holds client goroutines indefinitely, which is a regression from the Kitex-based API that had `RPCTimeout`.
- Source: eduardo/go-grpc §3 ("Deadlines Are Mandatory"), checklist #6, `references/clients.md` (service-config `timeout`) · eduardo/go-context §3.
- Recommendation: Add `WithClientDefaultTimeout(d time.Duration)`. It would install unary and stream interceptors that apply `context.WithTimeout` only when the incoming ctx has no deadline. Or add a `ClientConfig.ServiceConfig string` passed to `grpc.WithDefaultServiceConfig`. Document both in the migration table.
- Breaking: no (additive) · Needs approval: no.

### C3-009 — `ServerConfig.Address` is required but never used
- Area: G (Public API) · Severity: MEDIUM · Effort: S
- Location: grpc/server.go:18, 25-29, 83, 94; grpc/config.go:47-48
- Problem: `New` rejects an empty `Address` with `ERR_SYSTEM_CONFIG_INVALID`, stores it in `Server.cfg`, and never reads it again. `Serve` takes a caller-owned `net.Listener`. The README quick start therefore repeats the address twice (README:114, 126). This is DN-21.
- Evidence: the only use of `cfg` on `Server` is the assignment `&Server{srv: grpc.NewServer(so...), cfg: cfg}` (server.go:83). There are no reads of `s.cfg`. Tests have to invent `scfg.Address = "bufnet"` (roundtrip_test.go:97-99) only to pass validation.
- Impact: The API misleads users: a mismatched address in `ServerConfig` and `net.Listen` fails silently, and the required field gives a false sense of configuration.
- Source: eduardo/go-api-design (APIs are contracts) · eduardo/go-design-principles / YAGNI (a field with no behaviour) · eduardo/go-documentation §1 (say what the caller needs).
- Recommendation: Additive: add `(*Server).ListenAndServe() error` that does `net.Listen("tcp", s.cfg.Address)` and then `Serve`, which gives the field a purpose. At minimum, document that `Address` is informational. Relaxing the requirement would change the documented `ERR_SYSTEM_CONFIG_INVALID` behaviour and needs approval.
- Breaking: no (additive) · Needs approval: no (yes if the validation is relaxed).

### C3-010 — README quick start: receive loops spin forever on errors, and `Shutdown` gets a context that never expires
- Area: G (Documentation / DX) · Severity: MEDIUM · Effort: S
- Location: grpc/README.md:128, 130, 150-163
- Problem: (a) `for { msg, err := ss.Recv(); if err == io.EOF { break }; _ = msg }` (README:154, 163) never leaves the loop on a non-EOF error. A failed stream returns the same error on every `Recv`, so the loop becomes a busy spin. (b) `cs.Send(...)`, `CloseAndRecv`, `client.Unary` and `bs.Send` discard errors (150-162). (c) `_ = srv.Shutdown(context.Background())` (130) can never reach the documented forced-stop path, so with long-lived streams shutdown hangs indefinitely. (d) `go srv.Serve(lis)` drops the serve error.
- Evidence: throwaway test, server-stream handler returning `codes.Unavailable`, client following the README loop: `non-EOF errors returned in 1000 iterations without terminating: 1000`.
- Impact: Consumers copy quick starts. The result is a CPU-spinning goroutine on the first backend failure, and a shutdown that never completes under SIGTERM, so the orchestrator SIGKILLs the process mid-RPC.
- Source: eduardo/go-documentation §7 ("minimal working example") · eduardo/go-grpc §5 (terminate streams), §8 (graceful stop with forced fallback) · eduardo/go-error-handling checklist #1 · eduardo/go-context §3.
- Recommendation: Rewrite the samples. Use `if errors.Is(err, io.EOF) { break }; if err != nil { return err }`, check every error, use a deadline ctx for calls, and use `ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)` for `Shutdown`, reporting the `Serve` error through a channel.
- Breaking: no · Needs approval: no.

### C3-011 — No way to treat incoming trace context as untrusted (public endpoints)
- Area: G (Observability) / D · Severity: MEDIUM · Effort: S
- Location: grpc/server.go:68-79, grpc/options.go:45-62
- Problem: The server stats handler always makes the incoming `traceparent` the parent of the server span. otelgrpc v0.72.0 provides `WithPublicEndpoint()`/`WithPublicEndpointFn(...)` (otelgrpc config.go:110-126), which start a new root and link to the remote context instead, but the SDK exposes only tracer provider and propagator. The only workaround is `WithServerTracing(false)` plus a hand-built `WithRawServerOptions(grpc.StatsHandler(otelgrpc.NewServerHandler(otelgrpc.WithPublicEndpoint())))`.
- Evidence: options.go:45-62 define only `WithServerTracerProvider`/`WithServerPropagator`. server.go:71-78 builds `hopts` from those two only.
- Impact: For internet-facing gRPC servers, external callers choose trace IDs and, with the usual `ParentBased` sampler, the sampling decision. That allows trace poisoning or forced 100% sampling of the tracing backend.
- Source: eduardo/go-observability §2 + `references/tracing.md` "Sampling" (`ParentBased`) · eduardo/go-security-audit threat-model (trust boundaries: gRPC handlers).
- Recommendation: Add `WithServerPublicEndpoint()` (and optionally `WithServerOTelOptions(...otelgrpc.Option)` as a general escape hatch) that forwards to otelgrpc. Document when to use it.
- Breaking: no (additive) · Needs approval: no.

### C3-012 — Tests do not check the package's main promises: tracing, user interceptors inside recovery, and the client options
- Area: E (Testing) · Severity: MEDIUM · Effort: M
- Location: grpc/grpc_test.go:47-64, grpc/roundtrip_test.go, grpc/recovery_test.go, grpc/internal/testsvc/testsvc.go
- Problem:
  - The README claims tracing "instruments **all four** call modes". No test installs a `tracetest` exporter or asserts a span, and `WithServerTracerProvider`/`WithServerPropagator`/`WithClientTracerProvider`/`WithClientPropagator`/`WithClientTracing` have 0% coverage.
  - `WithClientUnaryInterceptors`/`WithClientStreamInterceptors`/`WithServerLogger` have 0% coverage.
  - `WithUnaryInterceptors`/`WithStreamInterceptors` are tested only by `TestServerOptions_Accumulate`, which checks the lengths of private slices (`len(b.unary) != 2`, grpc_test.go:61). That tests the implementation, not the behaviour. No end-to-end test shows that a user interceptor runs and that recovery wraps it.
  - No test asserts what the client sees after a recovered panic (C3-001) or after `ToStatus` over the wire. `Dial`'s `grpc.NewClient` error path and the `Serve` error path are untested (`Dial` 67.6%, `Serve` 66.7%).
  - No goroutine-leak check (`goleak` is not a dependency), although the package starts serve goroutines in every round-trip test.
  - `grpc/internal/testsvc` shows 0% because coverage is not collected with `-coverpkg`, not because it is unused.
- Evidence: `go tool cover -func` output above. `grep -n tracetest grpc/*_test.go` finds nothing.
- Impact: Regressions in the advertised behaviour (spans, propagation, interceptor order, client interceptor wiring) would pass CI.
- Source: eduardo/go-test-quality §1 (behaviour, not implementation), §7 (goleak), §6 (`-coverpkg`), anti-pattern "Reaching into private fields" · eduardo/go-grpc §7 + `references/testing.md` ("Same interceptors as production") · go-testing-strategy ("Case coverage is" the goal).
- Recommendation: Add bufconn tests with a `tracetest.SpanRecorder` provider and a `propagation.TraceContext` propagator that assert one server span and one client span per call mode with a shared trace ID. Add a recovery-wraps-user-interceptor test (unary and stream), a client interceptor invocation test, a panic-message assertion (C3-001), and a `ToStatus` over-the-wire test. Replace the private-field test with behavioural ones. Consider `goleak` (that would be a new test dependency, so it needs approval under `R-DEPS`).
- Breaking: no · Needs approval: no (yes only for adding `goleak`).

### C3-013 — Test hygiene: no deadlines, `context.Background()`, sleep pacing, pre-1.22 loops and unchecked `Close`
- Area: E (Testing) / B · Severity: LOW · Effort: S
- Location: grpc/roundtrip_test.go:46, 134, 144, 173, 177, 196, 203-212, 244, 248, 265, 277, 292, 295, 313, 317, 324, 326, 382, 385, 395; grpc/recovery_test.go:26, 37, 50, 62
- Problem: Every RPC in the tests uses `context.Background()` with no deadline, so a hang (e.g. `<-started` at roundtrip_test.go:334, 393) blocks until the 10-minute `go test` timeout instead of failing. `time.Sleep(20 * time.Millisecond)` paces the drain test (317). `wg.Add(1)` + `go func(){ defer wg.Done() … }` (203-212) can be `wg.Go`. `for i := 0; i < n; i++` loops (46, 177, 206, 313) can be `for i := range n`. `defer cc.Close()` results are unchecked (292, 324, 382; golangci-lint errcheck in baseline V9). No `t.Parallel()`, although each test owns its bufconn listener.
- Evidence: line list above; baseline.md V9 errcheck entries `grpc/roundtrip_test.go:292`, `:324`, `:382`.
- Impact: The suite hangs instead of failing, runs slower, and code drifts from modern idioms.
- Source: JetBrains `testing_t_context`, `sync_waitgroup_go`, `range_over_int` · eduardo/go-test-quality §7–8, anti-patterns `time.Sleep`, `context.Background()` in a test · eduardo/go-context §5 · go-testing-strategy "No time.Sleep synchronization".
- Recommendation: Use `ctx, cancel := context.WithTimeout(t.Context(), 5*time.Second)` per test, replace bare channel waits with a `select` against that ctx, apply `wg.Go` and `range n`, register `t.Cleanup(func(){ _ = cc.Close() })`, and add `t.Parallel()` where tests do not share state.
- Breaking: no · Needs approval: no.

### C3-014 — `errors.As` with a declared target where Go 1.26 `errors.AsType` applies
- Area: B (Modern Go) · Severity: LOW · Effort: S
- Location: grpc/status.go:53-54
- Problem: `var appErr *errorkit.AppError; if errors.As(err, &appErr) { … }` is the pattern that `errors.AsType` replaces in Go 1.26, the module's `go` directive.
- Evidence: status.go:53-54. The JetBrains CLI lists `errors_as_type` (Since Go 1.26) for this file.
- Impact: Readability only.
- Source: JetBrains `errors_as_type` · eduardo/go-modernize feature table (1.26+ `errors.AsType`) · eduardo/go-error-handling §3.
- Recommendation: `if appErr, ok := errors.AsType[*errorkit.AppError](err); ok { … }`.
- Breaking: no · Needs approval: no.

### C3-015 — Recovery status omits `ErrorInfo`; `ErrorInfo.Domain` is hard-coded to `"go-sdk"`
- Area: G (Public API) · Severity: LOW · Effort: S
- Location: grpc/interceptors.go:53, grpc/status.go:56-59
- Problem: Panics return a bare `status.New(codes.Internal, …)` with no `ErrorInfo`, while `ToStatus` attaches one, so clients cannot read the errorkit code programmatically for the most important server failure. Also, `ErrorInfo.Domain` is the constant `"go-sdk"`. In the `ErrorInfo` model the domain identifies the service that produced the error, so every consumer service reports the same domain. `ErrorInfo.Metadata` is unused, so the errorkit ID and `Retriable` flag are not surfaced.
- Evidence: interceptors.go:53; status.go:56-59.
- Impact: Error correlation between client and server logs is inconsistent, and errors cannot be attributed to a service.
- Source: eduardo/go-grpc §2 (status codes and error details) · eduardo/go-observability §4 (connecting logs and traces).
- Recommendation: Build the recovery status through `ToStatus` once C3-001 and C3-002 are fixed. Add an option, or a `ToStatus` variant, for the domain, and put `id`/`retriable` into `ErrorInfo.Metadata`.
- Breaking: no (additive) · Needs approval: no.

### C3-016 — `grpc` tracing wiring is not described in AGENTS.md §2.2 and does not use `*telemetry.Instrumenter`
- Area: G (API consistency) · Severity: LOW · Effort: S
- Location: grpc/options.go:33-62, 99-114; AGENTS.md §2.2
- Problem: AGENTS.md §2.2 lists the packages that follow the tracing triplet and the exceptions (`postgres`, `messaging`). `grpc` is in neither list. It uses boolean toggles (`WithServerTracing(bool)`, `WithClientTracing(bool)`) plus a raw `trace.TracerProvider`, not a `*telemetry.Instrumenter`, so the "one instrumenter passed down" invariant in AGENTS.md §3 cannot be applied to it.
- Evidence: options.go:33-62, 99-114. In AGENTS.md, `grpc` appears only in §0 and §1 (lines 37-39, 55).
- Impact: Agents and consumers following AGENTS.md wire tracing inconsistently. This is likely a duplicate of a P2.X1 API-consistency finding.
- Source: AGENTS.md §2.2, §3 · eduardo/go-api-design / go-documentation (contract accuracy).
- Recommendation: Add `grpc` to the §2.2 exception list (it takes a `TracerProvider`/propagator through options; spans come from otelgrpc). Optionally add `WithServerInstrumenter`/`WithClientInstrumenter` adapters if `telemetry.Instrumenter` can expose a provider.
- Breaking: no · Needs approval: no (documentation; any new option is additive).

## Strengths (keep)

- Recovery is installed by default for unary **and** streaming handlers, and it sits ahead of the SDK-managed user interceptors (`server.go:53-66`). It logs through an injected `*logger.Logger` or `logger.ErrorCtx`, which uses `CtxOrGlobal(ctx)` and attaches trace IDs (`logger/wrapper.go:73-76`), as AGENTS.md §2.3 requires.
- Tracing uses the otelgrpc **stats handler**, not interceptors, so all four call modes get spans and the span sees the post-recovery status. User interceptors run with the span already in `ctx`. otelgrpc v0.72.0 records no request metadata as span attributes and no message events by default, so trace data does not leak metadata.
- `Shutdown(ctx)` follows the right pattern: `GracefulStop` in a goroutine, a hard `Stop` when ctx expires, and `ERR_SYSTEM_TIMEOUT_INTERNAL` wrapping `ctx.Err()`. The throwaway test showed no leaked goroutine after a forced stop (`goroutines before=2 after=3` after cleanup, within the bufconn listener's tolerance).
- `Dial` uses `grpc.NewClient` (not the deprecated `Dial`) and leaves `ClientConn` ownership with the caller. Keepalive and message-size overrides are applied only when set, so stock gRPC defaults are preserved. The `MaxConnectionAge` hazard is documented clearly.
- Constructor errors are `*errorkit.AppError` with `WithWrapped` (`server.go:96-99`, `client.go:72-75`), so `errors.Is/As` reach the cause.
- Tests use bufconn with `passthrough:///` and the production `New`/`Dial` path, cover all four call modes, recovery in unary and stream handlers, keepalive wiring, drain and forced stop. They pass under `-race -count=5 -shuffle=on`. `internal/testsvc` avoids a protoc dependency in a clean way.
- The package doc (`doc.go`) and README document the import alias, codegen, defaults and migration. Every exported identifier has a doc comment.

## Open questions

- **Panics in goroutines started by handlers** (e.g. a bidi handler with a separate send goroutine) are not covered by the recovery interceptor, which is inherent to Go. The README "Recovery" row could say so. Not filed because it is a documentation nuance.
- **Keepalive mismatch guidance**: client `Time` below the server `MinTime` (default 5 min), or client `PermitWithoutStream` without server enforcement, causes `GOAWAY too_many_pings`. The README quick start configures both sides consistently, but the `ServerKeepalive`/`ClientKeepalive` docs do not warn. I did not reproduce a failure.
- **Baggage propagation to third parties**: if a service installs a global propagator that includes `propagation.Baggage{}`, the client stats handler forwards baggage to every target, including external ones. That is general OTel behaviour, but `WithClientPropagator` could be documented as the place to restrict it. Not verified against a real collector.
- **No health service or reflection support**: consumers can register `grpc.health.v1` on `Registrar()`, but `Shutdown` has no hook to set `NOT_SERVING` before draining (go-grpc §8, go-api-design §7). Whether the SDK should provide this is a design question for P2.X1/P3.
- `Shutdown` returns `ERR_SYSTEM_TIMEOUT_INTERNAL` even when ctx was *cancelled* rather than timed out. That may be intentional, and the README wording ("exceeds its deadline") covers only the deadline case.
- `ServerConfig.MaxRecvMsgSize`/`MaxSendMsgSize` and the client equivalents silently ignore negative values. That is harmless, but undocumented.
