### C5-001 — Shutdown (ctx cancel) dead-letters or drops the in-flight message; the retry loop ignores ctx
- Area: C (Concurrency) · Severity: HIGH · Effort: M
- Location: messaging/messaging.go:286-336, 328-331, 371-382
- Problem:
  - `handleDelivery` passes a ctx derived from the `Subscribe` ctx to the
    handler (`Extract(ctx, …)` at 288, `procCtx` at 314).
  - When the service shuts down by cancelling that ctx, a handler that honors
    ctx returns `context.Canceled`. The SDK treats this exactly like a business
    failure:
    1. `executeWithRetry` retries with `backoff.Retry`. It has no context, so it
       keeps sleeping and calling the handler with an already-cancelled ctx
       until `MaxAttempts`.
    2. It then calls `msg.Nack(false, false)` (requeue=false).
  - The message goes to the DLX. If the queue has no DLX, RabbitMQ discards it.
  - `Subscribe` cannot return until the retries are exhausted.
- Evidence (throwaway test, fake Acknowledger):
  ```
  handler cancels ctx and returns ctx.Err(), Retry=nil:
    acks=0 nacks=1 requeue=[false]
  ctx already cancelled, Retry{MaxAttempts:4, InitialDelay:200, MaxDelay:400}:
    calls=4 elapsed=1.01s nacks=1 requeue=[false]
  ```
- Impact:
  - Every rolling deploy or SIGTERM loses or dead-letters the messages being
    processed.
  - Shutdown is delayed by up to `MaxAttempts × MaxDelay`. A pod can exceed its
    termination grace period and be SIGKILLed mid-handler.
- Source: eduardo/go-context §2 "Check context cancellation in loops" and
  checklist 4 · eduardo/go-concurrency-review §4 "every blocking operation
  selects on ctx.Done()" · README "Error Handling Summary": "Context cancelled →
  Subscriber exits cleanly".
- Recommendation:
  - Pass ctx to the retry: `backoff.WithContext(bo, ctx)` / `backoff.RetryNotify`
    with a ctx-aware BackOff.
  - When `ctx.Err() != nil` (or the handler error `errors.Is` ctx.Err()), call
    `msg.Nack(false, true)` (requeue) instead of dead-lettering.
  - Consider giving the handler a ctx detached from shutdown
    (`context.WithoutCancel` plus a bounded timeout) so in-flight work can
    finish.
  - Add tests with a fake `amqp.Acknowledger`.
- Breaking: no · Needs approval: no

### C5-002 — `Publish` reports success for messages the broker drops (no publisher confirms, `mandatory=false`, queues declared lazily)
- Area: B/C (correctness) · Severity: HIGH · Effort: M
- Location: messaging/amqp.go:108, 123, 159, 167 (`channel.Publish(…, false, false, …)`);
  messaging/amqp.go:43-81 (no `Confirm`, no `NotifyReturn`); messaging/messaging.go:99, 247;
  messaging/README.md:45-46
- Problem:
  - `Channel.Publish` returns as soon as the frame is written to the socket.
  - Nothing in the package calls `Channel.Confirm`, `PublishWithDeferredConfirm*`
    or `NotifyReturn`, and `mandatory` is always `false`.
  - Queues and bindings are declared only when some process calls `Subscribe`
    (README:45-46). The consequences:
    - A message published before the first consumer of that queue ever started
      (fresh environment, producer deployed first, DLQ that nobody subscribes
      to) is routed to an exchange with no binding and silently discarded.
    - A publish to an exchange the broker does not have (topology drift) makes
      the broker close the channel asynchronously with 404. `Publish` has
      already returned `nil` for that message, and only the *next* publish
      notices and reconnects (amqp.go:159-173).
  - The DLQ described in README "Dead Letter Queues" is itself only declared if
    some service subscribes to it. Otherwise dead-lettered messages are dropped.
- Evidence: `grep -n 'Confirm\|NotifyReturn\|mandatory' messaging/*.go` finds
  nothing besides the four `false, false` literals.
- Impact:
  - Silent message loss on the core publish path.
  - The README "Error Handling Summary" ("Publish fails after all retries →
    error returned") implies delivery that the code does not provide.
  - The retry policy only covers socket errors, not broker rejection.
- Source: eduardo/go-error-handling §5/§9 (errors must not be swallowed) ·
  AGENTS.md §2.1 · RabbitMQ publisher-confirm semantics as exposed by
  amqp091-go `Channel.Confirm` / `PublishWithDeferredConfirmWithContext`.
- Recommendation:
  - Put the publisher channel in confirm mode and wait for the ack (or nack →
    `ERR_MQ_PUBLISH_FAILED`), with a timeout bound to the caller ctx.
  - Publish with `mandatory=true` and turn `basic.return` into an error.
  - Optionally add `WithDeclareTopology()` to declare all queues and bindings
    (including DLQs) in `NewPubSub`.
  - Document the delivery guarantee (at-least-once vs at-most-once) in the
    README.
- Breaking: no · Needs approval: yes. Eager declaration changes the documented
  lazy behavior, and confirms add per-publish latency.

### C5-003 — Default prefetch is unlimited; the client buffers the whole backlog in memory
- Area: F/C · Severity: MEDIUM · Effort: S
- Location: messaging/amqp.go:303 (`ch.Qos(s.queue.Prefetch, 0, false)`); messaging/types.go:135
  (`Prefetch int json:"prefetch,omitempty"`); amqp091-go@v1.16.0 consumers.go:74-97
- Problem:
  - When the topology omits `prefetch` (or misspells it, see C5-010),
    `Qos(0, …)` means "no limit". The broker pushes every ready message to the
    consumer.
  - amqp091-go keeps undelivered messages in an unbounded slice
    (`consumers.buffer`: `queue = append(queue, delivery)`).
  - `Subscribe` handles deliveries one at a time (messaging.go:269-281), so a
    large prefetch gives no throughput. It only moves the backlog from the
    broker into process memory.
  - A negative prefetch is passed through unchecked.
- Evidence: code path above. Also amqp091 consumers.go:79-82 (`var queue
  []*Delivery … queue = append(queue, delivery)`).
- Impact:
  - A backlog of N messages becomes N buffered deliveries in RAM, which risks an
    OOM kill.
  - On crash all of them are redelivered. Other consumers on the same queue
    starve, because the first consumer holds everything unacked.
- Source: eduardo/go-performance-review "Architecture review — unbounded …" ·
  eduardo/go-defensive-coding §7 (zero-value design) · README "Automatic
  Reconnection" (does not mention QoS).
- Recommendation:
  - Treat `Prefetch <= 0` as a safe default (e.g. 1 or a small constant), or
    reject it in validation.
  - Document the default in README.
  - Optionally add bounded concurrent handling so that a prefetch > 1 actually
    helps.
- Breaking: no · Needs approval: yes. It changes runtime behavior for
  topologies that rely on the implicit unlimited prefetch.

### C5-004 — Handler panics are not recovered: a poison message crash-loops the service
- Area: C · Severity: MEDIUM · Effort: S
- Location: messaging/messaging.go:312-326 (handler call at 320), 264-283
- Problem:
  - The user handler runs input-dependent code on broker-supplied data, with no
    `recover`.
  - A panic unwinds through `handleDelivery` and `Subscribe` and terminates the
    process, unless the caller recovers around `Subscribe`. In that case the
    subscriber still exits.
  - The delivery is neither acked nor nacked. It is redelivered after restart,
    panics again, and the service crash-loops.
- Evidence (throwaway test): `recovered=poison acks=0 nacks=0`. The panic
  escaped `handleDelivery` with the message left unsettled.
- Impact:
  - One malformed message takes down the consumer fleet.
  - The DLQ mechanism never engages.
  - The `grpc` package in this SDK already recovers panics, so the behavior is
    inconsistent across transports.
- Source: eduardo/go-concurrency-review §1 "Recover at the goroutine boundary"
  and red flag "Background goroutine running input-dependent code with no
  recover" · eduardo/go-error-handling §9.
- Recommendation:
  - In `run` (messaging.go:312), recover, record the stack on the span, and
    convert the panic into an error that is not retried.
  - Then Nack it without requeue, so it reaches the DLX.
  - Document the behavior.
- Breaking: no · Needs approval: no

### C5-005 — Ack/Nack errors are discarded; at-least-once redelivery is invisible and undocumented
- Area: B · Severity: MEDIUM · Effort: S
- Location: messaging/messaging.go:331 (`_ = msg.Nack(false, false)`), 335 (`_ = msg.Ack(false)`)
- Problem:
  - If the channel dies between the handler's success and the Ack (heartbeat
    timeout, broker restart), `Ack` returns `amqp.ErrClosed`.
  - The error is thrown away with no log, span event or metric. The broker
    redelivers the message after reconnect, so the handler runs twice.
  - The README never states that handlers must be idempotent.
- Evidence: the code lines above. `go-error-handling` checklist 1: "No `_`
  discarding errors (unless explicitly justified with comment)".
- Impact: duplicate side effects with no trace to explain them.
- Source: eduardo/go-error-handling §5 and checklist 1 · eduardo/go-observability §2
  ("RecordError … or the trace shows a green span").
- Recommendation:
  - Record ack/nack failures on `recvSpan` and log them through the injected
    logger.
  - Document at-least-once delivery and the idempotency requirement in README
    "Subscribing".
- Breaking: no · Needs approval: no

### C5-006 — SDK errors are re-encoded: `Subscribe` turns a retriable `ERR_MQ_CONNECTION_FAILED` into a non-retriable `ERR_INTERNAL`; several MQ codes are never used
- Area: B (G) · Severity: MEDIUM · Effort: S
- Location:
  - messaging/messaging.go:249-252 and 258-261: `NewSubscriber` / `Consume`
    errors re-wrapped as `ERR_INTERNAL`.
  - messaging/amqp.go:35-38: `NewPublisher` wraps `connect()`'s AppError
    (`ERR_MQ_CONNECTION_FAILED` or `ERR_MQ_EXCHANGE_ERROR`) inside another
    `ERR_MQ_CONNECTION_FAILED`.
  - messaging/amqp.go:324-327: `Reconnect` wraps twice.
  - messaging/amqp.go:272-273, 286-287, 296-297, 305-306: exchange, queue, bind
    and QoS failures all reported as `CONNECTION_FAILED`.
  - messaging/messaging.go:239, 352, 359: topology lookups reported as
    `ERR_INTERNAL`.
- Problem:
  - AGENTS.md §2.1 and §4 forbid re-encoding an existing `*errorkit.AppError`
    with a generic `ERR_INTERNAL`. §5 lists the pattern as an anti-pattern.
  - The outer code is the one callers see, and its metadata wins: `Subscribe`
    returns `Retriable=false`, HTTP 500, for a broker outage.
  - Specific codes exist but are never produced (grep outside
    `errors_codes.go`: 0 uses each): `ERR_MQ_QUEUE_ERROR`, `ERR_MQ_CHANNEL_ERROR`,
    `ERR_MQ_AUTH_FAILED`, `ERR_MQ_CONSUME_FAILED`, `ERR_MQ_TIMEOUT`,
    `ERR_MQ_UNAVAILABLE`, `ERR_MQ_ERROR`.
  - Authentication failures (`amqp.ErrCredentials`, 403) are mapped to the
    retriable `CONNECTION_FAILED`. As a result `reconnectWithBackoff` loops
    forever on bad credentials (messaging.go:390-407), until ctx ends.
- Evidence (throwaway test: `Subscribe` against a local listener that closes the
  connection):
  ```
  outer=ERR_INTERNAL retriable=false inner=ERR_MQ_CONNECTION_FAILED
  ```
- Impact:
  - Supervisors that restart `Subscribe` based on `Metadata.Retriable` (the
    AGENTS §2.1 "data-driven retry") give up on transient outages and retry
    permanent configuration errors.
  - Dashboards cannot tell auth, topology and outage failures apart.
- Source: AGENTS.md §2.1, §4, §5 · eduardo/go-error-handling §1, §4.
- Recommendation:
  - Return SDK AppErrors unchanged, or add context without changing the code.
  - Map AMQP failures to the specific codes: 403 → `ERR_MQ_AUTH_FAILED`
    (non-retriable); declare/bind → `ERR_MQ_QUEUE_ERROR` /
    `ERR_MQ_EXCHANGE_ERROR`; `Consume` → `ERR_MQ_CONSUME_FAILED`.
  - Use a validation or configuration code for topology lookups.
  - Stop the reconnect loop on non-retriable errors.
- Breaking: no (error codes are data, not API; callers matching on
  `ERR_INTERNAL` would see a different code) · Needs approval: no

### C5-007 — `Publish` ignores its ctx; the publisher mutex is held across dial and network I/O
- Area: C · Severity: MEDIUM · Effort: M
- Location: messaging/messaging.go:143, 195-215, 371-382; messaging/amqp.go:93-136, 138-176
- Problem:
  - `ctx` is used only for the span and for propagation. Neither
    `PublishWithHeaders` nor `executeWithRetry` take a ctx.
  - The AMQP call is `Channel.Publish` rather than `PublishWithContext`
    (amqp091-go@v1.16.0 channel.go:1853), and the backoff has no ctx.
  - `Publisher.mu` is held for the whole call, including `reconnect()` →
    `amqp.DialConfig` (default 30 s connection timeout), twice per call
    (lines 142-150 and 161).
  - With the broker unreachable, every goroutine publishing through the shared
    `PubSub` serializes behind one dial. Callers cannot abort with a deadline.
- Evidence (throwaway test): `Publish` with an **already-cancelled** ctx still
  dialed the broker:
  ```
  dials after Close with cancelled ctx=1 errIsCanceled=false code=ERR_MQ_PUBLISH_FAILED
  ```
- Impact:
  - Request handlers that publish cannot honor their own deadline. A broker
    outage turns into head-of-line blocking for all publishers.
  - Cancellation is reported as `ERR_MQ_PUBLISH_FAILED` instead of a ctx error.
- Source: eduardo/go-context §1–§3 · eduardo/go-concurrency-review §3 ("never
  call out to an external service … while holding one [lock]") and §4.
- Recommendation:
  - Use `PublishWithContext(ctx, …)` and `backoff.WithContext(bo, ctx)`.
  - Check `ctx.Err()` before reconnecting.
  - Do the reconnect outside the critical section (single-flight reconnect,
    then swap the channel under the lock), or bound the dial with
    `amqp.Config.Dial` and a timeout taken from ctx.
  - Wrap ctx errors so that `errors.Is(err, context.Canceled)` holds.
- Breaking: no · Needs approval: no

### C5-008 — `Close` is not terminal: `Publish` after `Close` silently re-dials and leaks a connection; `PubSub.Close` does not stop subscribers
- Area: C (lifecycle) · Severity: MEDIUM · Effort: S
- Location: messaging/amqp.go:97-106, 142-150 (auto-reconnect on `IsClosed()`), 180-202;
  messaging/messaging.go:338-341
- Problem:
  - `Publisher.Close` does not record a closed state. The next `Publish` sees
    `p.conn.IsClosed()==true`, treats it as a dropped link and opens a new
    connection. Nothing will ever close that connection.
  - This happens during shutdown when handlers that are still running publish
    after `defer mq.Close()` has run.
  - `PubSub.Close` closes only the publisher. Active `Subscribe` calls keep
    consuming until their own ctx is cancelled. The `Messager` interface and
    AGENTS §3 (`defer mq.Close()`) suggest `Close` releases the instance.
  - The godoc ("closes the shared publisher connection") is accurate but easy to
    misread.
- Evidence (throwaway test): after `ps.Close()`, a `Publish` produced one new TCP
  connection to the broker endpoint (`dials after Close … =1`). The log shows
  `"publisher connection closed, reconnecting"`.
- Impact:
  - A connection leak after shutdown, and publishes that appear to work after
    `Close`.
  - Subscribers outlive the object their caller believes is closed.
- Source: AGENTS.md §2.6 (lifecycle) · eduardo/go-concurrency-review §1 ("EVERY
  goroutine MUST have a clear termination path") · eduardo/go-defensive-coding §6.
- Recommendation:
  - Add a `closed` flag guarded by `mu`. `Publish` after `Close` returns an
    `ERR_MQ_*` "publisher closed" error.
  - Have `PubSub.Close` cancel or close the active subscribers it created (track
    them), or document clearly in README "Subscribing" that `Close` does not stop
    `Subscribe`.
- Breaking: no · Needs approval: yes, if `Close` starts stopping subscribers
  (behavior change for the `Messager` contract).

### C5-009 — Retry of a multi-routing-key publish re-sends keys that already succeeded; nested retries multiply attempts
- Area: B · Severity: MEDIUM · Effort: S
- Location: messaging/messaging.go:195-215; messaging/amqp.go:159-173
- Problem:
  - `publishOnce` publishes the event once per routing key and returns on the
    first failure. `executeWithRetry` then re-runs the whole closure from the
    first key.
  - If key 1 succeeded and key 2 failed, consumers bound to key 1 get the event
    again on every retry (same `event_id`).
  - Each `PublishWithHeaders` already does its own reconnect plus single retry.
    So `MaxAttempts` really means up to `2 × MaxAttempts` publish attempts and
    up to `2 × MaxAttempts` dials.
- Evidence: control flow at messaging.go:196-210 (loop with early `return err`)
  inside `executeWithRetry(publishOnce, …)` at 215.
- Impact: duplicate deliveries on partial failure, and retry/latency budgets
  larger than configured.
- Source: eduardo/go-error-handling §8 · eduardo/go-api-design §9
  (retries must be idempotent).
- Recommendation:
  - Retry per routing key, tracking which keys are done.
  - Remove one of the two retry layers.
  - Document that consumers must deduplicate on `event_id` (see C5-005).
- Breaking: no · Needs approval: no

### C5-010 — Topology is not validated: typos are ignored, negative `maxAttempts` wraps to effectively unbounded retries, duplicate bindings are dropped silently
- Area: D (defensive) · Severity: MEDIUM · Effort: M
- Location: messaging/topology.go:69-78 (bare `json.Unmarshal`), 49-56 (`GetBindingByQueue`
  returns the first match); messaging/messaging.go:375-380 (`uint64(retry.MaxAttempts)`);
  algorithms/backoff.go:29-41; messaging/README.md:230 (references the
  non-existent `schemas/rabbit-topology.json`, DN-25)
- Problem:
  - `LoadTopologyFromBytes` accepts any JSON:
    - Unknown fields are ignored, so `"prefech"` silently becomes prefetch 0,
      which is unlimited (C5-003).
    - A queue can reference an exchange that is not declared.
    - A queue can have several bindings. Only the first is ever bound or used.
    - Negative and zero numeric values are accepted.
  - `uint64(-1)` wraps to `MaxUint64`, which passes the `< 1` clamp in
    `algorithms`. Retries are then limited only by backoff's default
    `MaxElapsedTime` of 15 min (backoff/v4 exponential.go:83).
  - With `initialDelay`/`maxDelay` 0 the retry is a hot loop with no sleep.
- Evidence (throwaway tests):
  ```
  LoadTopologyFromBytes({"queues":[{"name":"q","prefech":10,"retry":{"maxAttempts":-1}}],
    "bindings":[{q→a,[x]},{q→b,[y]}]})
    → err=<nil> prefetch=0 maxAttempts=-1 bindingUsed=a exchanges=0
  executeWithRetry(fail until attempt 1000, RetryConfig{MaxAttempts:-1})
    → attempts=1000 err=<nil> elapsed=2.8ms
  ```
- Impact:
  - Configuration mistakes appear in production as message loss, a blocked
    queue (one failing message retried for up to 15 min while the consumer
    holds the line), or CPU-burning retry loops.
  - None of them surfaces at startup.
- Source: eduardo/go-defensive-coding §5 and numeric-safety.md "Conversion
  truncates, silently" (gosec G115) · eduardo/go-security-audit §1 ("Decode into
  a typed struct, then validate it") · DN-25.
- Recommendation:
  - Add `Topology.Validate()`, called by the loaders and by `NewPubSub`. It
    should check:
    - names are unique and non-empty;
    - every binding's exchange and DLX exchange is declared;
    - there is at most one binding per queue, or multiple bindings are supported;
    - `MaxAttempts >= 1`, delays >= 0, multiplier >= 1, prefetch >= 0.
  - Decode with `json.Decoder.DisallowUnknownFields()`.
  - Range-check before `uint64(...)`.
  - Ship the JSON schema the README promises, or remove the reference.
- Breaking: no. `DisallowUnknownFields` and validation reject topologies that
  load today · Needs approval: yes (stricter loading changes behavior).

### C5-011 — `WithLogger` is ignored by the publisher; failures are logged at Info with printf-style messages
- Area: G (observability) · Severity: MEDIUM · Effort: S
- Location: messaging/amqp.go:98, 105, 116, 143, 160 (global `logger.Info`);
  messaging/messaging.go:72-77, 411-417
- Problem:
  - `WithLogger` is documented as the logger "for messaging reconnect/retry
    diagnostics". README "Initialisation" also shows it. Only the subscriber's
    `warnReconnect` uses it.
  - `Publisher` has no logger field and always writes to the global zerolog
    logger (DN-24).
  - Publish failures are logged at **Info** (`"publish failed, attempting
    reconnect … error %s"`). The message embeds the error with `Msgf` instead
    of structured fields.
  - `retry_in %d` prints a `time.Duration` as raw nanoseconds.
  - None of these lines carries `trace_id`, although a span is active.
- Evidence: code lines above. `logger.Info`/`Warn` are `Msgf` wrappers
  (logger/wrapper.go:60-61, 93-94).
- Impact:
  - Services that inject a logger (per-tenant, OTLP-bridged) lose the
    publisher's reconnect diagnostics.
  - Alerting on Warn/Error misses publish failures.
  - The messages have high cardinality.
- Source: AGENTS.md §2.3 · eduardo/go-observability §1 (levels, structured
  fields, injected logger) · eduardo/go-error-handling §9 (low-cardinality
  messages).
- Recommendation:
  - Pass the resolved logger into `Publisher`.
  - Log reconnects at Warn with structured fields (`queue`, `error`,
    `retry_in` as a duration string).
  - Use the ctx-aware helpers so the trace IDs are attached.
- Breaking: no · Needs approval: no

- Source: eduardo/go-test-quality §4–§7 (synctest, fakes at boundaries, goleak
  for packages that start goroutines) · eduardo/go-test-table-driven §1
  (`buildQueueArgs` is a canonical table case) · project go-testing-strategy
  "Integration (real infra) … messaging producers" and build-tag table ·
  AGENTS.md §6.
- Recommendation:
  - Add table tests for `buildQueueArgs` and the carrier.
  - Add `handleDelivery` tests with a fake Acknowledger: ack on success, nack

### C5-013 — `Close` errors are unchecked on error and teardown paths
- Area: B/D · Severity: LOW · Effort: S
- Location: messaging/amqp.go:56, 70, 85, 259, 320; messaging/messaging.go:254
  (`defer sub.Close()`)
- Problem:
  - errcheck (baseline V9) flags these lines.
  - In `connect()` the dropped `conn.Close()` error is secondary to the error
    being returned, which is acceptable but undocumented.
  - In `reconnect()`/`Reconnect()` and the deferred `sub.Close()` in
    `Subscribe`, a failed close is invisible. `Subscribe` returns `nil` on ctx
    cancel even if the subscriber connection did not close cleanly.
- Evidence: baseline.md V9 errcheck list (`messaging/amqp.go:56`, `:70`, `:85`,
  `:259`, `:320`, `messaging/messaging.go:254`).
- Impact: teardown failures, such as a connection left half-open, leave no
  trace.
- Source: eduardo/go-defensive-coding §6 · eduardo/go-error-handling checklist 1.
- Recommendation:
  - Join the close error into the returned error (`errors.Join`, as
    `Publisher.Close` already does), or log it through the injected logger.
  - Use `_ =` with a comment where ignoring is intended.
- Breaking: no · Needs approval: no

### C5-014 — Connection options are hard-wired: no TLS config for `amqps://`, no dial timeout or properties; heartbeat detection is slower than documented
- Area: G/D · Severity: LOW · Effort: S
- Location: messaging/amqp.go:44-46, 247-249 (`amqp.Config{Heartbeat: DefaultHeartbeat}`);
  messaging/README.md:97-98; amqp091-go@v1.16.0 connection.go:99-101, 1049, 1084
- Problem:
  - Every dial uses a fixed `amqp.Config`. With `amqps://`, amqp091 uses an
    empty `tls.Config`. A private CA, mTLS client certificates or a TLS version
    floor cannot be configured.
  - The dial timeout and the connection name (`Properties`, which shows in the
    RabbitMQ management UI) are not configurable either.
  - README says the 60 s heartbeat detects dead links "quickly". amqp091 sets
    the read deadline to `3 × interval` (connection.go:1049, 1084), so detection
    takes up to about 180 s. Only then does the subscriber's 5 s reconnect delay
    start.
- Evidence: the code lines above.
- Impact:
  - Production brokers that require mTLS or an internal CA cannot be used.
  - Recovery after a silent network partition takes minutes.
- Source: eduardo/go-security-audit §7 (TLS) · eduardo/go-api-design (contract
  accuracy) · eduardo/go-documentation §1.
- Recommendation:
  - Add `WithAMQPConfig(amqp.Config)` or `WithTLSConfig(*tls.Config)` and
    `WithHeartbeat`/`WithDialTimeout` options. These are additive.
  - Correct the README wording.
- Breaking: no · Needs approval: no

## Strengths

- `Publisher` swaps `conn`/`channel` under `mu`. `PubSub` fields are immutable
  after construction. `Subscriber` state stays inside the `Subscribe` goroutine.
  `go test -race` passes, and no data race was found on the package's own state.
- Explicit acknowledgements (`autoAck=false`, amqp.go:337). The DLX is driven
  by `Nack(requeue=false)` instead of manual republishing.
- `Subscribe` reconnects with a ctx-aware loop (`select` on `ctx.Done()`,
  exponential delay capped at 60 s). After reconnect it redeclares the exchange,
  queue, bindings and QoS.
- `Close` methods try both the channel and the connection and join the errors
  (`errors.Join`, amqp.go:184-200, 354-371).
- Topology loading is explicit:
  - It never walks parent directories, and a test covers that
    (topology_test.go:159).
  - `WithTopology` allows hermetic tests, and `WithTracer`/`WithPropagator`
    allow explicit telemetry.
- W3C trace context and baggage propagate end-to-end over AMQP headers, with
  producer, consumer and process spans. This is the only SDK package that
  records errors and status on spans (DN-10).
- Error codes are registered in `init()` through `errorkit.MustRegister`, with
  tests for idempotent and isolated registration.
- Bindings use the exact routing keys from the topology, never wildcards.

## Open questions

- Publish throughput: the single `Publisher.mu` serializes all publishes on one
  channel. Whether this is a bottleneck needs a benchmark against a real broker,
  which was not run. The skill rule requires evidence, so it is not reported as
  a finding.
- `reconnectWithBackoff` waits `DefaultReconnectDelay` (5 s) before the
  *first* reconnect attempt (messaging.go:397). The intent is unclear (thundering
  herd protection?). Combined with C5-014, recovery takes at least 5 s even for
  a clean broker restart.
- Consumer tag = `serviceName` (messaging.go:247, amqp.go:336). Uniqueness is
  needed only per channel, and each `Subscribe` has its own connection, so this
  looks safe. Not verified against a broker for repeated `Consume` on the same
  channel.
- `amqp.DialConfig` is called with `Config{Heartbeat}` only (no `Locale`, no
  `Dial`). amqp091 fills in defaults for the dial, but whether an empty
  `Locale` is defaulted or sent empty was not checked against a broker.
- Per-call `otel.Tracer("messaging")` / `otel.GetTextMapPropagator()` lookups
  in `tracerOrDefault`/`propagatorOrDefault` (messaging.go:125-137). Cost is not
  measured; probably negligible.
- `Publish` uses the *consumer* queue's `Retry` policy for the publisher
  (documented in the README). Whether a separate publisher policy is wanted is a
  design question for P3.
- Could not verify:
  - Behavior against a real RabbitMQ: channel-level 404/406 closes, consumer
    cancel notifications, redelivery after `ErrClosed` on Ack. No broker was
    used, per the brief. These paths were reasoned from amqp091-go v1.16.0
    source and RabbitMQ semantics.
  - golangci-lint was unavailable in this session, so errcheck results come from
    `baseline.md`.
