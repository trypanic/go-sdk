## postgres (package `database`)

### C4-001 — DSN password leaked in plaintext through the error payload (logs and `PrettyJSON`)
- Area: D (Security) · Severity: HIGH · Effort: S
- Location: postgres/postgres.go:37-42 (also 65-70, 74-79); logger/errorkit.go:43-44; errorkit/fmt.go:215-224
- Problem: if `pgxpool.ParseConfig` fails, `NewPostgresClient` stores the raw
  pgx error with `errorkit.WithPayload(err)`. `*pgconn.ParseConfigError` has an
  exported field `ConnString`, documented by pgx as "the original, unredacted
  connection string". `logger.WithErrorKit` serializes the payload with
  `event.Interface("payload", …)` (JSON), and `AppError.PrettyJSON()` (which
  AGENTS.md §4 says to send in HTTP responses) does the same. The logger's
  `redactingWriter` masks only keys named like `password` or `email`, so a key
  named `ConnString` passes through unredacted. pgx's own `Error()` string
  redacts the password (`u:xxxxxx@`), so the SDK undoes the driver's
  protection.
- Evidence: test against `NewPostgresClient(Config{DSN: "postgres://svc:S3cr3tPw@db.internal:notaport/app"})`, then
  `logger.New(logger.Config{Env: logger.Prod, Writer: &buf}).ErrorCtx(ctx, appErr, "postgres init failed")`:
  ```
  log line contains password: true
  log line: {...,"message":"postgres init failed","payload":{"ConnString":"postgres://svc:S3cr3tPw@db.internal:notaport/app"},"reason":"parse config","retriable":true,...}
  ```
  `appErr.PrettyJSON()` for `postgres://u:secret@host:notaport/db` contained
  `"payload": {"ConnString": "postgres://u:secret@host:notaport/db"}`.
  Realistic triggers: a typo in the port, or a password that contains `/`
  (see C4-007).
- Impact: database credentials reach log storage, the OTLP log pipeline, and
  any HTTP error body built from `PrettyJSON()`. This happens through the
  canonical bootstrap path (AGENTS.md §3 step 5: `logger.Panic(err, "postgres init failed")`).
- Source: eduardo/go-security-audit §5 "NEVER log secrets" and §8; eduardo/go-observability §1 "Sensitive data — NEVER log"; eduardo/go-error-handling §9 (`err.Error()` leaks); AGENTS.md §2.1, §4
- Recommendation: never put the raw driver error in `Payload`. Attach the
  cause with `WithWrapped(err)` (see C4-003). If the README's "carry the
  underlying error in the payload" wording must stay, set the payload to the
  driver's redacted `err.Error()` string, never to the error value. Add a
  regression test asserting that the password appears neither in
  `PrettyJSON()` nor in a log line.
- Breaking: no · Needs approval: no (the README promise "carry the underlying error in the payload" is kept by using the redacted string)

### C4-002 — Every PostgreSQL failure is `ERR_DB_POSTGRES_ERROR` (retriable, HTTP 503), including not-found, constraint violations and caller cancellation
- Area: B (Idiomatic Go / error handling), G · Severity: HIGH · Effort: M
- Location: postgres/stored_procedure.go:32-48, 57-70; postgres/postgres.go:37-80; postgres/errors.go:88-96
- Problem: `StoredProcedure.QueryRow`/`Query` and `NewPostgresClient` map
  every error to `ERR_DB_POSTGRES_ERROR`, whose metadata says
  `Retriable: true, HTTPStatus: 503`. The package also defines
  `ERR_DB_POSTGRES_UNAVAILABLE`, `_TIMEOUT`, `_AUTH_FAILED`,
  `_CONNECTION_FAILED` and `_DEADLOCK`, but no code path uses them (`grep`
  outside `errors.go`: 0 uses each). Two consequences follow. A `QueryRow`
  that matches no row becomes a retriable 503. A unique violation (23505) or a
  cancelled request becomes "service unavailable, retry".
- Evidence: test with the existing `fakeQuerier`/`fakeRows`:
  ```
  no rows: code=ERR_DB_POSTGRES_ERROR retriable=true http=503 is(ErrNoRows)=true closed=true
  unique_violation_23505: code=ERR_DB_POSTGRES_ERROR retriable=true http=503
  deadlock_40P01: code=ERR_DB_POSTGRES_ERROR retriable=true http=503
  context_canceled: code=ERR_DB_POSTGRES_ERROR retriable=true http=503
  deadline_exceeded: code=ERR_DB_POSTGRES_ERROR retriable=true http=503
  ```
- Impact: AGENTS.md §2.1 makes retry decisions depend on
  `Metadata.Retriable`, and §4 tells handlers to answer with
  `Metadata.HTTPStatus`. Consumers that follow the contract retry requests
  that cannot succeed (duplicates, missing rows, a client that disconnected)
  and return 503 for a missing entity. The `mongo` package already maps
  duplicates and not-found (mongo/errors.go:54-66), so the two database
  adapters behave inconsistently.
- Source: eduardo/go-database §2 rule 4 (handle `ErrNoRows` explicitly), §4 and references/locking-and-retries.md (40001/40P01 retryable, 23505 → domain error); eduardo/go-error-handling §9; AGENTS.md §2.1 ("Pick the most specific code available")
- Recommendation: add one classifier (`classifyPgError(err, op)`) used by
  every path. `pgx.ErrNoRows` → a non-retriable 404 code (for example
  `errorkit.ERR_CLIENT_NOT_FOUND` or a new `ERR_DB_POSTGRES_NOT_FOUND`).
  `*pgconn.PgError` class 23 → `ERR_VALIDATION_DUPLICATE` /
  `ERR_VALIDATION_INCONSISTENT`. 40001/40P01 → `ERR_DB_POSTGRES_DEADLOCK`.
  28xxx → `_AUTH_FAILED`. `context.DeadlineExceeded` or `pgconn.Timeout(err)`
  → `_TIMEOUT`. `context.Canceled` → non-retriable. Connect errors →
  `_CONNECTION_FAILED`/`_UNAVAILABLE`. Keep `WithWrapped` so `errors.Is/As`
  keep working.
- Breaking: no (signatures unchanged) · Needs approval: yes (consumer-visible change of error codes and retriability; the README says "Pgx-level errors are wrapped with ERR_DB_POSTGRES_ERROR")

### C4-003 — Pool-construction errors carry the cause as `Payload`, not `Wrapped`: no `errors.Is/As`, and connect/ping failures serialize as "marshal_failed"
- Area: B (error handling) · Severity: MEDIUM · Effort: S
- Location: postgres/postgres.go:39-42, 67-70, 76-79; errorkit/fmt.go:236-240
- Problem: DN-12 confirmed. `errors.Unwrap(err)` is `nil`, so callers cannot
  test `errors.As(err, *pgconn.ConnectError)` or
  `errors.Is(err, context.DeadlineExceeded)`. Connect and ping failures make
  things worse: `*pgconn.ConnectError` embeds `*pgconn.Config`, which contains
  `func` fields. `json.Marshal` therefore fails, so `PrettyJSON()` returns only
  the fallback `{"error":"marshal_failed",…}` (reason and stack lost), and the
  log line records `"payload":"marshaling error: json: unsupported type: pgconn.DialFunc"`.
  The actual cause (for example "connection refused") appears nowhere.
- Evidence: test with `NewPostgresClient(Config{DSN: "postgres://svc:S3cr3tPw@127.0.0.1:1/app?sslmode=disable"})`:
  ```
  code=ERR_DB_POSTGRES_ERROR reason="ping database" errors.As(ConnectError)=false
  PrettyJSON ... head: {"error":"marshal_failed","id":"01M6J064F4P17M08XW6Y2W294X","code":"ERR_DB_POSTGRES_ERROR"}
  log ... "payload":"marshaling error: json: unsupported type: pgconn.DialFunc","reason":"ping database"
  ```
  For the parse path: `errors.As(ParseConfigError)=false unwrap=<nil>`.
- Impact: the most common start-up failure (database unreachable) is logged
  without its cause. Callers cannot classify the error. AGENTS.md §2.1
  ("Wrap, do not re-encode") is not followed.
- Source: eduardo/go-error-handling §3-4 (keep the chain walkable); AGENTS.md §2.1; discovery DN-12
- Recommendation: use `errorkit.WithWrapped(err)` on all three paths (the
  logger already emits `wrapped_error` through the redacted `Error()`). Keep
  a redacted string payload only if the README wording is kept (C4-001).
  Classify with C4-002.
- Breaking: no · Needs approval: no

### C4-004 — `NewPostgresClient` cannot be cancelled: no `context.Context`, fixed 5 s `context.Background()` budget
- Area: C (Concurrency / context) · Severity: MEDIUM · Effort: S
- Location: postgres/postgres.go:30, 61-63, 88
- Problem: pool creation and the start-up ping run under
  `context.WithTimeout(context.Background(), 5*time.Second)`. The caller
  cannot shorten the budget (a SIGTERM during start-up waits up to 5 s), cannot
  lengthen it (slow DNS or TLS on a cold cluster fails at 5 s whatever
  `connect_timeout` the DSN carries), and cannot propagate a start-up trace.
  `mongodb.New(ctx, cfg)` takes a context, so the two adapters differ.
- Evidence: postgres.go:61-63 `ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)`; signature `func NewPostgresClient(cfg Config) (*pgxpool.Pool, error)`; README "connects with a 5-second timeout context".
- Impact: start-up is not interruptible and not configurable. This is the
  red flag "`context.Background()` used where parent context was available"
  at the API level.
- Source: eduardo/go-context §1, §3 (timeout budgets); eduardo/go-concurrency-review §4 and Red Flags; discovery §5 ("no ctx — P2.X1/C4 question")
- Recommendation: add `NewPostgresClientContext(ctx, cfg)` and
  `NewPostgresClientFromEnvContext(ctx, cfg)` that derive the 5 s default only
  when `ctx` has no deadline. Have the current functions delegate with
  `context.Background()`. Optionally add `Config.ConnectTimeout`.
- Breaking: no (additive) · Needs approval: yes (new exported API; P2.X1 owns API consistency)

### C4-005 — `WrapWithInstrumenter(sp, nil)` does not disable tracing, contrary to the README
- Area: G (Public API) · Severity: MEDIUM · Effort: S
- Location: postgres/tracing.go:34-39; telemetry/trace.go:143-146; postgres/README.md:186, 221
- Problem: DN-11 confirmed. The README says "pass `nil` to disable tracing
  entirely" and "Pass `nil` to `WrapWithInstrumenter` to skip the wrapper".
  The implementation always returns `*tracingStoredProcedurer`, and a nil
  `*Instrumenter` falls back to the global tracer. The sibling
  `mongo.WrapWithInstrumenter` does return `inner` for nil
  (mongo/tracing.go:36-41).
- Evidence: test output `WrapWithInstrumenter(nil) type=*database.tracingStoredProcedurer[int] tracingWrapper=true`.
- Impact: consumers who opt out still emit one span per call through the
  global provider. There is also no documented untraced constructor (the
  untraced path is the struct literal `StoredProcedure[T]{Pool: p}`), so the
  AGENTS.md §2.2 triplet is incomplete.
- Source: postgres/README.md (contract); AGENTS.md §2.2; eduardo/go-api-design ("APIs are contracts")
- Recommendation: add `if instrumenter == nil { return inner }` as in `mongo`,
  plus a test. The code then matches the documented contract.
- Breaking: no · Needs approval: no (aligns code with the README contract; consumers passing nil stop getting spans, as documented)

### C4-006 — Stored-procedure spans: generic name for schema-qualified or `CALL` statements, no `db.*` attributes, failures not recorded
- Area: G (Observability) · Severity: LOW · Effort: S
- Location: postgres/tracing.go:11, 46-79
- Problem: the regex `(?i)\bFROM\s+(\w+)\s*\(` only matches unqualified
  `SELECT … FROM fn(`. Spans carry no `db.system`/`db.operation` attributes,
  and errors returned by `inner` are not recorded on the span (repo-wide
  DN-10, owned by P2.X1).
- Evidence: test output: `"SELECT * FROM get_item($1)" -> postgres.get_item`; `"SELECT * FROM public.get_item($1)" -> postgres.query`; `"CALL do_work($1)" -> postgres.query`.
- Impact: traces lump schema-qualified procedures and real stored procedures
  (`CALL`) together under `postgres.query`. Failed calls show as green spans.
- Source: eduardo/go-observability §2 (name after the operation; `RecordError` + `SetStatus`); AGENTS.md §2.2 (use `telemetry.DB` naming)
- Recommendation: extend the regex to `(?:CALL|FROM)\s+((?:\w+\.)?\w+)\s*\(`.
  Add `db.system=postgresql` and the procedure name as attributes. Record the
  error and set the status in the wrapper (coordinate with the DN-10 fix).
- Breaking: no · Needs approval: no

### C4-007 — DSN normalization handles only `@` in the password; README says the password is percent-encoded
- Area: B · Severity: LOW · Effort: S
- Location: postgres/postgres.go:98-136; postgres/README.md:152-157
- Problem: the authority ends at the first `/`, `?` or `#`, so a raw password
  containing `/` is cut off and the DSN fails to parse (which then triggers
  C4-001). `?` and `#` happen to parse in pgx v5.12, but `/` does not. The
  README claims the function "percent-encodes the password (and only the
  password)".
- Evidence: test output: `"postgres://u:pa/ss@db.internal:5432/app" -> unchanged -> parse error: cannot parse ... invalid port`; `"postgres://u:p@ss@…" -> "postgres://u:p%40ss@…" -> password="p@ss"`.
- Impact: valid passwords cause a start-up failure with a misleading
  "invalid port" error. The error path leaks the DSN (C4-001).
- Source: eduardo/go-defensive-coding (silent corruption at boundaries); eduardo/go-test-quality §4 (fuzz parsers)
- Recommendation: find the userinfo end as the last `@` before the first `/`
  that follows it, or document that `/` must be pre-encoded. Add a fuzz target
  `FuzzNormalizePostgresDSN` (idempotency plus round-trip through
  `pgconn.ParseConfig`). Fix the README wording.
- Breaking: no · Needs approval: no

## mongo (package `mongodb`)

### C4-010 — Mongo error classification contradicts its README and marks cancellations and config errors as retriable
- Area: B (error handling), G · Severity: MEDIUM · Effort: S
- Location: mongo/adapter.go:32-37, 47-52; mongo/errors.go:42-72; mongo/client.go:62-65, 133-140; mongo/README.md:221-226
- Problem: (1) `singleResultAdapter.Decode` sends decode failures through
  `WrapOperationError` and they come out as `ERR_DB_MONGO_ERROR` (retriable,
  503). The README table says "Decode failure (cursor/SingleResult) →
  `ERR_DB_MONGO_DECODE_FAILED`". (2) In the other direction,
  `cursorAdapter.All` maps *every* error to `DECODE_FAILED` (non-retriable,
  500), including network or `getMore` failures during iteration.
  (3) `context.Canceled`, `mongo.ErrClientDisconnected` and
  `mongo.ErrNilDocument` become retriable 503s. Driver timeouts that do not
  wrap `context.DeadlineExceeded` are not detected, because
  `mongo.IsTimeout`/`mongo.IsNetworkError` are not used. (4) URI parse and
  option-validation errors are `ERR_DB_MONGO_UNAVAILABLE` (retriable),
  although they are configuration errors.
- Evidence: test output:
  ```
  SingleResult decode failure: code=ERR_DB_MONGO_ERROR retriable=true http=503
  Cursor.All decode failure: code=ERR_DB_MONGO_DECODE_FAILED retriable=false http=500
  canceled: code=ERR_DB_MONGO_ERROR retriable=true http=503
  client_closed: code=ERR_DB_MONGO_ERROR retriable=true http=503
  nil_document: code=ERR_DB_MONGO_ERROR retriable=true http=503
  MaxPoolSize=5: code=ERR_DB_MONGO_UNAVAILABLE retriable=true (cause: minPoolSize must be less than or equal to maxPoolSize …)
  ```
- Impact: a schema mismatch on `FindOne` triggers retries. A transient
  network error while draining a cursor is reported as permanent. Retry
  policies that follow AGENTS.md §2.1 make the wrong decision.
- Source: mongo/README.md "Error Handling" (contract); AGENTS.md §2.1; eduardo/go-error-handling §9
- Recommendation: in `Decode`, return `WrapOperationError` only for
  `ErrNoDocuments`/driver errors and `WrapDecodeError` otherwise (check
  `result.Err()` first). In `All`, classify with `WrapOperationError` unless
  the error is a decode error. Treat `context.Canceled` as non-retriable, add
  `mongo.IsTimeout` → `_TIMEOUT` and `mongo.IsNetworkError` → `_UNAVAILABLE`,
  and map connect-time option errors to `ERR_SYSTEM_CONFIG_INVALID`.
- Breaking: no · Needs approval: no for (1) (brings the code in line with the README); yes for (2)-(4) (consumer-visible code changes)

### C4-011 — Defaults silently override URI options and make `MaxPoolSize < 10` fail at start-up
- Area: B / G · Severity: MEDIUM · Effort: S
- Location: mongo/client.go:51-60, 108-131; mongo/README.md:96-107
- Problem: `NewWithInstrumenter` calls `ApplyURI` and then unconditionally
  calls `SetConnectTimeout`, `SetServerSelectionTimeout`, `SetMaxPoolSize`,
  `SetMinPoolSize`, `SetMaxConnIdleTime` and `SetRetryWrites` with values from
  `applyDefaults`. Any `maxPoolSize`, `minPoolSize`, `retryWrites=false`,
  `connectTimeoutMS` or `serverSelectionTimeoutMS` in the URI is therefore
  discarded. `retryWrites=false` matters for deployments that do not support
  retryable writes. `MinPoolSize` defaults to 10 even when the caller sets
  `MaxPoolSize` below 10, and the driver then rejects the options. A
  `MinPoolSize` of 0 (the driver default) cannot be expressed.
- Evidence: the same builder chain as client.go:53-60, applied to
  `mongodb://h1:27017/?maxPoolSize=50&minPoolSize=0&retryWrites=false&connectTimeoutMS=1000&serverSelectionTimeoutMS=30000`
  → `effective: maxPool=100 minPool=10 retryWrites=true connectTimeout=10s serverSelection=5s`.
  `NewWithoutTracing(ctx, Config{URI: …, MaxPoolSize: 5})` → `ERR_DB_MONGO_UNAVAILABLE`,
  cause `minPoolSize must be less than or equal to maxPoolSize, got minPoolSize=10 maxPoolSize=5`.
- Impact: operators who tune the pool or disable retryable writes in the
  connection string get different behavior without any warning. A small
  `MaxPoolSize` makes the service fail at start-up with a misleading
  "unavailable" error. Each process also opens at least 10 connections per
  server whether or not it needs them.
- Source: eduardo/go-database §1 (configure the pool explicitly); eduardo/go-defensive-coding §7 (zero-value design); eduardo/go-coding-standards §13

  field nor the URI sets the option (inspect the `ClientOptions` after
  `ApplyURI`). Clamp the default `MinPoolSize` to `min(10, MaxPoolSize)`.
  Document the precedence.
- Breaking: no · Needs approval: yes (changes effective pool and retry settings for consumers whose URI carries options)

### C4-019 — Cursor-returning `Find` spans close before iteration; `Ping`/`Close` untraced; start-up ping ignores `ServerSelectionTimeout`

### C4-012 — `FileStorage` corrupts data when two instances or processes share a directory (shared fixed temp-file name, in-process lock only)
- Area: C (Concurrency) · Severity: HIGH · Effort: M
- Location: storage/file_storage.go:18-21, 37-51, 200-222; storage/README.md:58-102
- Problem: DN-34 confirmed, and it is worse than "undocumented". The only
  synchronization is a per-instance `sync.RWMutex`, and every writer uses the
  same temp path `<file>.tmp`. Two `FileStorage` values on one `baseDir` (two
  replicas on a shared volume, an overlapping restart, or two components in
  one process) run read-modify-write concurrently. Their `os.WriteFile` calls
  truncate and interleave in the same temp file, then `rename` it. The README
  sells `FileStorage` as the "Persistent append-log across restarts" with
  "Atomicity", and mentions neither restriction.
- Evidence: test with 200 concurrent `Append("k", …)` calls split across two
  instances on one `t.TempDir()`:
  ```
  200 appends via 2 instances: stored=0 appendErrors=88 listErr=[ERR_STORAGE_ERROR] failed to decode storage file
  ```
  The final file was not valid JSON, so all 200 records were lost (not just
  some updates).
- Impact: silent loss of the whole key on concurrent use, discovered only on
  the next read.
- Source: eduardo/go-concurrency-review §3 and "Shared state" audit pass; .skillshare/go-testing-strategy (atomicity pattern with N goroutines); eduardo/go-defensive-coding §6
- Recommendation: write through a unique temp file
  (`os.CreateTemp(dir, name+".*.tmp")`, see C4-013) so concurrent writers
  never share a temp file. Add an advisory lock (`flock` on a lock file per
  `baseDir`, or per key) for cross-instance read-modify-write, or document
  explicitly that one `FileStorage` per directory per host is the only
  supported mode. Add the concurrency test above as a regression.
- Breaking: no · Needs approval: no (documentation and an internal fix; a lock-file dependency on `syscall` is stdlib)

### C4-013 — Fixed, predictable temp-file name follows symlinks: an attacker with write access to `baseDir` can overwrite arbitrary files
- Area: D (Security) · Severity: MEDIUM · Effort: S
- Location: storage/file_storage.go:208-209
- Problem: `os.WriteFile(filename+".tmp", …, 0o644)` opens with
  `O_CREATE|O_TRUNC` and follows an existing symlink. Anyone who can create
  `<hex(key)>.json.tmp` in `baseDir` before an `Append` can make the process
  overwrite any file it can write. Afterwards the symlink is renamed onto the
  data file. Keys are public input, so their hex names are predictable.
- Evidence: test that created the symlink `<hex("k")>.json.tmp → victim.txt`
  and then called `fs.Append("k", "attacker-controlled")`:
  `append err=<nil>; victim now="[\n  \"attacker-controlled\"\n]"`.
- Impact: needs a second failure (a shared or world-writable `baseDir` such as
  a directory under `/tmp`, or a multi-tenant volume), hence MEDIUM.
  Exploited, it is an arbitrary-file clobber with the service's privileges.
- Source: eduardo/go-security-audit §3 "Paths" and references/injection.md (`os.Root`, symlinks); eduardo/go-modernize Priority 1 (`os.Root` for path containment, Go 1.24+)
- Recommendation: create the temp file with `os.CreateTemp(fs.baseDir, ".tmp-*")`
  (`O_EXCL`, random name, mode 0600), write, `f.Sync()`, `Close`, then
  `os.Rename`. Optionally open `baseDir` once with `os.OpenRoot` and do every
  operation through the `*os.Root`.
- Breaking: no · Needs approval: no

### C4-014 — `Clear()` deletes every `*.json` in `baseDir`, including files the store did not create
- Area: B (correctness) / D · Severity: MEDIUM · Effort: S
- Location: storage/file_storage.go:91-116 (vs 131-139); storage/README.md:109

- Source: eduardo/go-defensive-coding (silent corruption); eduardo/go-documentation §1 (document behavior precisely)

- Breaking: no · Needs approval: yes (the README literally documents "unlink every *.json")

### C4-016 — No durability: writes are never `fsync`ed and a zero-length file is read as an empty list
- Area: C / B (correctness) · Severity: MEDIUM · Effort: S
- Location: storage/file_storage.go:185-187, 200-222; storage/README.md:98-102
- Problem: `writeUnsafe` neither syncs the temp file before `rename` nor syncs
  the directory afterwards. After a crash or power loss the renamed file can
  be empty on some filesystems. `readUnsafe` then treats `len(data) == 0` as
  `[]T{}`, and the next `Append` overwrites it with a one-element list, with
  no error. The README advertises "Atomicity" without qualification.
- Evidence: code lines above (no `Sync` call anywhere in `storage/`:
  `grep -n Sync storage/*.go` → none). Not reproducible without a crash; the
  silent-empty branch is at lines 185-187.
- Impact: a crash can silently truncate a whole key's history.
- Source: eduardo/go-defensive-coding §6 (check errors on written resources; silent data loss); discovery DN-34
- Recommendation: use `CreateTemp` → write → `f.Sync()` → `Close` (check the
  error) → `Rename` → `Sync` on the directory handle. Treat a zero-length
  existing file as corruption (an error), not as empty. Document the
  durability guarantee precisely.
- Breaking: no · Needs approval: no

### C4-017 — `FileStorage.Append` rewrites and re-indents the whole file on every call (O(n) per append, O(n²) per log)
- Area: F (Performance) · Severity: MEDIUM · Effort: M
- Location: storage/file_storage.go:37-51, 174-222 (`MarshalIndent` at 201); storage/file_storage.go:60-69 (extra `Stat` before `ReadFile` in `List`)
- Problem: each `Append` reads the full JSON array, unmarshals it, appends,
  `json.MarshalIndent`s the full array and writes it back. Cost grows
  linearly per append, so building an append log is quadratic. `List` also
  calls `os.Stat` and then `readUnsafe`, which already handles `ErrNotExist`.
- Evidence: single-run timing from an audit test (no benchstat, 64-byte
  records, one key; indicative only):
  ```
  n=500  appends: total=430ms  avg≈0.86ms  file=51 KB
  n=1000 appends: total=1.67s  avg≈1.67ms  file=103 KB
  n=2000 appends: total=5.19s  avg≈2.59ms  file=207 KB
  ```
  Doubling n roughly triples or quadruples the total time.
- Impact: an "append-log" degrades with history size. A few thousand records
  per key already cost seconds and a full-file write per event.
- Source: eduardo/go-performance-review §1, §7 (streaming, batching) and "architecture review" mode; eduardo/go-data-structures §3
- Recommendation: switch the on-disk format to JSON Lines and append with
  `O_APPEND` (one encoded line per item; `List` streams lines), or at least
  drop `MarshalIndent` and the redundant `Stat`. Add `BenchmarkFileStorageAppend`
  with `b.Loop()` and sizes, and compare with `benchstat` before and after.
  A format change needs a reader for the old array format.
- Breaking: no (on-disk format is not part of the documented API, but existing files must stay readable) · Needs approval: yes (persistent format change)

### C4-018 — All storage failures are `ERR_STORAGE_ERROR` (retriable, 503), including programmer errors and the undocumented key-length limit

## Strengths

- **No SQL is built by the SDK.** `StoredProcedure` passes the caller's SQL
  text unchanged and every value as a positional parameter. The JSON argument
  of `QueryJSON`/`QueryRowJSON` is passed as a bound parameter
  (stored_procedure.go:108-121), never interpolated. No SQL-injection sink
  exists in the helpers; `.semgrep.yml` keeps a `sql-string-concat` rule for
  consumers. The README examples use placeholders.
- **`rows.Close`/`rows.Err` are handled correctly.** `pgx.CollectRows` and
  `pgx.CollectOneRow` close the rows and return `rows.Err()` (pgx v5.12
  rows.go:492-514). The audit test confirmed that a mid-stream `rows.Err()`
  surfaces and that rows end closed. The `nosemgrep: defer-rows-close`
  suppressions (stored_procedure.go:31, 56) are justified and commented.
- `QueryRow`/`Query` errors use `WithWrapped`, so `errors.Is(err, pgx.ErrNoRows)`
  works today (verified). Only the code and metadata are wrong (C4-002).
- **Pool lifecycle:** the ping failure closes the pool (postgres.go:74-75),
  and mongo disconnects on ping failure (client.go:70-72). Tuning fields only
  override pgx defaults when non-zero, which avoids the `MaxConns must be > 0`
  trap. `StoredProcedure` is stateless with value receivers, and the wrappers
  hold immutable fields, so both are safe to share, as documented.
- `NewPostgresClient` never reads the environment; `NewPostgresClientFromEnv`
  is the explicit opt-in (AGENTS.md §2.4), and a test locks this in.
- **Mongo:** `RetryWrites *bool` correctly expresses three states, with
  tests. `WrapWithInstrumenter(nil)` returns the inner client. Driver
  URI-parse errors do not echo credentials (verified with three malformed
  URIs). Duplicate-key and not-found are classified (mongo/errors.go:54-66).
  Filters and updates are passed unchanged as `any` (no string-built queries
  in the SDK).
- **storage:** hex-encoded file names make path traversal through keys
  impossible (`a/b`, `../x` and `:` all become `[0-9a-f]+.json`), and a test
  covers collisions. `MemoryStorage` returns defensive copies and has an
  aliasing regression test. Error paths (read-only directory, corrupt JSON)
  are tested. The interface split (`KVStorager` vs `AppendLogStorager`) is
  clear, and conformance is asserted at compile time.
- `go vet`, `staticcheck` and `go test -race` are clean for all three
  packages.

## Open questions

1. `pgRowMapper[T]` picks `RowTo[T]` for any non-struct `T`, so `T = *Item`
   (pointer to struct) would try to scan one column into `*Item` instead of
   using `RowToAddrOfStructByNameLax`. I did not reproduce this against a real
   row; the README only promises struct or scalar `T`.
2. `mongodb.Config.Database` is never validated. I did not verify what
   `mongo.Client.Database("")` operations return (late failure versus clear
   error).
3. NoSQL operator injection: `Collection` methods accept `filter any` unchanged.
   If consumers decode request JSON straight into `bson.M` filters, operators
   such as `$where`/`$regex` become injectable. That is consumer
   responsibility, but the README gives no guidance. Should the SDK document
   it, or offer a typed filter helper?
4. pgx redacts passwords in `ParseConfigError.Error()` only "on a best-effort
   basis" for malformed input (pgconn/errors.go:132, 243-246). Once C4-001
   moves the cause to `Wrapped`, the logged `wrapped_error` relies on that
   best effort; fuzzing `redactPW` with pathological DSNs was out of scope.
5. Whether any consumer service actually loops on
   `Metadata.Retriable` for database errors (which turns C4-002 from wrong
   metadata into real retry storms) cannot be checked from this repository.
6. semgrep could not run on this host (Python 3.15/protobuf crash). The
   per-package semgrep result is therefore taken from the baseline (0
   findings), not re-verified here.
