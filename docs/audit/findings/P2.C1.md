### C1-001 — `logger.New` mutates process-wide zerolog state (global level and time format)
- Area: C (Concurrency) / B (Correctness) · Severity: HIGH · Effort: S
- Location: logger/instance.go:42,59 → logger/config.go:301-313 (303-308 `zerolog.SetGlobalLevel`, 310 `zerolog.TimeFieldFormat`)
- Problem: `New` is documented as "does not mutate the package-level global"
  and the README says it builds a logger "without mutating package state";
  AGENTS.md §2.3 says "No SDK package mutates the global zerolog logger
  except `logger.Init`". Every `New` call goes through
  `newLoggerWithWriter`, which sets zerolog's process-wide level and
  overwrites `zerolog.TimeFieldFormat`. Loggers created by `New` carry no
  level of their own, so their filtering depends on whichever logger was
  constructed last. The `TimeFieldFormat` write is unsynchronized and is
  read by every zerolog event in the process.
- Evidence (temporary test, then removed):
  ```text
  after New(Dev):  global level=debug
  after New(Prod): global level=info
  dev logger debug output after a Prod logger was constructed: ""
  prod logger debug output after a Dev logger was constructed:
    "{\"level\":\"debug\",\"message\":\"debug-from-prod-logger\",...}"
  ```
  `go test -race` with one goroutine logging through a `*Logger` and one
  calling `New(Config{Env: Prod, Writer: io.Discard})`:
  ```text
  WARNING: DATA RACE
    logger/config.go:310   (write zerolog.TimeFieldFormat)
    logger/instance.go:59
    zerolog@v1.35.1/event.go:760 (read, Timestamp)
    logger/instance.go:67
  --- FAIL: TestAuditRaceNewWhileLogging
  ```
  The existing `TestNewDoesNotMutateGlobal` (logger/instance_test.go:13)
  only checks the package variable `global`, so it does not catch this.
- Impact: a library or component that builds its own `logger.New(Prod)`
  silently suppresses Debug output for every zerolog logger in the process
  (including the application's own); a `New(Dev)` turns Debug on for a
  production logger, which can emit debug-level data in production.
  Constructing loggers concurrently with logging is a data race.
- Source: AGENTS.md §2.3, §2.6 · logger/README.md "Instance API" ·
  eduardo/go-concurrency-review §5 "Avoid Mutable Globals", §3 ·
  eduardo/go-observability §1 (logger injected, not global)
- Recommendation: set the level on the instance
  (`zerolog.New(w).Level(level)`) and stop calling `SetGlobalLevel` /
  writing `TimeFieldFormat` from `New`. If the Unix time format is wanted,
  set it once in `Init` (the only function allowed to touch zerolog
  globals) or use a per-logger timestamp hook. Extend
  `TestNewDoesNotMutateGlobal` to assert `zerolog.GlobalLevel()` and
  `zerolog.TimeFieldFormat` are unchanged, and add a `-race` test.
- Breaking: no (this brings the code in line with the documented contract;
  callers who relied on the undocumented global side effect see a behaviour
  change) · Needs approval: no

### C1-002 — `PrettyJSON`, recommended for HTTP responses, sends stack traces, absolute paths and internal error text to clients
- Area: D (Security) · Severity: HIGH · Effort: M
- Location: errorkit/fmt.go:202-245 (217 `stack_trace`, 215 `payload`, 232-236 `wrapped.message`); errorkit/error.go:173-174, 189-197; errorkit/stack.go:107-113; AGENTS.md:256-257; errorkit/README.md:205-206
- Problem: AGENTS.md §4 says "HTTP handler responses should serialize
  `appErr.PrettyJSON()`", the `error.go` comment shows
  `w.Write([]byte(err.PrettyJSON()))`, and the README calls it "ideal for
  HTTP responses". `JSONFormatter.Format` always includes the full stack
  trace (package, function, file, line), the raw `Payload`, and
  `Wrapped.Error()` (the text of the underlying driver or library error).
  `formatFilePath` only shortens paths containing `market-ecosystem/` (a
  path from another repository), so file paths are absolute build paths.
- Evidence (temporary test, then removed):
  ```text
  first frame file="/home/trypanic/.proto/tools/go/1.27.3/src/testing/testing.go"
  PrettyJSON contains abs path: true
  ```
  `fmt.go:232-236` copies `e.Wrapped.Error()` into `"wrapped":{"message":…}`
  unchanged.
- Impact: following the documented guidance exposes internal layout
  (package/function names, absolute build-host paths, Go toolchain paths),
  dependency error text (SQL/driver messages, hostnames, URLs) and whatever
  the caller placed in `Payload` to any HTTP client (STRIDE "Information
  disclosure").
- Source: eduardo/go-error-handling §9 "Translate before it reaches a user" ·
  eduardo/go-security-audit "Important — Error messages don't leak
  internals", references/threat-model.md (Information disclosure) ·
  eduardo/go-api-design §8 "Internal errors should NEVER leak to clients"
- Recommendation: add a client-safe serializer (for example
  `AppError.PublicJSON()` / `JSONFormatter{IncludeInternal: false}`) that
  emits only `code`, `reason` (or `Metadata.Description`), `id`,
  `trace_id`, and keeps the stack, wrapped text and payload for logs. Change
  AGENTS.md §4, the README and the `error.go` comment to recommend it.
  Remove or make configurable the hard-coded `market-ecosystem/` root
  (see also C1-015). Keep `PrettyJSON` unchanged for compatibility.
- Breaking: no (additive API + documentation change) · Needs approval: yes
  (contradicts the AGENTS.md §4 guidance, which is a project contract)

### C1-003 — The redacting writer re-parses every log line (and every string field) as JSON: ~60× slower than zerolog
- Area: F (Performance) · Severity: MEDIUM · Effort: M
- Location: logger/config.go:312, 323-344 (`redactingWriter.Write`), 204-255 (`compactAndRedactJSON`, `redactStructuredValue`, 248-250); logger/otlp.go:47-50 (second decode on the OTLP path); logger/logger.go:14-21
- Problem: every logger built by `Init`/`New` wraps its writer in
  `redactingWriter`, which decodes the whole line into `map[string]any` and
  re-marshals it. `redactStructuredValue` then calls `compactAndRedactJSON`
  — a new `json.Decoder` — on every string value, and recurses into it.
  On the OTLP path the line is decoded again by `OTLPWriter.Write`. Side
  effects: keys come out sorted alphabetically and duplicate keys collapse
  to one.
- Evidence (`go test -bench -benchmem -count=5`, temporary benchmarks, then removed):
  ```text
  BenchmarkAuditRawZerolog-16      ~123 ns/op       0 B/op     0 allocs/op
  BenchmarkAuditSDKLoggerProd-16  ~7.7–9.1 µs/op  5362 B/op   105 allocs/op   (same 3-field event)
  BenchmarkAuditSDKErrorCtx-16    ~42–46 µs/op   31451 B/op   551 allocs/op   (ErrorCtx with a 32-frame AppError)
  BenchmarkAuditOTLPWriterParse   ~7.3–7.7 µs/op 5359 B/op   105 allocs/op   (redactingWriter alone)
  ```
  Output order example: `{"api_key":…,"authorization":…,…,"level":"info","message":…,"time":…}`.
  Secondary: when `Init` was not called, `globalLogger()` builds a new
  zerolog logger on every call (logger.go:19-20).
- Impact: logging costs tens of microseconds and hundreds of allocations
  per error line, which removes the reason for choosing zerolog and adds GC
  pressure on hot paths (request logging, consumer loops).
- Source: eduardo/go-performance-review §1, §8 and references/logging.md ·
  eduardo/go-observability §1 "Cost and control"
- Recommendation: (1) only enter the slow path when the line can contain a
  sensitive key (a cheap `bytes.Contains` pre-filter on the key list);
  (2) only try `compactAndRedactJSON` on strings whose first non-space byte
  is `{` or `[`; (3) better, redact at field-construction time (a typed
  sensitive value or a zerolog hook) so the writer stays a pass-through;
  (4) cache the fallback logger in `globalLogger()`. Add the benchmarks
  above to the package to guard against regressions.
- Breaking: no · Needs approval: no

### C1-004 — Log redaction only covers `password`/`email`-like keys; tokens, secrets, credentials in DSNs and free text pass through
- Area: D (Security) · Severity: MEDIUM · Effort: S
- Location: logger/config.go:257-287 (`shouldRedactEmailField`, `shouldRedactPasswordField`, `maskEmailDomain`); logger/errorkit.go:43-50 (payload and wrapped error logged verbatim)
- Problem: redaction is a key-name deny-list of two families. Common
  secret-bearing keys (`token`, `authorization`, `api_key`, `secret`,
  `cookie`, `set-cookie`, `access_token`, `refresh_token`, `dsn`) are not
  covered; values (for example credentials embedded in a URL) and the
  message are never inspected; email masking keeps the local part (a
  personal identifier). `WithErrorKit` logs `Payload` and
  `Wrapped.Error()` as-is, so redaction depends on the payload's key names.
- Evidence (temporary test, then removed; `logger.New(Config{Env: Prod})`):
  ```text
  {"api_key":"sk-123","authorization":"Bearer abc","cookie":"session=x",
   "dsn":"postgres://user:pa55@db:5432/app","email":"john.doe@*****",
   "level":"info","message":"contact jane@example.com","password":"*****",
   "secret":"s3","time":…,"token":"tok-secret"}
  ```
- Impact: credentials and personal data reach stdout and the OTLP
  collector (sent in plaintext, see C1-010) whenever a caller logs them
  under a common key name or inside an error payload.
- Source: eduardo/go-security-audit §5, §8 · eduardo/go-observability §1
  "Sensitive data — NEVER log" · AGENTS.md §2.5 (redaction-by-default
  principle, stated for HTTP bodies)
- Recommendation: extend the key list (tokens, secrets, authorization,
  cookies, API keys, DSN/URL user-info), mask URL user-info in string
  values, make the policy configurable through `Config` (a
  `Redactor func(key string, v any) any`), and document the policy in
  logger/README.md (today it is not documented at all). Consider masking
  the email local part too.
- Breaking: no (more redaction; log output changes for the newly covered
  keys) · Needs approval: no

### C1-005 — Unsynchronized mutable globals in `errorkit` (`MaxStackDepth`, `ColorsEnabled`, `GenerateID`, exported `ErrorRegistry` map)
- Area: C (Concurrency) · Severity: MEDIUM · Effort: M
- Location: errorkit/config.go:15, 23-25, 44-52; errorkit/colors.go:18, 21-36; errorkit/idgen.go:35, 160-166; errorkit/registry.go:5-8; errorkit/error.go:65, 72
- Problem: `SetMaxStackDepth`, `InitFromEnv`, `DisableColors`/`EnableColors`
  and `SetIDGenerator` write plain package variables that `NewError`,
  `Pretty` and `FormatColored` read without synchronization. `ErrorRegistry`
  is an exported map guarded by the unexported `errorRegistryMu`; any
  direct read or write by a consumer bypasses the lock. The README calls
  the registry helpers "safe for concurrent use", but the exported map
  is not.
- Evidence (`go test -race`, temporary tests, then removed):
  ```text
  TestAuditRaceSetMaxStackDepth: DATA RACE  error.go:65 (read MaxStackDepth) vs config.go:24 (write)
  TestAuditRaceSetIDGenerator:   DATA RACE  error.go:72 (read GenerateID)    vs idgen.go:162 (write)
  TestAuditRaceColors:           DATA RACE  colors.go:22 (read ColorsEnabled) vs colors.go:30 (write)
  TestAuditRaceExportedRegistryMap: DATA RACE registry.go:199 …
    fatal error: concurrent map read and map write
  ```
- Impact: adjusting configuration at runtime (or in parallel tests) races
  with error creation; a consumer writing `ErrorRegistry[...]` while any
  goroutine creates an error crashes the process with a fatal map error
  that `recover` cannot catch.
- Source: eduardo/go-concurrency-review §3, §5, references/mutex-and-atomics.md
  "Atomic operations" · JetBrains `atomic_types` · AGENTS.md §2.6
- Recommendation: back the setters with unexported `atomic.Int32`,
  `atomic.Bool` and `atomic.Pointer[func() string]`, and read through them
  inside the package. The exported variables cannot change type in v1:
  mark `MaxStackDepth`, `ColorsEnabled`, `GenerateID` and `ErrorRegistry`
  `Deprecated:` (pointing to the setters, `GetMetadata`/`RegisterMany` and
  `Factory`), document that writing them directly is unsafe, and keep
  the setters as the supported path.
- Breaking: no (deprecation only; changing the exported variables' types
  would be breaking) · Needs approval: yes (deprecating exported v1 API)

### C1-006 — `OverrideMetadata` runs the updater while holding the registry write lock: re-entry deadlocks the whole registry; results are not validated
- Area: C (Concurrency) · Severity: MEDIUM · Effort: S
- Location: errorkit/register.go:171-183 (global, updater call at 180), 187-201 (`Registry.OverrideMetadata`)
- Problem: the caller-supplied `updater` runs under
  `errorRegistryMu.Lock()`. Any errorkit call inside it that reads the
  registry (`GetMetadata`, `NewError`, a logger call that creates an
  `AppError`) blocks forever, and from then on every `NewError` in the
  process blocks on the same lock. The updated metadata is stored without
  `ValidateMetadata`, and the updater can change `Code` so that the key and
  `Metadata.Code` disagree.
- Evidence (temporary tests, then removed):
  ```text
  DEADLOCK: OverrideMetadata updater calling GetMetadata never returns   (2 s watchdog)
  ok=true stored.Code="ERR_SOMETHING_ELSE" stored.HTTPStatus=0
    ValidateMetadata=errorkit: invalid metadata: ERR_SOMETHING_ELSE invalid HTTP status 0
  ```
  (Running the deadlock test together with other tests hung the package
  test binary until it was killed.)
- Impact: a plausible use (deriving an override from another code's
  metadata) freezes all error creation process-wide; invalid metadata
  (HTTP status 0) can be installed and served.
- Source: eduardo/go-concurrency-review §3 "never call out … while holding
  one", references/mutex-and-atomics.md (no recursive locking) ·
  eduardo/go-defensive-coding §7
- Recommendation: copy the entry under the lock, release it, run the
  updater on the copy, validate (and reject a changed `Code`), then
  re-acquire the lock and store it if the entry is unchanged (or retry).
  Document that the updater must not call errorkit.
- Breaking: no · Needs approval: no

### C1-007 — Stack capture on every `NewError` costs ~31 µs and 67 allocations; the per-frame `runtime.Caller` loop is ~5× slower than `runtime.Callers`
- Area: F (Performance) · Severity: MEDIUM · Effort: S
- Location: errorkit/stack.go:12-44 (loop at 21-41, `runtime.Caller(i)` at 22, `runtime.FuncForPC` at 27), 47-64 (`filterStack` builds `fullName` per frame); errorkit/error.go:68-81
- Problem: `captureRawStackWithDepth` calls `runtime.Caller(i)` once per
  frame; each call walks the stack again from the top, so 32 frames do 32
  walks. `filterStack` then allocates a concatenated string per frame.
  Every `NewError` (including expected validation failures and the
  `ERR_INTERNAL` wrappers that `logger.Error` creates, see C1-008) pays
  this cost.
- Evidence (`-bench -benchmem -count=6`, called from 20 frames deep, temporary benchmarks, then removed):
  ```text
  BenchmarkAuditNewError-16           ~30.5–31.2 µs/op  11496 B/op  67 allocs/op
  BenchmarkAuditCaptureCallerLoop-16  ~19.5–20.5 µs/op   8504 B/op  54 allocs/op  (current captureRawStackWithDepth, depth 32)
  BenchmarkAuditCaptureCallers-16     ~3.5–3.7 µs/op     2032 B/op   3 allocs/op  (runtime.Callers + runtime.CallersFrames, same depth, same parseFuncName)
  BenchmarkAuditPlainError-16         ~87 ns/op            52 B/op   3 allocs/op  (fmt.Errorf %w, reference)
  ```
- Impact: error creation on hot or high-failure-rate paths (validation,
  retries, consumer redeliveries) is ~350× more expensive than a plain
  wrapped error, mostly due to the capture algorithm, not the feature.
- Source: eduardo/go-performance-review §1, §9 ("panic/recover … captures
  a stack trace" cost note), references/benchmarking.md
- Recommendation: capture with one `runtime.Callers(skip, pcs)` into a
  fixed array and resolve with `runtime.CallersFrames` (optionally resolve
  lazily, only when the trace is formatted or logged); filter on
  `Frame.Function` prefixes without building strings. Commit the
  benchmark with `b.ReportAllocs()`.
- Breaking: no (same `[]TraceContext` output) · Needs approval: no

### C1-008 — `logger.Error` / `Logger.Error` use a type assertion: an `*AppError` wrapped with `%w` is logged as a new generic `ERR_INTERNAL`
- Area: B (Idiomatic Go / correctness) · Severity: MEDIUM · Effort: S
- Location: logger/wrapper.go:27-43 (assertion 33, re-wrap 39); logger/instance.go:77-91 (assertion 82, re-wrap 87)
- Problem: both functions check `appErr.(*errorkit.AppError)`. When the
  `AppError` sits anywhere below the top of the chain (for example
  `fmt.Errorf("repo: %w", appErr)`), they build a new
  `NewError(ERR_INTERNAL)` around it, which is exactly the double-wrap that
  AGENTS.md §2.1/§4/§5 forbids. Building that wrapper also captures a full
  stack (C1-007) inside the logger, so the logged trace starts in the
  logger, not at the error's origin.
- Evidence (temporary test, then removed):
  ```text
  appErr := errorkit.NewError(errorkit.ERR_CLIENT_NOT_FOUND)
  l.Error(fmt.Errorf("repo: %w", appErr), "lookup failed")
  logged={"error_category":"system","error_code":"ERR_INTERNAL","error_group":"system",…,"http_status":500
  ```
- Impact: logs show the wrong code, HTTP status and retriability, which
  breaks alerting and dashboards keyed on `error_code`.
- Source: AGENTS.md §2.1, §4, §5 · eduardo/go-error-handling §3 and
  checklist item 5 · JetBrains `errors_as_type`
- Recommendation: use `errors.AsType[*errorkit.AppError](appErr)`
  (Go 1.26) and log the found `AppError`, attaching the outer message as
  `wrapped_error`/context. Also handle a nil `appErr` explicitly.
- Breaking: no · Needs approval: no

### C1-009 — `WithErrorKit` (and every `*Ctx` / `*WithTrace` logging helper) panics on a nil `*AppError`
- Area: B / D (robustness) · Severity: MEDIUM · Effort: S
- Location: logger/errorkit.go:21-31 (`appErr.ID` at 25); callers logger/wrapper.go:73-91, logger/otel.go:47-63, logger/instance.go:99-108
- Problem: `AppError`'s own methods are nil-safe (`Error`, `Code`, `With`,
  `Unwrap`, `Pretty`, `PrettyJSON` all check `e == nil`), but
  `WithErrorKit` dereferences fields directly. A typed-nil `*AppError`
  passed to `ErrorCtx`, `WarnCtx`, `LogErrorWithTrace`,
  `LogWarnWithTrace` or `Logger.ErrorCtx/WarnCtx` panics inside the
  logging call.
- Evidence (temporary test, then removed):
  ```text
  var appErr *errorkit.AppError
  l.ErrorCtx(context.Background(), appErr, "nil")
  PANIC: runtime error: invalid memory address or nil pointer dereference
  ```
- Impact: an error-handling path, typically inside a handler or recovery
  block, crashes the goroutine instead of logging.
- Source: eduardo/go-defensive-coding §1 and references/nil-and-aliasing.md
  "Nil receivers can be valid" (do it consistently or not at all)
- Recommendation: guard `appErr == nil` in `WithErrorKit` (emit
  `error_code=ERR_UNKNOWN` or skip the fields) and add a regression test.
- Breaking: no · Needs approval: no

### C1-010 — OTLP log provider: plaintext transport forced, setup and shutdown errors swallowed, README promises `WithBlock`
- Area: D (Security) / G (API) · Severity: MEDIUM · Effort: M
- Location: logger/logprovider.go:23-27 (`Shutdown`), 61-91 (64 `WithInsecure()`, 66-69 error → stderr + no-op provider, 71-78 resource, 88 global registration); logger/README.md:176
- Problem: `InitLogProvider` always uses `otlploggrpc.WithInsecure()`
  and offers no TLS, header (auth) or timeout option. It returns no
  error: failures print to stderr and return a no-op provider. The README
  says it "Uses `grpc.WithBlock()` so connection errors surface at
  startup"; the code has no blocking dial, and `otlploggrpc.New` connects
  lazily, so a wrong endpoint is never reported at startup. `Shutdown`
  returns nothing and prints errors to stderr. The resource is built only
  from `service.name` (no `resource.WithFromEnv`, so
  `OTEL_RESOURCE_ATTRIBUTES` is ignored). Calling `InitLogProvider` twice
  replaces the global provider without shutting down the first.
- Evidence: logprovider.go:62-69, 23-27 as quoted above; README.md:176
  versus the option list at logprovider.go:62-65.
- Impact: log records, which carry payloads, stack traces and anything
  C1-004 misses, can only be shipped in plaintext. Misconfiguration
  silently drops all exported logs, and callers cannot detect or handle
  either failure.
- Source: eduardo/go-security-audit §7 (TLS) · eduardo/go-observability §6
  "Graceful Shutdown of Telemetry" (shutdown with its own timeout, error
  handled) · eduardo/go-error-handling §5 · logger/README.md (DN-02)
- Recommendation: add `NewLogProvider(ctx, LogProviderConfig{Endpoint,
  Insecure, TLSConfig, Headers, Timeout}) (*LogProviderHandle, error)` and a
  `Shutdown`-variant that returns the error (for example
  `(*LogProviderHandle).Close(ctx) error`); keep `InitLogProvider` as a
  wrapper for compatibility; merge `resource.Default()`/`WithFromEnv`;
  fix the README claim.
- Breaking: no (additive) · Needs approval: no

### C1-011 — OTLP records get second-precision timestamps and lose large integer precision
- Area: B (Correctness) · Severity: MEDIUM · Effort: S
- Location: logger/config.go:310 (`TimeFieldFormat = TimeFormatUnix`); logger/otlp.go:50, 64-65 (`time.Unix(int64(ts), 0)`), 150-170 (`anyToLogValue`); logger/otlp.go:109 (map allocated per write)
- Problem: zerolog is configured to write whole Unix seconds, and
  `OTLPWriter.Write` converts that into the OTel record timestamp, so all
  records within one second get the same timestamp. `json.Unmarshal`
  without `UseNumber` turns every number into `float64`, so integer fields
  above 2^53 (snowflake IDs, nanosecond durations) lose precision in OTLP
  attributes.
- Evidence: `TestAuditTimestampPrecision` output
  `{"level":"info","message":"a","time":1793753281}`; otlp.go:64-65 as
  quoted above.
- Impact: log ordering and correlation with spans (which have nanosecond
  timestamps) are lost in the backend; numeric IDs in attributes can be
  wrong.
- Source: eduardo/go-observability §4 "Connecting Logs, Traces, and
  Metrics" · eduardo/go-defensive-coding §5 (silent numeric conversion)
- Recommendation: use `zerolog.TimeFormatUnixMicro`/`UnixNano` (or
  RFC3339Nano) set on the logger instance, parse it accordingly in
  `OTLPWriter`, decode with `UseNumber`, and map integers to
  `Int64Value`. Better, emit OTel records directly from a zerolog hook
  instead of re-parsing JSON (also helps C1-003).
- Breaking: no (the `time` field value format changes in JSON output) ·
  Needs approval: no

### C1-012 — `DetectEnv`: insecure default (Dev, Debug level), case-sensitive match, wrong doc comment, env re-read on every Dev log line, implicit read inside `New`
- Area: D (Security) / B · Severity: MEDIUM · Effort: S
- Location: logger/config.go:31-39 (doc says `APP_ENV`, reads `ENVIRONMENT`), 44-62 (`os.Getenv("ENVIRONMENT")` inside `FormatExtra` at 57), logger/instance.go:44-47, logger/logger.go:45
- Problem: an unset or mistyped `ENVIRONMENT` (for example `PRODUCTION`,
  `Production`, `prd`) selects `Dev`: Debug level and the ANSI console
  writer on stdout. The doc comment names the wrong variable. The Dev
  console writer reads `ENVIRONMENT` on every log line and uses an
  undocumented value `local`. `New(Config{})` reads the environment
  implicitly, against AGENTS.md §2.4 ("No package reads environment
  variables silently"), although the `Config.Env` comment does mention it.
- Evidence (temporary test, then removed):
  ```text
  DetectEnv() with ENVIRONMENT unset = "development"
  DetectEnv() with ENVIRONMENT=PRODUCTION = "development"
  ```
- Impact: a production deployment that forgets or capitalizes the
  variable logs at Debug level with non-JSON output that log pipelines
  cannot parse, increasing data exposure and breaking ingestion.
- Source: AGENTS.md §2.4 · logger/README.md "Environment Detection" ·
  eduardo/go-security-audit (secure defaults) · eduardo/go-observability

### C1-019 — ULID generator: monotonicity not guaranteed under contention, decoder not case-insensitive as documented, dead fallback RNG
- Area: B / D · Severity: LOW · Effort: S
- Location: errorkit/idgen.go:18-19 (doc), 44-77 (`now` read at 46 before `Lock` at 48; `time.Sleep` under the lock at 58), 143-152 (LCG fallback), 174-216 (`ParseULID` accepts upper case only), 219-257
- Problem: the timestamp is taken before acquiring the mutex, so a
  goroutine that waited on the lock can store an older timestamp after a
  newer one (`now < lastTimestamp` takes the "new millisecond" branch with
  fresh randomness), breaking the documented "monotonically increasing"
  property and moving `lastTimestamp` backwards. The comment says the
  encoding is case-insensitive, but `ParseULID`/`ValidateULID` reject
  lower case. `crypto/rand.Read` does not return an error since Go 1.24,
  so the time-seeded LCG fallback is dead code (and would be predictable
  if reached).
- Evidence: code references above (logic; uniqueness is not affected
  because 80 random bits are drawn per new timestamp).
- Impact: IDs created concurrently in the same millisecond are not
  guaranteed to sort in creation order; lower-case ULIDs from other
  systems are rejected.
- Source: eduardo/go-concurrency-review §3 (state read outside the
  critical section) · eduardo/go-security-audit §6 (`crypto/rand`)
- Recommendation: read the clock inside the lock and use
  `max(now, lastTimestamp)`; accept lower case in the decoder (or fix the
  comment); remove the LCG fallback.
- Breaking: no · Needs approval: no

## Strengths

- `AppError` methods (`Error`, `Code`, `Unwrap`, `With`, `Pretty`,
  `PrettyJSON`, `WriteTo`) are nil-safe, and `Unwrap` keeps the chain
  walkable for `errors.Is/As` (errorkit/error.go:90-134).
- `WithReason` is recognized by `go vet`'s printf analyzer: a temporary
  test calling `WithReason(nonConstant)` failed to build with
  `non-constant format string in call to …WithReason`, so format-string
  misuse is caught at test time.
- Registry validation (`ValidateMetadata`) with wrapped sentinel errors
  (`ErrInvalidMetadata`, `ErrMetadataConflict`) that support
  `errors.Is`; idempotent re-registration of identical metadata;
  `MustRegister` documented as a deliberate `Must*` panic.
- Explicit, mutation-free alternatives already exist and are well
  isolated: `Registry`, `NewDefaultRegistry`, `Factory`,
  `NewStackFormatterWithConfig`, `telemetry.Instrumenter` (with nil-safe
  fallback, trace.go:143-148), `logger.New` (apart from C1-001).
  `Registry` uses its own `sync.RWMutex`, and `Merge` snapshots the source
  under its read lock before writing to the target (no lock-order
  deadlock).
- Error IDs come from `crypto/rand`, not `math/rand`.
- `WithTrace` takes `trace_id`/`span_id` from the live span and
  `WithErrorKit` deliberately does not overwrite them; `OTLPWriter`
  rebuilds a `SpanContext` so the backend gets first-class trace
  correlation.
- `SetupOTLP` packages the provider-then-writer order, and the canonical
  bootstrap defers shutdowns at `main` scope in the right (LIFO) order.
- Span naming helpers are small, consistent and covered by a table test
  against an in-memory exporter.
- `go vet` is clean for all three packages; the only staticcheck errors
  are the pre-existing SA1019 (C1-024).

## Open questions

1. `NewOTLPWriter` binds to `otelglobal.GetLoggerProvider()` at
   construction. In `otel v1.47.0` the deprecated `log/global` package
   forwards to `otel`; whether a writer created *before* `InitLogProvider`
   is upgraded through the global delegate was not verified (needs a test
   with an SDK provider and a fake exporter). If it is not, the "wrong
   order" case silently drops all OTLP logs.
2. `AppError.With` mutates the receiver in place. If consumers keep a
   package-level `*AppError` as a sentinel and call `With` on it from
   several goroutines, that is a data race and the stack/ID are stale. No
   such use exists in this repository (`grep` found no package-level
   `errorkit.NewError` value), so this is not a finding; a doc note may be
   enough.
3. `AppError.Error()` omits the wrapped cause, so `err.Error()` and
   `%v` lose it unless the formatter is used. This looks intentional
   ("prevents duplicate output with structured loggers"); confirm with the
   maintainers that this is the intended behaviour.
4. Span names built from caller input (`External(ctx, system, op)`,
   `DB(…)`) can have unbounded cardinality if consumers pass IDs. No such
   call was found in the SDK; consumer usage is unknown.
5. The project skill `.skillshare/skills/go-design-principles/SKILL.md`
   (appendix, lines 317, 402, 447) recommends `errorkit.WithMessage` and
   `errorkit.ErrorTypeValidation`, which do not exist (the API has
   `WithReason`, `ErrorTypeInternal`, `ErrorTypeExternal`). The skill is
   installed outside the module (gitignored), so this is forwarded to P2.X2
   rather than reported as a package finding.
6. `logger.Panic` exits with `os.Exit(1)` without flushing the OTLP batch
   processor; records logged right before the exit (including the fatal
   one) are likely lost unless the caller shuts the provider down first.
   Not reproduced (needs a collector or fake exporter).
