### C2-001 — A Hertz `Run()` bind failure panics the whole process; `Run()` can never return an error
- Area: C (Concurrency / lifecycle) · Severity: HIGH · Effort: M
- Location: `httpserver/hertz/wrapper.go:58-61`; Hertz `pkg/app/server/hertz.go:56-79,90-113`, `pkg/network/netpoll/transport.go:100`
- Problem: `Run()` calls `engine.Spin()` and always returns `nil`. `Spin` runs `engine.Run()` in its own goroutine. When the listen fails (port in use, permission denied), the netpoll transport **panics** in that goroutine. No caller can recover from that panic. The `HTTPServer.Run` contract says "Returns error if server fails to start" (`httpserver/contracts.go:169-171`). `Spin` also installs `signal.Notify` for SIGINT/SIGHUP/SIGTERM and never stops it. On a signal it runs its own `Shutdown(context.Background())`, so the library takes over the process's signal handling.
- Evidence: test that occupies a port with `net.Listen` and then calls `New(cfg).Run()` on the same port:
  ```text
  panic: create netpoll listener fail: listen tcp 127.0.0.1:34259: bind: address already in use
  goroutine 15 [running]:
  github.com/cloudwego/hertz/pkg/network/netpoll.(*transporter).ListenAndServe(...) transport.go:100
  github.com/cloudwego/hertz/pkg/route.(*Engine).Run(...) engine.go:384
  github.com/cloudwego/hertz/pkg/app/server.(*Hertz).Spin.func1() hertz.go:60
  FAIL github.com/trypanic/go-sdk/httpserver/hertz 0.013s
  ```
- Impact: A deploy or config mistake (two replicas on one host, a port already taken) crashes the service. Deferred cleanups and SDK structured logging never run. Callers cannot implement "retry bind", "fail readiness" or "log and exit cleanly". Consumers that use `signal.NotifyContext` themselves get two competing shutdown paths.
- Source: eduardo/go-api-design §6 (serve error returned via `errc`, exit only from `main`) · eduardo/go-concurrency-review §1 ("start goroutines in the owner, not the callee"), Red flags ("goroutine started without shutdown path") · httpserver/contracts.go:169-171
- Recommendation: Do not use `Spin`. Call `engine.Run()` directly, which returns its error to the caller without signal handling. If netpoll still panics on bind, pre-bind with `net.Listen` (Hertz `server.WithListener`) so the error surfaces as an `*errorkit.AppError`. Leave signal handling to the caller, as the README's own Quick Start already does.
- Breaking: no (signature unchanged) · Needs approval: yes (consumers that rely on Hertz's built-in SIGTERM handling would have to add their own)

### C2-002 — The retry loop ignores HTTP method idempotency: non-idempotent POSTs, including billable LLM calls, are re-sent up to 5 times
- Area: B (Idiomatic Go / correctness) · Severity: HIGH · Effort: M
- Location: `httprequest/httprequest.go:181-223` (decision at 211), `309-317`; `httprequest/errors_codes.go` and `httpclient/errors_codes.go` (`Retriable: true` for 5xx, 429, network error, network timeout); `llmclient/client.go:124-133`
- Problem: Whether to retry depends only on `Metadata.Retriable`. The method and whether the request may already have been processed are never considered. A POST that times out after the server received it (`ResponseHeaderTimeout`, `http.Client.Timeout`, context deadline) or that gets a 500/502/503 is sent again. The default is 5 attempts. `llmclient` always POSTs, and `llmclient.New` accepts any requester, including the default `httprequest.New` with 5 attempts.
- Evidence: throw-away test against `httptest` servers:
  ```text
  POST hits=5 err=[ERR_EXTERNAL_SERVICE_ERROR] External service error (500)
  POST (server processed each) hits=5 err=[ERR_NETWORK_TIMEOUT] Request deadline exceeded
  ```
  In the second case the handler ran to completion 5 times. The client gave up on each attempt after `ResponseHeaderTimeout = 50ms`.
- Impact: Duplicate side effects such as double charges, duplicate orders or duplicate messages. For LLM calls it means up to 5 billed completions for one `Execute`. Both the default `httprequest.New` and `httpclient.SetupForLLM` (whose `ResponseHeaderTimeout` is 4 min) are affected.
- Source: eduardo/go-api-design §9 (idempotency keys, "Clients and proxies retry; without this, a retry is a double charge") · AGENTS.md §2.1 ("Retryability is data-driven") — see Needs approval
- Recommendation: By default, retry only idempotent methods (GET, HEAD, OPTIONS, PUT, DELETE), or requests that carry an `Idempotency-Key` header. Retry a non-idempotent request only on errors that prove the request was never sent: dial errors, and a connection refused before any write. Add an explicit opt-in such as `RetryConfig.RetryNonIdempotent` or a per-request flag. Document in `llmclient` that its requester should use `MaxRetries: 1`, or have it set an idempotency key.
- Breaking: no (no signature change) · Needs approval: yes (consumer-visible behavior change; the README states that retryability "is determined entirely by `Metadata.Retriable`", and AGENTS §2.1 frames retry as data-driven)

### C2-003 — A negative `MaxRetries` makes `Do` return `nil` without sending any request
- Area: B (Idiomatic Go / correctness) · Severity: HIGH · Effort: S
- Location: `httprequest/httprequest.go:117-128` (only `== 0` is normalized), `187` (`for attempt := 0; attempt < rc.MaxRetries; …`), `222` (`return lastErr`, which is `nil`)
- Problem: `normalizeRetryConfig` replaces only zero values. With `MaxRetries < 0` the loop never runs, and `Do` returns `lastErr == nil`. The caller sees success, but no request was sent and `out` was never filled. Writing `-1` to mean "no retries" is a plausible mistake, because the README calls the field "Total number of attempts".
- Evidence:
  ```text
  MaxRetries=-1: hits=0 err=<nil> out=map[]
  ```
- Impact: Silent data loss. A write such as a payment, a notification or an upstream sync is reported as successful although it never left the process.
- Source: eduardo/go-defensive-coding §7 (zero-value and initialization safety; validate in constructors) · eduardo/go-error-handling §1
- Recommendation: Clamp `MaxRetries < 1` to 1 in `normalizeRetryConfig`, or return an error. Make the final `return lastErr` unreachable, or guard it. Add a regression test for 0, -1 and 1.
- Breaking: no · Needs approval: no

### C2-004 — Response decoding panics for named string or bool types and for typed-nil `out` pointers
- Area: B (Idiomatic Go / defensive coding) · Severity: HIGH · Effort: S
- Location: `httprequest/decode.go:15-49` (dispatch on `Kind()`), `57` (`out.(*string)`), `124` (`out.(*bool)`), `23` (`outValue.Elem().Type()` on a nil pointer)
- Problem: `processResponse` dispatches on `reflect.Kind`. The string and bool decoders then use an unchecked type assertion to `*string` or `*bool`. A pointer to a named type such as `type Status string` or `type Flag bool` has kind `String` or `Bool`, so the assertion panics. A typed-nil pointer such as `(*Foo)(nil)` passes the `out != nil` check and panics in `Elem().Type()`. The int, uint and float paths use `reflect.Value.Set*` and do not have this bug.
- Evidence:
  ```text
  named bool: PANIC: interface conversion: interface {} is *httprequest.namedBool, not *bool
  named string: PANIC: interface conversion: interface {} is *httprequest.namedString, not *string
  ```
- Impact: An ordinary caller type crashes the goroutine. Outside an HTTP handler with recovery, it crashes the process. Callers should receive `ERR_SYSTEM_UNEXPECTED`.
- Source: eduardo/go-defensive-coding references/nil-and-aliasing.md ("Comma-ok on every dynamic lookup") · eduardo/go-error-handling §7 (panic is not error handling)
- Recommendation: Use `outValue.Elem().SetString` / `SetBool` / `SetBytes`, matching the numeric paths. Check `outValue.IsNil()` and return `ERR_SYSTEM_UNEXPECTED`. Add a test for each kind, including named types.
- Breaking: no · Needs approval: no

### C2-005 — The inbound audit middleware is on by default but logs nothing, and it still copies every request body and both header sets
- Area: D (Security) · Severity: HIGH · Effort: S
- Location: `httpserver/hertz/server.go:152-205`, installed at `57-59`; `httpserver/options.go:31-49` (`EnableAudit: true` by default); `httpserver/README.md` §"Body redaction" ("The inbound audit middleware passes every captured request/response body through `Audit.BodyRedactor` before logging"); AGENTS.md §2.5
- Problem: The logging block is commented out (`server.go:158-161,176-177,186-203`). `redact` is assigned but never used; this is the ineffassign at `:155` in baseline V9. `Audit.CaptureBodies` is ignored. On every request the middleware still copies the full request body (up to Hertz's 4 MiB default) and builds two header maps, and then throws them away.
- Evidence: test with `EnableAudit=true`, `CaptureBodies=true`, `BodyRedactor=RawBodyRedactor`, sending a POST through `ut.PerformRequest`, with the global zerolog redirected to a buffer:
  ```text
  EnableAudit=true CaptureBodies=true Raw: status=200, bytes logged by global zerolog=0
  ```
- Impact: Services that rely on the documented default inbound audit trail have none. That is a repudiation gap for auth and admin actions. Every request also pays an allocation and copy cost for nothing.
- Source: eduardo/go-security-audit references/threat-model.md (STRIDE "Repudiation": audit log for auth and admin actions) · eduardo/go-performance-review §1 · AGENTS.md §2.5 · httpserver/README.md "Body redaction"
- Recommendation: Either restore the logging (redacted by default, through `logger.CtxOrGlobal(ctx)` with trace correlation, honoring `CaptureBodies`), or remove the copies and document that inbound audit is not implemented. Add a test that asserts the log line and the redaction.
- Breaking: no · Needs approval: yes (restoring adds one log line per request for every consumer that keeps the default; removing changes the documented contract)

### C2-006 — URL credentials, query-string secrets and upstream error messages bypass redaction into error payloads, the global error log, audit logs and span events
- Area: D (Security) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httperror.go:31` (`url` in network-error payload), `:30-36` (`original_error` = `url.Error` text), `:80,84` (`res.Request.URL.String()`), `:91-99` (`provider_error_message` copied from the response body without redaction), `:156` (`logger.Error(appErr)`); `httprequest/audit.go:54`; `httprequest/httprequest.go:198` (span event `http.url`)
- Problem: Redaction covers bodies and some headers only. The full URL, including userinfo (`user:pass@`) and query parameters such as `?key=` (Google APIs) or `?token=`, is placed verbatim into the error payload, the audit log and span events. `res.Request.URL.String()` does not strip passwords; `url.URL.Redacted()` would. The upstream error message is extracted from the response body and logged at error level even when body capture is off. Providers often echo input there, and OpenAI echoes a partial API key.
- Evidence: 401 response to `http://user:p4ssw0rd@127.0.0.1:…/v1?key=SECRET123`, with no `WithBodyCapture` and no audit log. The library itself logged:
  ```text
  {"level":"error","error_code":"ERR_AUTH_UNAUTHENTICATED",…,"payload":{"provider_error_code":"invalid_api_key",
   "provider_error_message":"Incorrect API key provided: sk-live-ABCDEF","status_code":401,
   "url":"http://user:p4ssw0rd@127.0.0.1:45847/v1?key=SECRET123"},…}
  ```
- Impact: Credentials end up in log storage, third-party log sinks and traces. Retention and access controls there are weaker than for secret stores.
- Source: eduardo/go-security-audit §5, §8 ("NEVER log secrets, tokens, or passwords") · eduardo/go-observability §1 "Sensitive data — NEVER log" · AGENTS.md §2.5 (redact by default)
- Recommendation: Sanitize URLs before any payload, log or span: `u.Redacted()`, then drop or mask the query string, or allowlist its keys. Put `provider_error_message` behind `captureBodies` and the redactor, and keep `provider_error_code` and `type`, which are low-cardinality and safe. See C2-009 for the logging call itself.
- Breaking: no · Needs approval: yes (payload keys and values that consumers may read change)

### C2-007 — Response bodies are read without a size limit (error bodies, decoders, transparent gzip)
- Area: D (Security / resource exhaustion) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httprequest.go:253` (`io.ReadAll(res.Body)` on non-2xx), `:262-263`; `httprequest/decode.go:53,63,80,97,114,130,140` (`io.ReadAll` / unbounded `json.Decoder`); `httpclient/httpclient.go:246-252` (`DisableCompression: false`, so gzip is decompressed transparently)
- Problem: Nothing caps how much of a response is read. A misbehaving, compromised or attacker-chosen upstream (SSRF, or user-configured webhook and LLM endpoints) can return a body as large as the transport will deliver, and gzip multiplies that. The error path buffers the whole body only to extract `error.code` and `error.message`.
- Evidence: 500 response with a 64 MiB body, `MaxRetries: 1`:
  ```text
  500 with 64 MiB body: TotalAlloc delta = 159 MiB
  ```
  With the default 5 attempts, that cost is paid 5 times per `Do`.
- Impact: Memory exhaustion or OOM kill of the calling service, triggered by an upstream.
- Source: eduardo/go-security-audit §1 ("an unbounded decoder is a memory exhaustion vector"), references/injection.md (decompression bombs: `io.LimitReader`) · eduardo/go-performance-review §7, §9 ("`io.ReadAll` on request or response bodies → stream with a decoder and a size cap")
- Recommendation: Wrap `res.Body` in `io.LimitReader`, for example 64 KiB for error bodies and a configurable `MaxResponseBytes` option with a generous default for success bodies. Return a specific error such as `ERR_EXTERNAL_INVALID_RESPONSE` when the limit is exceeded. Drain the remainder with a bounded copy so the connection can be reused.
- Breaking: no (new option) · Needs approval: yes (a default cap is a visible behavior change for very large responses)

### C2-008 — Every successful decoded response is buffered a second time, even when the audit log is off
- Area: F (Performance) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httprequest.go:260-268`
- Problem: `respBuf` and `io.TeeReader` are created whenever `out != nil`, but `respBuf` is only used when `h.auditLog` is true. That flag is off by default, and in that case the audit line only prints `[REDACTED]` anyway. The whole body is therefore copied into a growing `bytes.Buffer` on every call.
- Evidence: 8 MiB JSON body, `NewWithoutTracing` (audit off):
  ```text
  8 MiB JSON body, audit off: TotalAlloc delta = 80 MiB
  baseline decode without TeeReader: TotalAlloc delta = 48 MiB
  ```
  That is about 67% more allocation on the hot success path.
- Impact: Higher GC pressure and peak memory for every consumer, scaling with response size. LLM responses and list endpoints are the typical large cases.
- Source: eduardo/go-performance-review §1, §7 ("stream instead of buffering") · references/memory-and-io.md
- Recommendation: Use the tee only when `h.auditLog` is true and the redactor is not `DefaultBodyRedactor`. The default redactor ignores content, so it only needs to know whether the body was empty.
- Breaking: no · Needs approval: no

### C2-009 — `httprequest` logs every non-2xx response through the global logger and also returns the error (log-and-return, once per attempt)
- Area: B (Idiomatic Go / error handling) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httperror.go:156` (DN-09); its return value is also unchecked (baseline V9 errcheck)
- Problem: `buildHTTPError` calls `logger.Error(appErr)` and then returns the same error. It uses the global logger, not `logger.CtxOrGlobal(ctx)`, so there is no `trace_id` or `span_id` and no request-scoped fields. Because it runs inside the retry loop, one `Do` against a failing upstream logs up to 5 error lines before the caller logs the final error again. Expected outcomes such as 404 or 401 are logged at error level from inside a library.
- Evidence: code at `httperror.go:156`; the log line quoted in C2-006 was emitted by this call during a plain `Do`.
- Impact: Duplicate, uncorrelated error logs; noise that hides real incidents; extra log volume and cost; and the leak described in C2-006 reaches the logs even when the caller handles the error.
- Source: eduardo/go-error-handling §5 ("Handle errors exactly once") · eduardo/go-observability §1 ("NEVER log at Error level for expected conditions") · AGENTS.md §2.3 (use `CtxOrGlobal(ctx)`)
- Recommendation: Remove the log call and let the caller decide. If the logging is kept, make it opt-in through an option, log once after the final attempt, use `logger.CtxOrGlobal(ctx)` with trace correlation, and use the warn level for 4xx.
- Breaking: no · Needs approval: yes (consumers that rely on the library's own error lines would lose them)

### C2-010 — Hertz `Shutdown(ctx)` is silently capped at 5 s and returns `nil` while requests are still in flight
- Area: C (Concurrency / lifecycle) · Severity: MEDIUM · Effort: S
- Location: `httpserver/hertz/wrapper.go:65-67`; Hertz `pkg/route/engine.go:307-352` (`context.WithTimeout(ctx, opt.ExitWaitTimeout)`), default `ExitWaitTimeout = 5s` (`pkg/common/config/option.go:41`); `httpserver.ServerConfig` has no field to change it
- Problem: The contract says "The supplied context bounds how long Shutdown waits for in-flight requests" (`contracts.go:173-176`). Hertz caps the caller's context at `ExitWaitTimeout` (5 s), and the adapter offers no way to raise that. `Shutdown` then returns `nil`, so the caller believes the drain is complete.
- Evidence: one in-flight request of 8 s, then `Shutdown` with a 30 s context:
  ```text
  HERTZ: Begin graceful shutdown, wait at most 5s ...
  Shutdown(ctx 30s) returned after 5s err=<nil>
  in-flight 8s request result: 200 OK (at 7.7s)
  ```
- Impact: Callers close the database pool, broker and OTLP exporters (the AGENTS §3 order) while handlers are still running. Those handlers then fail midway, and the last spans and logs can be lost.
- Source: eduardo/go-api-design §6 (graceful shutdown bounded by the caller's deadline) · eduardo/go-context §3 (timeout budgets) · httpserver/contracts.go:173-176
- Recommendation: Set `server.WithExitWaitTime` to a large value and let the caller's context be the bound. Alternatively, derive it from the context deadline, or add `ServerConfig.ShutdownTimeout`. Report a timeout as `ERR_SYSTEM_TIMEOUT_INTERNAL`, as `grpc.Server.Shutdown` does.
- Breaking: no · Needs approval: no

### C2-011 — `EnableRecovery=false` cannot disable recovery; with `true`, two recovery layers run and Hertz logs panics through its own logger
- Area: D (Security / operability) · Severity: MEDIUM · Effort: S
- Location: `httpserver/hertz/server.go:48,51` (`server.Default` always adds `recovery.Recovery()`; Hertz `pkg/app/server/hertz.go:48-53`), `:54-56`, `:103-109` (DN-16)
- Problem: The outermost recovery is always Hertz's default handler. It logs `err=%v` and the full stack trace through `hlog` as unstructured stderr text, which bypasses the SDK logger, its redaction and trace correlation. The switch documented in `ServerOptions` therefore has no effect. With recovery enabled, the SDK's `RecoveryHandler` runs inside it, so a panic in SDK middleware placed before it (tracing) is handled only by Hertz's handler. `RecoveryHandler` also ignores its `stack` argument.
- Evidence: `EnableRecovery=false`, handler panics with `"boom secret=xyz"`:
  ```text
  [Error] HERTZ: [Recovery] err=boom secret=xyz
  stack=/home/…/httpserver/hertz/zz_audit_c2_test.go:87 (0xc8b404) …
  EnableRecovery=false, panicking handler -> status 500 (no crash)
  ```
- Impact: Panic values, which can contain request data or secrets, and source paths go to an unmanaged sink. The documented option is misleading.
- Source: eduardo/go-api-design §2 (one recoverer, outermost) · eduardo/go-security-audit §8 · AGENTS.md §2.3
- Recommendation: Build the engine with `server.New`, install the SDK recovery as the outermost middleware when `EnableRecovery` is true, and include the panic stack in the structured log.
- Breaking: no · Needs approval: yes (with `EnableRecovery=false`, a panic would then crash the process, which is what the option promises)

### C2-012 — No end-to-end bound on the LLM path, and per-attempt budgets multiply on the default path
- Area: C (Concurrency / timeouts) · Severity: MEDIUM · Effort: S
- Location: `httpclient/httpclient.go:91-107` (`SetupForLLM`: `Timeout: 0`, `ResponseHeaderTimeout: 4m`), `:62` (`DialTimeout: 60s`), `:263`; `llmclient/client.go:103-107` (`Timeout` is optional, and 0 means no deadline); `httprequest/httprequest.go:187-221`
- Problem:
  - On the LLM path, `SetupForLLM` disables the client timeout and `llmclient.Config.Timeout` defaults to 0. If the caller's context has no deadline, nothing bounds reading the response body once headers have arrived. A stalled upstream holds the goroutine and the connection indefinitely. `ResponseHeaderTimeout` covers only the time to the first header byte.
  - On the default path, `http.Client.Timeout` (60 s) applies per attempt, and timeouts are retriable. One `Do` without a context deadline can therefore take about 5 × 60 s plus backoff, roughly 5 minutes.
  - The default `DialTimeout` of 60 s is far above what is typical for service-to-service calls.
- Evidence: code as cited. The `llmclient` README says "0 = no client-side deadline". `TestExecuteNoDeadlineWhenTimeoutZero` (`llmclient/client_test.go:77`) pins this behavior.
- Impact: Goroutine and connection exhaustion under upstream stalls, and request latencies far beyond any inbound handler budget.
- Source: eduardo/go-context §3 (timeout budgets; child calls spend the parent budget) · eduardo/go-performance-review §7 ("One `http.Client` … with a `Timeout`")
- Recommendation: Give `llmclient` a non-zero default timeout, or require one. Add an overall `Do` budget, for example `RetryConfig.MaxElapsed`, or document that the context deadline covers all attempts. Lower the default `DialTimeout` to around 5–10 s. Fix the stale `SetupForLLM` doc comment (see C2-027).
- Breaking: no · Needs approval: yes (changing defaults is visible to consumers)

### C2-013 — Non-transient failures are classified as retriable network errors (redirect-limit violations, invalid URL or scheme)
- Area: B (Idiomatic Go / error classification) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httperror.go:68-74` (every non-timeout transport error becomes `ERR_NETWORK_ERROR`, `Retriable: true`); `httprequest/httprequest.go:309-317` (`errors.As` finds the outer error first); `httpclient/httpclient.go:269-276` (redirect-limit error is `ERR_EXTERNAL_SERVICE_ERROR`, `Retriable: true`)
- Problem: `buildNetworkError` wraps everything returned by `client.Do` as `ERR_NETWORK_ERROR`. That includes the `CheckRedirect` limit error, "unsupported protocol scheme" from an empty or misconfigured URL, and TLS certificate verification failures. `isRetryable` reads the outermost `AppError`, so the more specific inner classification is lost, and permanent errors are retried with backoff.
- Evidence:
  ```text
  redirect loop: server hits=10 code=ERR_NETWORK_ERROR retriable=true      (MaxRedirects=2 → 5 attempts × 2 hits)
  empty endpoint: attempts=5 elapsed=1.503s err=[ERR_NETWORK_ERROR] Network communication error   (llmclient, Endpoint "")
  ```
- Impact: Wasted latency and upstream load. A configuration error looks like a flaky network in dashboards and alerts.
- Source: eduardo/go-error-handling §3, §9 (the type that carries the cause must be detectable) · AGENTS.md §2.1 ("Wrap, do not re-encode")
- Recommendation: Preserve an inner `*errorkit.AppError` from `CheckRedirect` instead of re-encoding it. Classify `x509` and TLS errors, invalid URLs and unsupported schemes as non-retriable, for example `ERR_SYSTEM_CONFIG_INVALID` or `ERR_EXTERNAL_INVALID_RESPONSE`. Validate `RequestConfig.URL` once, before the loop.
- Breaking: no · Needs approval: yes (error codes returned for these cases change)

### C2-014 — Backoff has no jitter and ignores `Retry-After` on 429 and 503
- Area: F (Performance / resilience) · Severity: MEDIUM · Effort: S
- Location: `httprequest/httprequest.go:215-232`, `321-328`; `httprequest/httperror.go:119-125`
- Problem: Delays are deterministic: 100, 200, 400 and 800 ms. A rate-limited upstream, including LLM providers that send `Retry-After`, is hit again on a fixed schedule, and every client instance retries in lockstep.
- Evidence: `nextDelay` doubles a fixed value with no randomness. `buildHTTPError` never reads `res.Header.Get("Retry-After")`.
- Impact: Thundering herd after an upstream incident, extended 429 storms, and retries that fail by design because they fire before the advertised window.
- Source: eduardo/go-performance-review §7 · eduardo/go-api-design §9 (clients retry) · algorithms package (exponential backoff with randomization already exists in the SDK)
- Recommendation: Add full jitter. Parse `Retry-After` (seconds or HTTP-date), honor it up to `MaxDelay`, and stop retrying if it exceeds the context budget. Optionally reuse `algorithms.NewExponentialBackoff`.
- Breaking: no · Needs approval: no

## Strengths (keep)

- **`httpclient`:**
  - A single factory with sane pool sizes (`MaxIdleConnsPerHost: 50` instead of Go's default of 2), `ResponseHeaderTimeout`, `ProxyFromEnvironment`, `ForceAttemptHTTP2`, and a TLS 1.3 minimum by default.
  - An explicit redirect policy, and `InsecureSkipVerify` only as an opt-in.
  - The `TransportWrapper` seam keeps OTel out of the baseline build.
- **Retries resend the body safely:** `buildRequest` builds a fresh `bytes.NewReader` per attempt, and `http.NewRequestWithContext` sets `GetBody`, so 307/308 redirects and retries resend the body correctly.
- **Context handling:** the context is checked before every attempt, the backoff wait selects on `ctx.Done()`, and W3C trace context is injected into outbound headers.
- **Connection reuse works (verified empirically).** 10 sequential requests used 1 TCP connection for each of: JSON-decoded output, `out == nil`, and string output. With an unread 256 KiB body and `out == nil`, they used 2 connections. The suspected "close before EOF prevents reuse" issue does not reproduce on go1.26.2.
- **Concurrency safety:** `HTTPRequest` is immutable after construction and `Do` works on a local copy of the retry configuration (confirmed by the race-clean baseline V5 and `TestDoIsConcurrentSafe`).
- **Body redaction is the default** for outbound error payloads and audit lines (`DefaultBodyRedactor`), and `WithRawBodies` must be chosen explicitly. Request headers in the outbound audit are sanitized.
- **Error classification:** `insufficient_quota` 429 responses are correctly forced non-retriable. The status→`errorkit` mapping is broad and documented.
- **`httpserver` core** has no framework imports, and `BuildReply` is pure with an injectable clock and layout.
- **`llmclient`:** small surface, immutable `Config`, the API key sent only in the `Authorization` header (redacted by the outbound audit), a timeout applied through the context, and the triplet constructors in place.

## Open questions (not proven)

1. Hertz builds route parameter values for catch-all segments with `bytesconv.B2s` (zero-copy, `pkg/route/tree.go:441`), and `HTTPContext.GetBody()` (`httpserver/hertz/context.go:39`) returns the Hertz-owned request buffer. Do strings or slices kept beyond the handler (in goroutines or caches) change when Hertz reuses the `RequestContext`? The README forbids keeping `HTTPContext`, but says nothing about the values it returns. No reproducing test was written.
2. When `Spin`'s signal path is taken, the goroutine that sends `h.Run()`'s result on the unbuffered `errCh` may block forever (Hertz `hertz.go:57-61`). After the SDK caller's own `Shutdown`, `Spin` may also call `Engine.Close()` while a graceful drain is in progress. Neither was observed in the C2-010 test (the in-flight request completed), but neither was exhaustively tested.
3. Hertz's default `ReadTimeout` (3 min), `IdleTimeout` and `MaxRequestBodySize` (4 MiB) cannot be configured through `httpserver.ServerConfig`. Slowloris resistance under netpoll was not measured.
4. The TLS 1.3-only default (`httpclient.go:235`) is a deliberate, documented choice, but it rejects TLS 1.2-only upstreams, which are still common in enterprise and partner APIs. Should the floor be TLS 1.2, with 1.3 as an opt-in? This needs a product decision, not a defect fix.
5. `ServerOptions` boolean fields cannot be backfilled (DN-18, owned by P2.X2). A partial `ServerOptions{EnableTracing: true}` silently disables recovery, audit, the NoRoute/NoMethod handlers and health. A constructor that starts from `DefaultServerOptions()` may be safer; this is left to P2.X1/P2.X2.
6. Should `llmclient` enforce single-attempt semantics itself, for example by wrapping the injected requester or setting an idempotency header, rather than relying on how the consumer builds the requester? This depends on the outcome of C2-002.
