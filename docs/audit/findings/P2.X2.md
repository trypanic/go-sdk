### X2-001 — No CI runs on push or pull request; the repo's own gates are already red and nothing notices
- Area: H (Maintainability & DevEx) · Severity: HIGH · Effort: M
- Location: `.github/workflows/release.yml:15-17` (the only workflow; trigger `push: branches: [main]`)
- Problem: Nothing runs build, vet, tests, race, lint, staticcheck, semgrep, `govulncheck` or `gorelease` on a PR or a non-release push. Every gate is a local honor-system step (pre-commit, `task check`). The first workflow job that executes `go test` is `assets`, which only runs after a release was created (see X2-004).
- Evidence:
  - `git ls-files .github` → `release.yml` plus `.gitkeep` files only.
  - Baseline on the untouched tree: V7 `task staticanalysis` FAIL (4× SA1019 in `logger`), V8 govulncheck FAIL on go1.26.2 (19 reachable stdlib vulns), V9 25 lint issues, coverage 47.7%. Gates that fail on `main` for an unknown time are the direct symptom of having no enforcement.
  - `go test -short -count=1 ./...` completes in ~0.8 s wall time here, and `go mod tidy -diff` and `go mod verify` are clean, so the cost of CI would be trivial.
- Impact: v1 public-API compatibility (a contract, `audit.md` §2.1), vulnerability exposure and regressions are only caught if a contributor happens to run the local gates with the right tools installed (see X2-002). Contributors without the local setup, including external PRs and dependabot PRs, merge unverified.
- Source: eduardo/go-ci §1 ("exactly four gates: build, vet/lint, test with race detector, vulnerability scan"), Verification Checklist 1, 4, 12 · eduardo/go-dependency-audit §1 ("Run this in CI. No exceptions.") · SECURITY.md:5-6 (claims CI exists)
- Recommendation: Add a `ci.yml` (push to `main` + `pull_request`, `permissions: contents: read`, SHA-pinned actions, `go-version-file: go.mod`) with parallel jobs: build+vet+`go test -race -shuffle=on -short`; `staticcheck`/semgrep (or the same runner, once X2-002/X2-003 are fixed); `govulncheck` (pinned, see X2-012); `go mod tidy -diff` + `go mod verify`; `gorelease -base=<last tag>` on PRs (informational first). Note: release-please PRs created with `GITHUB_TOKEN` do not trigger `pull_request` workflows; decide whether to use a PAT/GitHub App or to also run the checks on `push` to the release branch. Start lint as informational (no `.golangci.yml` is committed; V9 has 25 issues).
- Breaking: no · Needs approval: yes (new CI jobs and, for lint, new tooling configuration — `audit.md` §3)

### X2-003 — `staticanalysis.sh` reports "OK" (exit 0) when staticcheck or semgrep crash, or when staticcheck is missing
- Area: H · Severity: HIGH · Effort: S
- Location: `.skillshare/skills/go-code-quality-check/scripts/staticanalysis.sh:275-278, 284-304, 330-359, 365-368, 399-409` (external, gitignored skill; executed by Taskfile and pre-commit)
- Problem: Tool exit codes are captured (`rc`) but never gate the result. If a tool produces no parsable output (crash, bad config, Docker/semgrep failure, staticcheck build error), the script writes `[]`, prints `✓ (0 findings, 0 errors, rc=2)` and ends with `OK`. A missing `staticcheck` is "skipped" and also exit 0, although the skill document says "quote the install command and stop". `jq` is hard-required (lines 140, 163…) with no `command -v` guard, and is neither installed by `tools:install` nor mentioned in README/SECURITY.
- Evidence: reproduced with fake shims for `docker`, `semgrep`, `staticcheck` (each exiting non-zero with an error on stderr), `QG_FULL=1 QG_SKIP_VET=1`, output dir in scratchpad:
  ```text
  staticanalysis: mode=full pkgs=1 files=1 → <scratch>/out1
  [2/3] staticcheck ✓ (0 findings, 0 errors, rc=2)
  [3/3] semgrep     ✓ (0 findings, 0 errors, rc=2)
  staticanalysis: 0 findings, 0 errors. OK.      exit=0
  ```
  Consequence in this audit: `discovery.md` §11 could not tell which semgrep path (Docker with community packs vs. local CLI with `.semgrep.yml` only) produced "0 findings", because the report does not record it and the stderr log is empty.
- Impact: The only static-analysis/security gate can silently pass without having analysed anything (broken Docker, offline pack download, staticcheck built with an older Go than `go.mod`, uninstalled tool). Combined with X2-001 there is no second line of defence.
- Source: eduardo/go-ci §1 (gates must fail the build) · eduardo/go-code-review §0 ("skip any tool that is not installed *and note it in the report*") · project skill go-code-quality-check "Boundaries" ("If … is missing, quote the install command and stop")
- Recommendation: In the script: treat `rc` not in {0, tool's "findings found" code} with empty output as a tool failure (exit non-zero); fail when `staticcheck`/`jq` are absent unless explicitly skipped via `QG_SKIP_*`; record in the report which semgrep path and rule packs ran. The script lives in `trypanic/skills`, so fix it upstream and pin the new ref (see X2-002).
- Breaking: no · Needs approval: yes (changes the behavior of the project's quality gate; external repo)

### X2-004 — Release verification (build/vet/test) runs only after the tag and GitHub Release are published; nothing gates the merge to `main`
- Area: H · Severity: MEDIUM · Effort: S
- Location: `.github/workflows/release.yml:26-38` (job `release-please`), `:40-65` (job `assets`, `if: release_created == 'true'`, step "Verify tagged tree")
- Problem: The tag and GitHub Release are created by the `release-please` job; `assets` then runs `go build/vet/test -short` against the tag. If that fails, the failing version is already public: the tag cannot be moved (module proxy and users' `go.sum` pin it) and the only remedy is `retract` plus a new patch. - Source: eduardo/go-build-release §7 ("Never move or delete a published tag … withdrawn with `retract`") and Verification Checklist 5 · eduardo/go-ci §1
- Recommendation: Move the verification to a PR/push CI that must be green before the release PR is merged (X2-001) and keep the post-release job as a smoke check. Optionally add `workflow_dispatch` to re-run asset upload for an existing tag.
- Breaking: no · Needs approval: yes (CI/release workflow change)

- Recommendation: Decide explicitly: add a `.semgrepignore` that does not exclude tests (and keep the per-rule `paths.exclude` already in `.semgrep.yml`), or document in SECURITY.md that tests are out of scope and exclude them in staged mode too. Fix or suppress the one test-side warning.

## Strengths

- Release pipeline hygiene: every third-party action pinned by commit SHA with a version comment; workflow-level `permissions: contents: read` with per-job `contents/pull-requests: write`; `persist-credentials: false`; `concurrency` group with `cancel-in-progress: false`; SBOM tool pinned (`cyclonedx-gomod@v1.12.0`); proxy warm-up; header comment documents the required repository setting.
- Conventional Commits enforced by a `commit-msg` hook and mirrored in `release-please-config.json` and `cliff.toml` (`task changelog` preview matches the release PR sections).
- Module hygiene verified now: `go mod tidy -diff` clean, `go mod verify` "all modules verified", no `replace` directives.
- Taskfile quality: version-3 schema, documented tasks, preconditions with actionable messages, packages list derived from `go list` (new top-level packages join automatically), parallel per-package test/verify, and a deliberate single `go get` in `deps:update` to avoid `go.mod` races; `release:check` derives the base tag with `git describe` instead of a hard-coded version.
- Tests are fast (`go test -short -count=1 ./...` ≈ 0.8 s), so a full CI gate with `-race` is cheap.
- SECURITY.md's runner description (knobs, outputs, exit-code contract, Docker vs. CLI rule packs) matches the script; semgrep suppressions use documented `// nosemgrep: <rule>` markers; `.staticanalysis/` reports are gitignored with a `.gitkeep`.
- Package READMEs exist for all 21 importable packages; AGENTS.md on disk already uses `task …` commands (no stale `moon` references in tracked docs).
