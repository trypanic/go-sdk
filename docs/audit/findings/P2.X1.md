### X1-001 — `logger` mixes the zerolog API with the OTLP gRPC exporter, so every package that logs pulls gRPC and OTLP into consumer binaries
- Area: A (Architecture & design) · Severity: HIGH · Effort: M
- Location: logger/logprovider.go:8,62 (imports and calls `otlploggrpc`); httprequest/httperror.go:14,156 and httprequest/audit.go:10,50-51 (only uses of `logger` in `httprequest`); grpc/options.go:8,59; messaging/messaging.go:14,75, messaging/amqp.go:10; httpserver/hertz/server.go:17, request_logger.go:11
- Problem: `logger` is a hub of the import graph (imported by `httprequest`, `grpc`, `messaging`, `httpserver/hertz`, and through `httprequest` by `llmclient`), and the same package holds the OTLP log exporter (`otlploggrpc`, which depends on `google.golang.org/grpc` and protobuf). A consumer that only wants a retrying HTTP client therefore links a gRPC stack and an OTLP exporter it never calls. `httprequest` imports `logger` for two log statements.
- Evidence:
  - `go list -deps` third-party module count per package: `httpclient` 0, `telemetry` 8, `logger` 25, `httprequest` 25, `llmclient` 25, `grpc` 26, `messaging` 27. `go list -deps ./httprequest` contains `google.golang.org/grpc` and `.../otlploggrpc`. Only `logger/logprovider.go` imports `otlploggrpc`/`sdk/log`.
  - Two scratchpad binaries built with go1.26.2: `main` calling `httprequest.NewWithoutTracing(http.DefaultClient)` = **17 MB, 26 module deps** (`go version -m` lists `google.golang.org/grpc v1.85.0`, `otlploggrpc v0.23.0`, `go.opentelemetry.io/proto/otlp`, `grpc-gateway/v2`, `zerolog`). `main` using `net/http` + `telemetry.NewInstrumenter` + `errorkit.NewError` = **6.0 MB, 9 deps**.
  - `go mod why -m github.com/cenkalti/backoff/v5` → `logger` → `otlploggrpc` → `.../internal/retry`.
- Impact: binary size, build time, attack surface (govulncheck findings in gRPC reach HTTP-only services) and dependency churn for every consumer of the HTTP, messaging and gRPC packages. It also goes against the stated aim (AGENTS.md §5 warns about pulling Hertz in transitively, and the `httpserver` README avoids a framework import for the same reason). P2.X3 measures the module-level weight. This finding is about the package-level dependency direction that causes it.
- Source: eduardo/go-architecture-review §2 (dependency direction), §4 (one package = one purpose); go-design-principles SRP ("A package that mixes … is … packages"); AGENTS.md §5 (transitive-weight anti-pattern)
- Recommendation: (1) Non-breaking, now: drop the `logger` import from `httprequest` (log through `zerolog.Ctx(ctx)`/`log.Ctx` or an injected hook, which C2's DN-09 fix needs anyway). That alone frees `httprequest` and `llmclient` from gRPC/OTLP. (2) Non-breaking: move the exporter into a new `logger/otlp` (or `otlplog`) package and leave `logger.SetupOTLP`/`InitLogProvider`/`NewOTLPWriter` as `Deprecated:` forwarders. `logger` still links the exporter until v2, but new code stops depending on it. (3) v2: remove the forwarders so `logger` is zerolog-only. `grpc.WithServerLogger`, `messaging.WithLogger` and `hertz.RequestLoggerMiddleware` take `*logger.Logger` in their signatures, so they can only be decoupled in v2.
- Breaking: no (steps 1–2) | yes (step 3, removal of forwarders) · Needs approval: yes (architecture change, new package; step 3 is breaking)

### X1-002 — Tracing injection takes four different shapes, and the "one instrumenter passed down" invariant cannot be honoured
- Area: A/G · Severity: MEDIUM · Effort: M
- Location: telemetry/trace.go:56-58 (`Instrumenter{tracer}`, no accessor), 143-147 (nil receiver falls back to the global tracer); grpc/options.go:47,106 (`trace.TracerProvider`); messaging/messaging.go:48-51,125-130 (`trace.Tracer`, default `otel.Tracer("messaging")`); httpserver/hertz/server.go:45-49 (`hertztracing.NewServerTracer()` with no options); postgres/tracing.go:34-39; AGENTS.md:106, 226, 339; README.md:57-60
- Problem: `httprequest`, `llmclient`, `mongo` and `postgres` take a `*telemetry.Instrumenter`. `grpc` takes a `trace.TracerProvider`. `messaging` takes a `trace.Tracer`. `httpserver/hertz` can only use the global provider, because hertz-contrib `tracing@v0.4.1` has no provider option (`options.go:87` hard-codes `otel.GetTracerProvider()`). `Instrumenter` exposes neither its tracer nor its provider, so a service that builds one instrumenter as AGENTS.md:226 asks ("One instrumenter passed down") cannot hand it to `grpc`, `messaging` or `hertz`, and has to keep a separate provider/tracer in sync by hand. AGENTS.md:106 lists only `postgres` and `messaging` as exceptions. `grpc` and `hertz` are undocumented exceptions to the triplet that AGENTS.md:339 requires of new packages. README.md:57 says "Every package that produces spans accepts a `*telemetry.Instrumenter`", which is false for three packages. Nil semantics also differ: `WrapWithInstrumenter(x, nil)` returns `x` untraced in `httprequest`/`llmclient`/`mongo` but wraps in `postgres`, where the nil instrumenter falls back to the global tracer (trace.go:144-145). That is DN-11, owned by C4 for the postgres fix. The inconsistency across packages is reported here.
- Evidence: signatures above. `go doc ./telemetry Instrumenter` shows only `Start, Job, Batch, External, Messaging, DB`.
- Impact: tracer scope names and providers drift between components, and test setups need a different injection per package. Callers who read the contract expect `nil` to mean "off" everywhere.
- Source: eduardo/go-dependency-injection §1 (explicit dependencies, one mechanism); eduardo/go-design-patterns §1; AGENTS.md §2.2, §3 invariant 3, §8
- Recommendation: all of these are additive. Add `func (*Instrumenter) TracerProvider() trace.TracerProvider` (store the provider) so it can be passed to `grpc.WithServerTracerProvider`/`messaging.WithTracer`. Optionally add `grpc.WithServerInstrumenter`/`WithClientInstrumenter` and `messaging.WithInstrumenter`. Document in AGENTS.md §2.2 that `grpc` and `hertz` are exceptions and that `hertz` tracing always uses the global provider. Pick one meaning for a nil instrumenter ("no tracing") and apply it in `postgres` too (C4 item).
- Breaking: no · Needs approval: yes (changes the AGENTS.md/README contract text; nil semantics in `postgres` change observable behaviour)

### X1-003 — SDK tracing wrappers never mark failed operations on the span
- Area: G (observability) · Severity: MEDIUM · Effort: S
- Location: httprequest/tracing.go:57-61; llmclient/tracing.go:38-42; mongo/tracing.go:66-122; postgres/tracing.go:46-72
- Problem: every decorator does `ctx, span := Start(...); defer span.End(); return inner.X(...)` and drops the returned error. No call to `span.RecordError`/`SetStatus(codes.Error)`, and no use of `telemetry.RecordError` (telemetry/helpers.go:31-34), which exists for this purpose. `messaging` is the only package that records errors (messaging.go:216-217, 322-323, 329-330). Confirms DN-10.
- Evidence: `grep -rn 'RecordError\|SetStatus' --include='*.go'` outside `telemetry`: only `messaging/messaging.go`.
- Impact: a failed HTTP call, LLM call, Mongo operation or stored procedure shows up as a green span. Error-rate views and tail sampling on status (go-observability "Sampling") miss every SDK-level failure.
- Source: eduardo/go-observability §2 ("On failure call span.RecordError(err) and span.SetStatus … or the trace shows a green span"), checklist item 6
- Recommendation: in each wrapper, capture the error and call `telemetry.RecordError(span, err, <code>)` (and add `errorkit` code/retriable as attributes when the error is an `*AppError`). One shared unexported helper per package, or an exported `telemetry.End(span, err)` helper (additive).
- Breaking: no · Needs approval: no

### X1-004 — Span naming, kind and attributes ignore the SDK's own conventions, and HTTP span names are high-cardinality
- Area: G (observability) · Severity: MEDIUM · Effort: M
- Location: httprequest/tracing.go:63-105; llmclient/tracing.go:44-49; mongo/tracing.go:66-68; postgres/tracing.go:70-79; messaging/messaging.go:170-172, 290-291, 314-315; AGENTS.md:113-115
- Problem: AGENTS.md:113-115 says to use `telemetry.Job/Batch/External/Messaging/DB` and "Do not invent ad-hoc span name conventions". No SDK package calls them: the six matches of `telemetry.(DB|External|Job|Batch|Messaging)(` outside `telemetry` are all doc comments inside `telemetry/trace.go`. Each package invents its own scheme: `http.<host label>.<METHOD>.<seg>.<seg>`, `llm.<model>`, `mongo.<coll>.<op>`, `postgres.<proc>`, `messaging.publish <queue>` (space-separated). The SDK wrappers set no `SpanKind` (only `messaging` sets Producer/Consumer) and no semantic-convention attributes (`db.system`, `server.address`, `http.request.method`). The HTTP name includes the last two path segments verbatim, so `GET https://api.example.com/v1/users/8f3a` becomes `http.example.GET.users.8f3a`, which mints one span name per resource ID.
- Evidence: code above. `lastTwoPathSegments` (httprequest/tracing.go:95-105) uses raw path segments.
- Impact: inconsistent trace trees across services. Backends that group by span name get unbounded cardinality. Without `SpanKindClient`, service maps cannot draw the outbound edge.
- Source: eduardo/go-observability §2 (name after the operation), §3 (bounded cardinality), references/tracing.md "Span naming"; AGENTS.md §2.2
- Recommendation: route the wrappers through `Instrumenter.External/DB` (or document new helpers such as `telemetry.HTTP`/`LLM`), set `trace.WithSpanKind(trace.SpanKindClient)`, put variable parts in attributes, and use a low-cardinality HTTP name (method + host, or a caller-provided route template). Span names are a consumer-visible contract (dashboards, alerts): roll out behind an option or in a minor release with a CHANGELOG note.
- Breaking: no (API) · Needs approval: yes (changes telemetry visible to consumers, and contradicts the documented span-name examples in httprequest/postgres/mongo READMEs)

### X1-005 — Exported interfaces that consumers are invited to implement freeze the v1 surface; `httpserver` cannot route PATCH/HEAD/OPTIONS
- Area: G/A · Severity: MEDIUM · Effort: M
- Location: httpserver/contracts.go:12-67 (`HTTPContext`, 15 methods), 119-139 (`RouterGroup`), 147-177 (`HTTPServer`); mongo/contracts.go (`Collection`, 9 methods; `ClientPort`); httpserver/README.md:10; mongo/README.md:257
- Problem: these are producer-side interfaces that also serve as extension points. The httpserver README says consumers "implement the same interfaces", and the mongo README says tests "substitute a fake `ClientPort`". Under semver v1, adding a method to any of them breaks every outside implementer, so they cannot grow. They are already incomplete. `HTTPServer` and `RouterGroup` have only `GET/POST/PUT/DELETE`: no `PATCH`, `HEAD`, `OPTIONS` or `Any`. Because the Hertz wrapper type is unexported (httpserver/hertz/wrapper.go:13) and exposes no engine, a service on `httpserver` has no way to register a PATCH route. `HTTPContext` has no `Method`, `Path`, cookies, form values or remote address, and `Redirect` takes `location []byte`, a Hertz idiom in a framework-agnostic contract. `mongo.Collection` lacks `UpdateMany`, `DeleteMany`, `Aggregate`, `FindOneAndUpdate`, `Distinct` and index management.
- Evidence: interface bodies above; `go doc ./httpserver HTTPServer`.
- Impact: consumers fall back to the raw framework or driver, which defeats the abstraction, or the SDK has to go to v2 for routine additions.
- Source: eduardo/go-interface-design §1 (define at the consumer), §2 (small interfaces), §8; eduardo/go-api-design §4 (PATCH for partial update); go-design-principles YAGNI/KISS
- Recommendation: add capabilities through new optional interfaces checked with comma-ok assertions (e.g. `type PatchRouter interface{ PATCH(string, HandlerFunc) }`, implemented by the Hertz wrapper and group), plus a generic `Handle(method, path, h)` on the concrete adapter. Both are additive and gorelease-compatible. For v2, make the router interfaces small and consumer-side, and return concrete adapter types (see X1-006).
- Breaking: no (optional-interface route) | yes (adding methods to the existing interfaces) · Needs approval: yes (contract evolution strategy for the httpserver/mongo public contracts)

### X1-006 — Adapters return interfaces, hide their concrete types and offer no escape hatch (unlike `grpc`)
- Area: G · Severity: MEDIUM · Effort: M
- Location: httpserver/hertz/server.go:23,30 and wrapper.go:13-17 (unexported `wrapperHertzServer`, no engine accessor); httpserver/hertz/request_logger.go:16; mongo/client.go:38-80 (returns `ClientPort`), 83-85 (`(*Client).Database`); httprequest/httprequest.go:142-170; llmclient/client.go:80-95; messaging/messaging.go:88; mongo/README.md:206-210; httprequest/README.md:125,135
- Problem: the constructors of `httprequest`, `llmclient`, `mongo`, `messaging.NewPubSub` and `hertz` return interfaces (discovery §4 constructor table). The concrete types and their extra capabilities are unreachable:
  - `(*mongodb.Client).Database()` exists, but `New`/`NewWithInstrumenter` return a tracing decorator, so a type assertion fails.
  - There is no constructor taking an existing `*mongo.Client` or custom `*options.ClientOptions`. The mongo README concedes that adding `otelmongo` "requires direct driver use".
  - `hertz.RequestLoggerMiddleware` returns `app.HandlerFunc`, which cannot be installed through `HTTPServer.Use`, and the engine is unexported (DN-17).
  - `httprequest.New`/`NewHTTPRequestWithRetry` are documented to return `*HTTPRequest` (DN-07) but return the interface.

  `grpc` shows the alternative inside the same SDK: concrete `*Server`, `*grpc.ClientConn`, and `WithRawServerOptions`/`WithRawDialOptions` escape hatches (grpc/options.go:77,127).
- Evidence: signatures from `grep '^func New'`. mongo/adapter.go:10 asserts `(*Client)` implements `ClientPort`, but callers never receive a `*Client` from the traced constructors.
- Impact: any need beyond the wrapped subset forces consumers off the SDK for the whole component.
- Source: eduardo/go-interface-design §3 (accept interfaces, return structs); eduardo/go-design-patterns §3 (return interfaces only from genuine factories); eduardo/go-grpc §6
- Recommendation: additive escape hatches. `hertz.NewEngine(...)` returning a concrete type with `Engine() *server.Hertz` (or `UseHertz(app.HandlerFunc)`). `mongodb.NewFromClient(*mongo.Client, db string, instr)` and `WithClientOptions`. Exported `Unwrap()` on the tracing decorators. Changing existing return types to concrete is v2 material.
- Breaking: no (additions) | yes (changing return types) · Needs approval: yes (return-type change would be breaking; new public constructors)

### X1-007 — `errorkit` metadata is "data-driven" but neither transport adapter uses it; package codes become gRPC `Internal`
- Area: A/G · Severity: MEDIUM · Effort: S
- Location: grpc/status.go:14-38 (`codeFor`), 48-66; httpserver/response.go:28-40 (`WithErrorOpt`); AGENTS.md §2.1 and §4 ("use `appErr.Metadata.HTTPStatus`")
- Problem: every `AppError` carries `Metadata.HTTPStatus` and `Retriable`, and each package registers rich codes for its domain. `grpc.ToStatus` instead hard-codes the 15 core codes, so every package-owned code (`ERR_DB_*`, `ERR_MQ_*`, `ERR_NETWORK_*`, `ERR_AUTH_*`, `ERR_EXTERNAL_*`) maps to `codes.Internal`, including retriable 503s and auth 401s. On the HTTP side, `WithErrorOpt` copies only `err.Error()` and `TraceID`. No helper turns an `AppError` into a status. Each handler must repeat the mapping AGENTS §4 describes, and there is no `FromStatus` to bring gRPC client errors back into `AppError` form, so callers of generated clients leave the error contract. Overlaps DN-23 (C3). This finding covers the cross-package design.
- Evidence (scratchpad program calling the public API, removed afterwards):
  ```text
  ERR_DB_POSTGRES_UNAVAILABLE http=503 retriable=true -> grpc=Internal
  ERR_MQ_UNAVAILABLE http=503 retriable=true -> grpc=Internal
  ERR_AUTH_UNAUTHENTICATED http=401 retriable=false -> grpc=Internal
  ```
- Impact: gRPC clients cannot tell "retry later" (`Unavailable`) from bugs (`Internal`), and HTTP error responses drift between services.
- Source: eduardo/go-grpc §2 (map domain errors in ONE place; `Unavailable` is retryable), references/clients.md "Reading errors"; eduardo/go-api-design §8 (consistent error responses); AGENTS.md §2.1
- Recommendation: derive the gRPC code from `Metadata` when no explicit mapping exists (`HTTPStatus` 503→`Unavailable`, 504→`DeadlineExceeded`, 401→`Unauthenticated`, 403→`PermissionDenied`, 404→`NotFound`, 409→`AlreadyExists`/`Aborted`, 429→`ResourceExhausted`, 4xx→`InvalidArgument`/`FailedPrecondition`). Add `httpserver` helpers (`ReplyError(c, err)` or a `StatusFor(err)` function) and `grpc.FromStatus(err) error`. These are additive functions, but the gRPC code returned for existing package codes changes.
- Breaking: no (API) · Needs approval: yes (visible change in returned gRPC codes)

### X1-008 — Logger injection is inconsistent; library code logs returned errors through the global logger
- Area: A · Severity: MEDIUM · Effort: M
- Location: httprequest/httperror.go:156 (`logger.Error(appErr)` on every non-2xx); messaging/amqp.go:98,105,116,143,160 (global `logger.Info` despite `WithLogger`, messaging.go:75); httpserver/hertz/server.go:103-109 (`RecoveryHandler` → global `logger.ErrorCtx`, no option); grpc/options.go:59 (`WithServerLogger`, the one complete case); AGENTS.md:120-121
- Problem: AGENTS.md §2.3 says adapters and middleware "accept an explicit `*logger.Logger` or read `logger.CtxOrGlobal(ctx)`". In practice there are four behaviours: `grpc` injects a logger properly. `messaging` injects one only for reconnect warnings (DN-24, C5). `hertz` has no injection. `httprequest` calls the global logger, ignoring the context logger it already uses in `audit.go:50-51` (DN-09, C2). Besides the inconsistency, `httprequest` logs an error it also returns, so a caller following AGENTS §4 (log at the boundary) logs every failure twice.
- Evidence: lines above.
- Impact: per-request fields and trace correlation are lost for SDK-emitted lines. Tests cannot capture or silence SDK logs without mutating the global logger, which AGENTS §5 calls race-prone. Error logs are duplicated.
- Source: eduardo/go-dependency-injection §1, §3 (no hidden global dependencies); eduardo/go-observability §1 ("Inject the logger as a dependency"); AGENTS.md §2.3
- Recommendation: one rule for all packages: resolve the logger as option > `logger.CtxOrGlobal(ctx)` > global, and do not log errors that are returned to the caller (leave that to the boundary). Add `hertz` server options for a logger (see X1-010) and make `messaging.WithLogger` cover the publisher. Individual fixes stay with C2/C5. This finding covers the shared policy.
- Breaking: no · Needs approval: no

### X1-009 — Constructors that do network I/O handle `context` inconsistently
- Area: G · Severity: MEDIUM · Effort: S
- Location: mongo/client.go:38-73 (`New(ctx, cfg)`); postgres/postgres.go:30, 60-65 (`NewPostgresClient(cfg)` with `context.WithTimeout(context.Background(), 5*time.Second)`); messaging/messaging.go:88, amqp.go:29,43-46 (`NewPubSub(url, ...)` dials with no ctx and no timeout option)
- Problem: three components that connect at startup expose three conventions. `mongo` takes a caller context. `postgres` ignores the caller and uses a fixed 5 s budget. `messaging` dials with neither a context nor a configurable timeout. Callers cannot cancel startup (e.g. SIGTERM during a slow connect) or give a slow network more than 5 s for Postgres.
- Evidence: signatures above.
- Impact: inconsistent DX. Startup cancellation and deadlines cannot be controlled for two of the three data adapters.
- Source: eduardo/go-context (via go-database §2 "Always pass context"); eduardo/go-database §1; semgrep project rule `context-must-be-first-param` (.semgrep.yml)
- Recommendation: add `NewPostgresClientContext(ctx, cfg)` / `NewPostgresClientFromEnvContext` (and keep the current functions as wrappers with the 5 s default), and a `messaging.WithDialTimeout` option or `NewPubSubContext`. All additive.
- Breaking: no · Needs approval: no

### X1-010 — `httpserver.ServerOptions` is an options struct whose zero value silently disables tracing, recovery, audit and health
- Area: G · Severity: MEDIUM · Effort: S
- Location: httpserver/options.go:41-65 ("The zero value is not meaningful"); httpserver/hertz/server.go:30-31, 45-69, 78-99 ("keeps NewWithOptions safe when callers construct ServerOptions partially")
- Problem: `NewWithOptions(cfg, httpserver.ServerOptions{NoRouteStatus: 410})` looks like "defaults plus one override". In fact it turns off tracing, recovery, audit, `/health`, NoRoute and NoMethod, because `applyOptionDefaults` can only backfill non-bool fields (server.go:81-99). The doc comments contradict each other: options.go:41-43 says start from `DefaultServerOptions()`, while server.go:78-80 promises safety for partial structs. `grpc` uses default-on functional options (grpc/options.go:29-43) and avoids the problem. Docs side: DN-18 (X2). This finding is the API-shape issue.
- Evidence: code above. An `Enable*` field set to `false` cannot be told apart from an unset one.
- Impact: a one-field override in production code can remove panic recovery.
- Source: eduardo/go-design-patterns §1 and references/creation-patterns.md (functional options for optional settings with sensible defaults), §5 (zero values first); eduardo/go-api-design §2 (Recoverer outermost)
- Recommendation: add functional options (`hertz.NewServer(cfg, hertz.WithoutTracing(), hertz.WithNoRouteStatus(410), hertz.WithLogger(l))`) with default-on behaviour, mark `NewWithOptions` as the advanced path, and fix the server.go:78-80 comment. Adding a variadic parameter to the existing `New` would change its signature, so it has to be a new function.
- Breaking: no · Needs approval: no

### X1-011 — Third-party types, including a superseded major and a pre-1.0 module, are part of the v1 API

## Strengths

- **Acyclic, layered graph with a dependency-free core.** `errorkit` has zero
  intra-module and zero third-party imports. Ten packages (`errorkit`,
  `httpclient`, `httpserver`, `ioutils`, `marshal`, `slices`, `storage`,
  `stringutils`, `urlkit`, `validators`) are stdlib-only (discovery §3.3).
  The `.sentrux` boundaries hold.
- **Framework isolation where it was designed.** `httpserver` has no
  framework import, Hertz lives only in `httpserver/hertz`, and `postgres`
  and `mongo` do not pull `otelpgx`/`otelmongo`.
- **`grpc` is the model package.** It has default-on functional options,
  injectable tracer provider and propagator, raw escape hatches
  (`WithRawServerOptions`, `WithRawDialOptions`), concrete return types, a
  thorough `doc.go`, recovery as the outermost interceptor, a
  graceful-then-hard `Shutdown`, and `bufconn` round-trip tests over all
  four call modes. It matches eduardo/go-grpc §4, §6, §7, §8.
- **Decorator-based tracing over small interfaces** (`HTTPRequester`,
  `LLMProvider`, `StoredProcedurer[T]`) keeps tracing optional and makes the
  small interfaces easy to fake. The fixes in X1-003/X1-004 can be made
  inside the wrappers.
- **Consistent error-code registration pattern** in six packages
  (`ErrorMetadata` + `RegisterErrors(*Registry)` + `init()` → `MustRegister`).
  Retriability is data-driven and consumed by `httprequest`.
- **Explicit configuration seams for tests**: `messaging.WithTopology`,
  `postgres.Querier` (satisfied by `*pgxpool.Pool` and `pgx.Tx`, verified by
  a compile check), `httpclient.WithTransportWrapper`, and an injectable
  clock in `httpserver.ReplyOptions`.
- **No API break since v1.0.0**: `gorelease` reports no incompatible change.
  Compile-time interface assertions exist in `mongo` (adapter.go:10,71) and
  `httprequest` (httprequest.go:113).

## Open questions

1. CORS preflight: with no `OPTIONS` routing in `httpserver` (X1-005), does a
   global `Use` middleware on the Hertz adapter run for unmatched-method
   requests before the NoMethod 405 handler? Not executed. It decides
   whether browser clients can be served at all.
2. Do any consumers implement `httpserver.HTTPServer`/`HTTPContext` or
   `mongodb.Collection` outside this repo? That sets how much X1-005 matters
   in practice. It cannot be checked from the tree.
3. `WrapWithTracing`/`New` capture `otel.GetTracerProvider()` at
   construction. OTel's global delegate should forward to a provider set
   later, but this was not tested for the SDK wrappers (relevant to the
   AGENTS §3 bootstrap order).
4. `httpserver.WithErrorOpt` sends `err.Error()` to HTTP clients
   (response.go:33-34). For an `AppError` this may include internal reasons
   or wrapped driver text. This is an information-leak question for P2.C2.
5. `logger.Panic` calls `os.Exit(1)` (discovery §2/AGENTS bootstrap) and
   does not panic, so deferred shutdowns do not run. Naming and behaviour
   belong to P2.C1.
6. `llmclient.LLMRequest` has `MaxTokens`/`Temperature`, but
   `LLMRequestConfig` cannot set them (llmclient/client.go:21-26, 53-57).
   This is an API-completeness question for P2.C2.
7. Whether the single module should be split, so that HTTP-only consumers
   avoid Hertz, gRPC, Mongo, pgx and AMQP in their module graph, is a P2.X3
   and P3 decision. X1-001 covers only the package-level part.
