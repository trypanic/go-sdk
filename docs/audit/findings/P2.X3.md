### X3-001 — Core packages reach 19 standard-library vulnerabilities when built with Go ≤ 1.26.9, and the SDK's own release pipeline builds with Go 1.26.1
- Area: D (Security / supply chain) · Severity: HIGH · Effort: S
- Location: go.mod:3; .github/workflows/release.yml:57-65,70; httprequest/httprequest.go:245,253; messaging/amqp.go:247; postgres/postgres.go:65,75; mongo/client.go:54,62,94,102; httpserver/hertz/wrapper.go:59
- Problem: govulncheck reports 19 vulnerabilities in the standard library
  that the call graph reaches, through the main paths of `httprequest`,
  `messaging`, `postgres`, `mongo`, `httpserver/hertz` and `logger`. The
  highest fix level is `go1.26.10` (GO-2026-6809). Nothing raises a
  consumer's toolchain to that level, and nothing tells consumers to do it.
  `go.mod` declares `go 1.26.1` and has no `toolchain` line. The release
  job installs Go from `go-version-file: go.mod`, so the tagged tree is
  built, vetted, tested and given an SBOM with a toolchain that has every
  one of these vulnerabilities plus older ones.
- Evidence (go1.26.2, `-show verbose`, sample traces):
  - GO-2026-4918 (infinite loop in the HTTP/2 transport on a bad
    `SETTINGS_MAX_FRAME_SIZE`, fixed in 1.26.3): `httprequest/httprequest.go:245:25: HTTPRequest.executeRequest calls http.Client.Do`
  - GO-2026-6809 (distrust of compromised intermediates in crypto/x509,
    fixed in 1.26.10): `messaging/amqp.go:247:30: Subscriber.connect calls amqp091.DialConfig, which eventually calls x509.Certificate.Verify`
  - GO-2026-6607, -6090, -5856 (crypto/tls): `postgres/postgres.go:75`,
    `mongo/client.go:94`, `httprequest/httprequest.go:245`, `messaging/amqp.go:247`
  - GO-2026-6608 (MIME header memory-limit bypass, fixed in 1.26.9):
    `httpserver/hertz/wrapper.go:59:15: wrapperHertzServer.Run calls server.Hertz.Spin, which eventually calls multipart.Reader.ReadForm`
  - GO-2026-5972 (asn1 recursion): `mongo/client.go:54:11: NewWithInstrumenter calls options.ClientOptions.ApplyURI, which eventually calls asn1.Unmarshal`
  - Count by stdlib package: net/http 9, crypto/tls 3, crypto/x509 2,
    net/textproto 2, encoding/asn1 1, net 1, net/url 1. The fix levels are
    1.26.3, 1.26.4, 1.26.5, 1.26.6, 1.26.9 and 1.26.10.
  - With go1.27.3 the same command finds `No vulnerabilities found` at
    symbol and package level.
  - `release.yml:57-59`: `actions/setup-go@… # v7.0.0` with
    `go-version-file: go.mod`, and `go.mod:3` is `go 1.26.1`. Discovery §8.5
    records that this resolves Go 1.26.1.
- Impact: a service built with Go 1.26.1–1.26.9 is exposed through ordinary
  SDK use. Examples: a malicious or compromised upstream can hang the
  `httprequest` client with GO-2026-4918, and AMQP/Postgres/Mongo TLS
  connections accept certificates that 1.26.10 distrusts. The project's
  own release checks pass on a toolchain that is known to be vulnerable.
  The vulnerable code is the toolchain's, not the SDK's. The SDK makes it
  reachable and leaves the toolchain policy unstated.
- Source: eduardo/go-dependency-audit §1 ("Run this in CI. No exceptions"),
  §6 (Go version management); eduardo/go-security-audit "Run the Scanners
  First"; audit.md §1 (Go facts), baseline V8.
- Recommendation: (1) Build and test the repository with a patched
  toolchain: add a `toolchain` line (see X3-002) or set `go-version` in
  `release.yml` explicitly. (2) Add a "Supported toolchains" note to
  `README.md`/`SECURITY.md`: build consumers with the latest patch release
  of Go 1.26 (≥ 1.26.10 today) or 1.27. (3) Run govulncheck in CI against
  that toolchain (X3-003). Do not raise the `go` directive only to force a
  patched toolchain on consumers (X3-002).
- Breaking: no · Needs approval: yes (a `toolchain` line changes `go.mod`, so it belongs to R-DEPS; changing the release workflow is CI tooling)

### X3-002 — Go version policy: `go 1.26.1` with no `toolchain` line, while `.prototools` pins 1.27.3 and CI resolves 1.26.1
- Area: D / H (supply chain, reproducibility) · Severity: MEDIUM · Effort: S
- Location: go.mod:3; .prototools:1; .github/workflows/release.yml:57-59
- Problem: three different toolchains are in play. Developers who use proto
  run 1.27.3 (`.prototools:1`, `go = "1.27.3"`). The PATH on this host has
  1.26.2. CI uses 1.26.1, read from the `go` directive. Vulnerability
  results and test behavior differ between them (X3-001: 19 vulnerabilities
  vs 0). The brief asks whether `go.mod` should bump `toolchain` or `go`.
  The analysis:
  - A `toolchain` directive takes effect only when this module is the main
    module (development, CI, the release job). Consumers ignore it. With the
    default `GOTOOLCHAIN=auto`, an older local `go` command switches to the
    named toolchain (go.dev/doc/toolchain). It is the right lever to make
    repository builds use a patched Go, and it costs consumers nothing.
  - The `go` directive is a floor for every consumer. A consumer module
    declaring `go 1.25.0` was bumped by the toolchain on import (output
    below). The linked dependencies already require `go 1.26.0`:
    `grpc@v1.85.0`, `otel@v1.47.0`, `otlploggrpc@v0.23.0`, `otelgrpc@v0.72.0`
    and `genproto/googleapis/rpc` all declare `go 1.26.0` in the module
    cache `.mod` files. Raising the SDK's `go` to `1.26.10` would force a
    patch-level toolchain floor on every consumer, including consumers who
    import only `errorkit`, which reaches none of these vulnerabilities (0
    third-party modules, X3-004). It also shifts toolchain patching, which
    the consumer owns, into a library's version history.
- Evidence:
  ```text
  $ go get github.com/trypanic/go-sdk/errorkit@v1.0.0   # consumer go.mod: go 1.25.0
  go: upgraded go 1.25.0 => 1.26.1
  go: added github.com/trypanic/go-sdk v1.0.0
  ```
  `.prototools:1` `go = "1.27.3"`; `go.mod:3` `go 1.26.1`, no `toolchain`
  line; `release.yml:59` `go-version-file: go.mod`.
- Impact: CI results do not reflect what developers run or what a patched
  consumer builds. The vulnerability status of the release pipeline depends
  on which toolchain happens to be installed.
- Source: eduardo/go-dependency-audit §6 ("`go` = minimum version that
  supports features you use; `toolchain` pins the exact toolchain"; "Test
  against multiple Go versions in CI"); references/resolution-and-workspaces.md
  (MVS); audit.md §2.1 (JetBrains guidance limited to the `go` directive).
- Recommendation: keep `go 1.26.1`. Lowering it to `1.26.0` to match the
  dependencies would be a cosmetic consumer-facing change with no real
  benefit. Add `toolchain go1.27.3` to align with `.prototools`, or the
  latest patched 1.26.x if the project wants CI to test the minimum
  supported language line. Use a CI matrix of {latest 1.26.x, latest 1.27.x}
  once CI exists (P2.X2). Record in `README.md` that the `go` directive is a
  language floor, not a security floor.
- Breaking: no · Needs approval: yes (`go.mod` change, which is R-DEPS only, plus a toolchain policy decision)

### X3-003 — No automated vulnerability or dependency scanning anywhere (no govulncheck task, hook, or CI job, and no Dependabot config in the tree)
- Area: D / H · Severity: MEDIUM · Effort: S
- Location: Taskfile.yml (no `vuln` task); .pre-commit-config.yaml; .github/workflows/ (only release.yml); SECURITY.md (no mention of govulncheck)
- Problem: govulncheck runs only when someone types it by hand (baseline
  V8). `grep -n govulncheck` over `Taskfile.yml`, `SECURITY.md`, `README.md`,
  `.pre-commit-config.yaml` and `release.yml` returns nothing. There is no
  `.github/dependabot.yml` or `renovate.json` (`ls` → not found).
  Dependabot merges on `main` (discovery §8.5) mean it may be configured in
  the repository settings. That cannot be verified from the tree, and it
  would not cover call-graph reachability or the toolchain.
- Evidence: the grep and `ls` results above; discovery §8.1 ("No task runs …
  `govulncheck`") and §8.5 (no CI for govulncheck).
- Impact: a new advisory against the toolchain or a linked module (X3-001,
  X3-010) is found only if someone happens to run the tool. Consumers have
  no signal from the SDK's own pipeline.
- Source: eduardo/go-dependency-audit §1 ("Run this in CI. No exceptions");
  eduardo/go-security-audit checklist ("`govulncheck` in CI pipeline");
  audit.md §3 (no new tooling without approval).
- Recommendation: add a `vuln` task running
  `go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...` (pinned version)
  and a scheduled plus per-PR CI job that runs it with the patched
  toolchain. For this library, prefer the pinned `go run …@vX` over the
  skill's `go get -tool`. Tool requirements are ordinary `require` lines in
  `go.mod`, so they would join the requirement graph that every consumer's
  MVS reads (the mechanism shown in X3-004). That is an inference from the
  Go modules reference and was not tested here. Overlaps P2.X2 (missing CI).
- Breaking: no · Needs approval: yes (new task/CI job)

### X3-004 — The single module puts the SDK's whole requirement list into every consumer's version selection, even for stdlib-only packages
- Area: D / A (supply chain, architecture) · Severity: MEDIUM · Effort: L
- Location: go.mod:5-68 (single module for 22 packages)
- Problem: `errorkit` (like `httpclient`, `httpserver`, `storage`, `marshal`,
  `urlkit`, `validators`, `slices`, `stringutils`, `ioutils`) imports only
  the standard library. Importing it nonetheless adds the SDK's 59
  `go.mod` requirements to the consumer's module graph, and minimal version
  selection then treats them as floors. A consumer that imports only
  `errorkit` cannot select `google.golang.org/grpc` or
  `go.opentelemetry.io/otel` below the SDK's versions, although its binary
  links neither. The `go` directive floor (X3-002) spreads the same way.
  Linked code and `go.sum` stay small, because graph pruning keeps the cost
  in version selection only.
- Evidence (throw-away consumer, published `v1.0.0`):
  ```text
  # imports only errorkit
  go.mod:  require github.com/trypanic/go-sdk v1.0.0
  go.sum:  2 lines
  go list -m all | wc -l                 -> 61   (consumer + go-sdk + its 59 requirements)
  go list -deps … non-main modules       -> 1    (only go-sdk is linked)

  # same consumer also imports google.golang.org/grpc
  $ go get google.golang.org/grpc@v1.80.0
  go: removed github.com/trypanic/go-sdk v1.0.0
  go: downgraded google.golang.org/grpc v1.83.2 => v1.80.0
  $ go mod tidy
  go: found github.com/trypanic/go-sdk/errorkit in github.com/trypanic/go-sdk v1.0.0
  go.mod -> google.golang.org/grpc v1.83.2, go.opentelemetry.io/otel v1.46.0
  go mod graph: github.com/trypanic/go-sdk@v1.0.0 google.golang.org/grpc@v1.83.2
  ```
  At HEAD the floors are `grpc v1.85.0`, `otel v1.47.0`, `pgx v5.12.0`,
  `mongo-driver v2.9.3`, `hertz v0.10.6` and so on (go.mod:5-26). Every SDK
  dependency bump raises them for all consumers.
- Impact: consumers pinned to an older gRPC/OTel/Mongo/pgx (for example,
  for compatibility with another library) cannot adopt even
  `errorkit`/`validators` without upgrading those, or are silently upgraded
  by `go mod tidy`. Any `fix(deps)` release of the SDK is a forced upgrade
  wave for every consumer, whichever packages they use.
- Source: eduardo/go-dependency-audit §5 ("A dependency forcing a higher
  minimum version of a shared module on everyone"), §3 ("Size");
  references/resolution-and-workspaces.md (MVS); audit.md §1 (single
  module) and §7 (module split needs approval); discovery §3.3.
- Recommendation: decide explicitly whether the single module is a product
  choice and document it. The alternative is nested modules for the heavy
  adapters (`httpserver/hertz`, `grpc`, `mongo`, `postgres`, `messaging`,
  and the OTLP part of `logger`; see X3-005), keeping the root module for
  the stdlib-only core. A split keeps import paths but needs careful
  sequencing (the root module must drop the moved packages in the same
  release, or consumers hit "ambiguous import"), and it is an architecture
  change. Coordinate with P2.X1.
- Breaking: no for import paths if sequenced correctly; yes for the release/versioning model · Needs approval: yes (module split, per audit.md §7)

### X3-005 — `logger` hard-imports the OTLP gRPC log exporter, so every consumer of `logger`, `httprequest`, `llmclient` or `messaging` links `google.golang.org/grpc`
- Area: D / A / F (dependency weight) · Severity: MEDIUM · Effort: M
- Location: logger/logprovider.go:8 (`otlploggrpc`); httprequest/audit.go:10, httprequest/httperror.go:14 (import `logger`); messaging/messaging.go (public `WithLogger(*logger.Logger)`)
- Problem: the OTLP gRPC exporter is needed only by `InitLogProvider` and
  `SetupOTLP`, but it sits in the same package as the zerolog helpers that
  every other package uses. `httprequest` uses only three internal
  `logger` calls (`audit.go:50`, `httperror.go:156`), and its exported API
  exposes no `logger` type (`go doc -all ./httprequest | grep logger.` →
  empty). Yet any outbound-HTTP consumer links gRPC, protobuf and the OTLP
  log SDK. Confirms DN-42.
- Evidence: stripped binaries (`-trimpath -ldflags='-s -w'`, go1.26.2) of
  `package main; import _ "<pkg>"; func main(){}` against HEAD:

  | Imported package | Binary bytes | Linked pkgs | 3rd-party modules |
  | --- | ---: | ---: | ---: |
  | errorkit | 1,597,602 | 102 | 0 |
  | httpclient | 3,567,881 | 190 | 0 |
  | telemetry | 4,088,073 | 219 | 8 |
  | postgres | 4,616,457 | 259 | 14 |
  | mongo | 5,710,089 | 301 | 16 |
  | logger | 11,862,281 | 390 | 25 |
  | grpc | 11,866,377 | 396 | 26 |
  | httprequest | 11,878,665 | 393 | 25 |
  | llmclient | 11,878,665 | 395 | 25 |
  | messaging | 11,878,665 | 394 | 27 |
  | httpserver/hertz | 18,075,913 | 524 | 37 |

  `go list -deps ./logger ./httprequest ./messaging` all contain
  `google.golang.org/grpc` and `golang.org/x/net/trace`. govulncheck trace:
  `logger/logprovider.go:8:2: logger.init calls otlploggrpc.init`.
- Impact: about 8 MB and about 200 extra packages, with their `init()`
  side effects (X3-006), in every service that only wants retrying HTTP or
  structured logs. That attack surface makes the toolchain advisories in
  X3-001 reachable through more paths.
- Source: eduardo/go-dependency-audit §5 ("Oversized transitive trees (a
  logging library pulling in gRPC)" is the skill's own example), §3
  ("Size"); AGENTS.md §5 (the anti-pattern list already warns about
  transitive Hertz, by the same reasoning).
- Recommendation: non-breaking first step: move the zerolog/trace helpers
  that `httprequest` uses into an internal package that `logger` also uses,
  so `httprequest`/`llmclient` stop importing `logger`. Behavior and API stay
  the same. Measure again afterwards. The full fix (OTLP setup in its own
  package or nested module, for example `logger/otlp`) needs
  `InitLogProvider`/`SetupOTLP` removed from `logger`, which breaks the v1
  API. Candidate for a v2 or a module split (X3-004). `messaging` and `grpc`
  expose `*logger.Logger` in their APIs (`WithLogger`, `WithServerLogger`),
  so they keep the edge.
- Breaking: no (internal refactor); yes for the full fix (removes exported `logger` symbols) · Needs approval: yes (full fix: breaking API / module split; the internal refactor alone does not need approval)

### X3-006 — Importing `logger` (and anything that depends on it) registers `/debug/requests` and `/debug/events` on `http.DefaultServeMux`
- Area: D (Security) · Severity: LOW · Effort: S (follows X3-005)
- Location: logger/logprovider.go:8 → `google.golang.org/grpc` → `golang.org/x/net/trace` (`trace.go:120-131` in x/net v0.62.0)
- Problem: `x/net/trace`'s `init()` calls `http.HandleFunc` for both debug
  paths. The chain comes in through gRPC, which `logger` pulls in for OTLP
  (X3-005), so the side effect hits consumers who never use gRPC. Its
  default `AuthRequest` allows loopback clients. Behind a same-host reverse
  proxy, every request looks like it comes from loopback.
- Evidence: scratch program importing only `_ "github.com/trypanic/go-sdk/logger"`:
  ```text
  /debug/requests registered="/debug/requests" status_from_loopback=200
  /debug/events registered="/debug/events" status_from_loopback=200
  ```
  `go mod why golang.org/x/net/trace` → `go-sdk/grpc → google.golang.org/grpc → golang.org/x/net/trace`;
  the same module is in `go list -deps ./logger`.
- Impact: a consumer that serves `http.DefaultServeMux`, for example
  `http.ListenAndServe(addr, nil)`, exposes these debug pages without
  knowing it. `grpc.EnableTracing` defaults to `false`, so little data is
  recorded, which is why the severity is LOW. The exposure is still
  unexpected and undocumented, and conflicts with
  go-security-audit §7 ("pprof and other debug handlers only on an internal
  listener").
- Source: eduardo/go-security-audit §7, references/threat-model.md
  (information disclosure); eduardo/go-defensive-coding §7 (avoid `init()`
  side effects).
- Recommendation: fixed as a side effect of X3-005. Until then, add a note to
  `logger/README.md` (and `grpc/README.md`) that the package links
  `x/net/trace`, and that services should not serve `http.DefaultServeMux`
  publicly.
- Breaking: no · Needs approval: no (docs); see X3-005 for the code change

### X3-007 — Deprecated `go.opentelemetry.io/otel/log/global` used in `logger`, which makes the static-analysis gate fail
- Area: B / D (deprecated API) · Severity: MEDIUM · Effort: S
- Location: logger/logprovider.go:9,88; logger/otlp.go:10,41
- Problem: the package and its `SetLoggerProvider`/`GetLoggerProvider` are
  deprecated in otel/log v1.47.0. In the module cache source
  (`go.opentelemetry.io/otel/log@v1.47.0/global/log.go`) they are one-line
  forwards to `otel.SetLoggerProvider`/`otel.GetLoggerProvider`, which
  `go.opentelemetry.io/otel` v1.47.0 (already a direct requirement)
  provides. The replacement keeps behavior and needs no `go.mod` change.
- Evidence:
  ```text
  $ staticcheck -checks SA1019 -tests ./...      # 2026.2.2
  logger/logprovider.go:9:13: go.opentelemetry.io/otel/log/global is deprecated …
  logger/logprovider.go:88:2: …global.SetLoggerProvider is deprecated: Use [otel.SetLoggerProvider] instead.
  logger/otlp.go:10:13: go.opentelemetry.io/otel/log/global is deprecated …
  logger/otlp.go:41:11: …global.GetLoggerProvider is deprecated: Use [otel.GetLoggerProvider] instead.
  ```
  No other SA1019 hit in the repository (tests included).
- Impact: baseline V7 (`task staticanalysis`) fails on an untouched tree.
  A future otel/log release may remove the package and break the next
  `fix(deps)` update.
- Source: baseline V7/V9; eduardo/go-dependency-audit §4 (upgrade
  strategy); staticcheck SA1019.
- Recommendation: replace the import with `go.opentelemetry.io/otel` and
  call `otel.SetLoggerProvider` and `otel.GetLoggerProvider`. Add a test that
  `NewOTLPWriter` resolves the provider registered by `InitLogProvider`.
  Likely duplicate of a P2.C1 finding; P2.Z should keep the first ID.
- Breaking: no · Needs approval: no

### X3-008 — Two major versions of `cenkalti/backoff` are linked; the v4 type is part of the public `algorithms` API
- Area: D · Severity: LOW · Effort: M
- Location: algorithms/backoff.go:6,28; go.mod:7 (v4), go.mod:32 (v5, indirect via `otlploggrpc`)
- Problem: `algorithms.NewExponentialBackoff` returns the v4 type
  `backoff.BackOff` (`go doc ./algorithms`). The v4 line has had no release
  since v4.3.0 (2024-01-02, module cache `.info`, `go list -m -versions`).
  v5 is current and already linked through
  `otlploggrpc/internal/retry` (`go mod why -m github.com/cenkalti/backoff/v5`).
  `go list -deps ./messaging` contains both `backoff/v4` and `backoff/v5`.
- Evidence: the commands above.
- Impact: duplicate code in `messaging`/`httprequest` consumers. Moving to v5
  changes an exported return type, which is a breaking change under the
  v1.0.0 contract.
- Source: eduardo/go-dependency-audit §5 ("Two major versions of one library
  linked side by side"; "Abandoned transitive deps").
- Recommendation: keep v4 in v1 (it is small and stable, and no advisory
  exists). For v1.x, optionally add a v5-returning constructor alongside the
  existing one and switch `messaging` to it internally. Drop v4 in a future
  v2.
- Breaking: no (additive option); yes if the existing signature changes · Needs approval: yes (dependency/API change)

### X3-009 — Low-maintenance modules in the Hertz adapter's closure: `hertz-contrib/obs-opentelemetry/tracing` (last release 2024-05) and `twitchyliquid64/golang-asm` (2021)
- Area: D · Severity: LOW · Effort: M
- Location: httpserver/hertz/server.go:13; go.mod:10, go.mod:51, go.mod:57
- Problem: the adapter's tracing middleware comes from
  `hertz-contrib/obs-opentelemetry/tracing v0.4.1`, the latest tag
  (`go list -m -versions`), released 2024-05-16. Its `go.mod` targets
  `go 1.21`, `hertz v0.9.0` and `otel v1.20.0`, and it requires
  `contrib/propagators/{b3,ot}`, `otel/exporters/prometheus v0.43.0` and
  `prometheus/client_golang v1.17.0`. MVS overrides the overlapping
  versions, so the SDK builds against code its maintainers never tested
  with otel v1.47. It also keeps `go.opentelemetry.io/contrib/propagators/ot v1.25.0`
  in the SDK's `go.mod` (line 57; v1.47.0 available), which consumers
  inherit through X3-004. Hertz's JSON engine `bytedance/sonic` links
  `twitchyliquid64/golang-asm v0.15.1` (2021-01-12;
  `go mod why -m` → `hertz → binding → sonic → internal/jit → golang-asm`).
- Evidence: release dates from `$GOMODCACHE/cache/download/<mod>/@v/<ver>.info`.
  Every other linked module had a release in 2026, except stable
  leaf libraries: `jackc/pgpassfile` 2019, `go-logr/stdr` 2021,
  `xdg-go/stringprep` 2022, and `google/uuid`, `cespare/xxhash`,
  `jackc/pgservicefile`, `youmark/pkcs8` in 2024.
- Impact: no known vulnerability today (govulncheck clean on go1.27.3). The
  risk is a future otel or Hertz API change with nobody upstream to adapt
  the middleware, and slow advisory response in an unmaintained JIT
  assembler.
- Source: eduardo/go-dependency-audit §3 ("Maintenance: last commit < 6
  months"), §5 ("Abandoned transitive deps").
- Recommendation: track it. If it breaks or gets an advisory, replace it with
  a small in-repo Hertz middleware on the OTel API (the SDK already owns
  `telemetry`). That is a dependency change and needs approval. No action
  needed on `golang-asm` beyond following Hertz/sonic releases.
- Breaking: no · Needs approval: yes (only if the dependency is replaced)

### X3-010 — Module-level advisory GO-2026-5932 (`golang.org/x/crypto/openpgp`) on the required x/crypto v0.58.0; not imported, and fixed only in an untagged pseudo-version
- Area: D · Severity: LOW · Effort: S
- Location: go.mod:62 (`golang.org/x/crypto v0.58.0 // indirect`)
- Problem: govulncheck (both toolchains) lists GO-2026-5932 in "Module
  Results", meaning the package is not imported. The only linked x/crypto
  packages are `pbkdf2`, `scrypt` and `ocsp`
  (`go list -deps ./... | grep golang.org/x/crypto`), reached through
  `mongo → mongo-driver/v2/mongo/options → youmark/pkcs8 → x/crypto/pbkdf2`.
  `go list -deps -test ./... | grep -c openpgp` → 0. The listed fix is
  `v0.58.1-0.20261009181718-2f1f834330b2`, a pseudo-version. The newest
  tag is v0.58.0 (`go list -m -versions`).
- Evidence: govulncheck output above.
- Impact: none at runtime. Module-level scanners (Dependabot alerts, Trivy,
  OSV) in consumers will flag `x/crypto v0.58.0`, because the SDK sets it as
  the floor (X3-004). Expect triage noise.
- Source: eduardo/go-dependency-audit §1 (govulncheck vs. reachability), §8
  (MVS).
- Recommendation: do not pin a pseudo-version in a library. Bump x/crypto in
  R-DEPS once a tagged release (≥ v0.59.0) contains the fix. Meanwhile,
  record the "not affected: package not imported" triage in `SECURITY.md`
  so consumers can suppress it with confidence.
- Breaking: no · Needs approval: yes (dependency bump when available)

### X3-011 — `task deps:outdated` cannot see test-only and graph-only requirements, so it reports "up to date" while `go.mod` lists outdated modules
- Area: D / H · Severity: LOW · Effort: S
- Location: Taskfile.yml:138-147 (`go list -deps … ./<pkg>/...` without `-test`)
- Problem: the task collects modules from the build closure of each
  package only. Requirements that appear in `go.mod` only because of tests
  (`stretchr/testify`, `go.yaml.in/yaml/v3`) or because of a dependency's
  tests (`contrib/propagators/ot`) are never checked. The task also does not
  report deprecated or retracted modules.
- Evidence: `task deps:outdated` → every package "up to date" / "no external
  modules". `go list -m -u all` shows, among modules listed in the SDK's own
  `go.mod`: `go.yaml.in/yaml/v3 v3.0.5 -> v3.0.6` (go.mod:60, `go mod why`:
  `urlkit.test → testify/assert/yaml`) and
  `go.opentelemetry.io/contrib/propagators/ot v1.25.0 -> v1.47.0` (go.mod:57,
  `go mod why`: `obs-opentelemetry/tracing.test`). 26 more updates belong to
  graph-only modules (prometheus, go-jose, …) that are not linked.
- Impact: small. The task gives false assurance for the `go.mod` entries that
  consumers inherit as MVS floors (X3-004).
- Source: eduardo/go-dependency-audit §4 (`go list -m -u all`), §5.
- Recommendation: add `-test` to the per-package `go list -deps`, plus a
  whole-module pass `go list -m -u -f '{{if .Update}}…{{end}}{{if .Deprecated}}…{{end}}' all`
  that labels linked and graph-only modules separately. Overlaps P2.X2.
- Breaking: no · Needs approval: no (edits an existing task; no new tool)

## Strengths

- **Every linked dependency is at its latest version.** `task deps:outdated`
  is clean, and `go list -m -u all` shows updates only for modules that are
  not linked. `go mod tidy -diff` is empty, `go mod verify` passes, and
  `go.mod` has no `replace`, `exclude` or `retract` directives.
- **No third-party module vulnerability is reachable.** With go1.27.3,
  govulncheck finds 0 symbol-level and 0 package-level vulnerabilities.
  All 19 reachable findings on go1.26.2 are in the standard library.
- **The core is stdlib-only.** `errorkit` and nine other packages link no
  third-party module. An `errorkit`-only consumer has a 2-line `go.sum` and
  a 1.6 MB binary. Graph pruning works as intended, and the remaining cost
  is version selection (X3-004), not code.
- **Supply-chain basics in the release job:** actions pinned by SHA, a
  workflow-level `contents: read`, `cyclonedx-gomod` pinned at v1.12.0, and
  an SBOM with licenses attached to each release.
- **No deprecated or retracted module is linked.** The two deprecated
  modules in the graph (`golang/protobuf`, the GCP detector) appear only
  through dependency tests.
- **`deps:update` serializes `go get`** across packages that share one
  `go.mod`, which avoids corrupting `go.sum`.

## Open questions

1. Does `actions/setup-go@v7` with `go-version-file` read a `toolchain`
   directive, and does it set `GOTOOLCHAIN`? If it sets `GOTOOLCHAIN=local`,
   the `toolchain` line from X3-002 alone would not change the CI toolchain,
   and `release.yml` would need an explicit `go-version`. Not verifiable
   offline.
2. Is Dependabot (or another scanner) configured in the GitHub repository
   settings? `main` contains Dependabot merges, but the tree has no
   configuration (X3-003).
3. `bytedance/sonic v1.15.5` gates its JIT behind a Go version window
   (`compat.go`: `//go:build (!amd64 && !arm64) || go1.28 || …`). Building
   `httpserver/hertz` with go1.27.3 works, but on Go 1.28 Hertz would
   silently fall back to the `encoding/json` path until sonic is updated.
   This affects performance only, not correctness, and has not been
   measured.
4. `messaging` uses `github.com/google/uuid` once, for `EventID`
   (messaging.go:154). `errorkit` already ships ULID helpers, so the
   dependency could go, but the ID format visible to consumers would change.
   Product decision; not proposed.
5. `logger/logprovider.go:12` imports `otel/semconv/v1.21.0` while the rest
   of the graph uses v1.37/v1.43. No schema-URL conflict was observed,
   because `resource.New` is not merged with `resource.Default()`. Left to
   P2.C1.
6. License compatibility of the 52 linked modules was not reviewed. The
   release SBOM is generated with `-licenses`, but no policy check consumes
   it.
