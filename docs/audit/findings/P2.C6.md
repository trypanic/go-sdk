## HIGH

### C6-001 — `urlkit.BuildURL` concatenates `base + path` and re-parses it, so `path` can change the host, query or base query
- Area: D (Security) · Severity: HIGH · Effort: S
- Location: urlkit/url.go:41-56 (also README "Edge cases" urlkit/README.md:63-67)
- Problem: when `path != ""` the function runs `url.Parse(base + path)`. The path is therefore interpreted as URL syntax, not
  as a path. A path that does not start with `/` (or that contains `@`, `?`, `#`) changes the authority, the query or the
  fragment. The README and `AGENTS.md` §1 present the package as the way to "build URLs / join paths **safely**", and the
  OAuth/vendor examples feed `BuildURL` with dynamic data.
- Evidence (probe test, `params={"p":"1"}`):

  ```text
  base="https://api.good.com"  path="@evil.com/x"          -> https://api.good.com@evil.com/x?p=1     host="evil.com"
  base="https://api.good.com"  path=".evil.com/x"          -> https://api.good.com.evil.com/x?p=1     host="api.good.com.evil.com"
  base="https://api.example.com" path="users"              -> https://api.example.comusers?p=1        host="api.example.comusers"
  base="https://api.example.com" path="/users/1?admin=true"-> https://api.example.com/users/1?admin=true&p=1
  base="https://api.example.com/v1?key=abc" path="/users"  -> https://api.example.com/v1?key=abc%2Fusers&p=1  (path swallowed into the query value, key corrupted)
  ```

- Impact: if any part of `path` is attacker-influenced and the caller omits the leading `/` (for example `BuildURL(base, id)`), the
  request goes to an attacker-chosen host (SSRF, credential forwarding by `httprequest` `Authorization` headers).
  A `?`/`#` in an ID injects query parameters. A base that already carries a query (API keys, signed URLs) is silently
  corrupted. The first four cases are source-visible but documented only partially ("does not join paths"); the host
  swap and query injection are not documented.
- Source: eduardo/go-security-audit §1 (validate at the boundary, reject rather than repair) and §3 (SSRF) · eduardo/go-defensive-coding §7 ·
  AGENTS.md §1 ("safely")
- Recommendation: treat `path` as a path. For example, parse `base` once, reject a `path` that contains `?`, `#` or does not start with
  `/` (or add the missing slash), set `baseURL.Path`/`RawPath` through `url.JoinPath` semantics (`baseURL.JoinPath(path)`) or `url.URL{Path: path}`
  escaping, and keep the base query intact. Document the new rules in the README and add the cases above as table tests.
- Breaking: no signature change, but behavior changes for inputs that today produce host/query rewriting · Needs approval: yes
  (README documents raw concatenation as the contract; rejecting or escaping such paths is a visible behavior change).

## MEDIUM

### C6-002 — `urlkit.JoinPath` keeps `..` segments and accepts scheme-less or non-HTTP bases
- Area: D (Security) · Severity: MEDIUM · Effort: S
- Location: urlkit/url.go:110-134 (`BuildURL` has the same lack of scheme check at 28-38)
- Problem: segments are only trimmed of `/`; dot segments are not rejected or cleaned. Base is accepted if `url.Parse` succeeds, so
  `foo` and `javascript:alert(1)` are valid bases.
- Evidence:

  ```text
  JoinPath("https://a.com/v1", "..", "x")           = "https://a.com/v1/../x"
  JoinPath("foo", "bar")                            = "foo/bar"
  BuildURL("javascript:alert(1)", "", {"p":"1"})    -> "javascript:alert(1)?p=1"
  JoinPath("https://a.com/")  (no segments)         = "https://a.com"   (trailing slash dropped)
  ```

  `?` and `#` inside segments are percent-encoded (`a%3Fb=c`), which is correct.
- Impact: a segment such as an unvalidated resource ID of `..` escapes the intended prefix once the server normalizes the path
  (traversal to sibling endpoints). Callers who expect an absolute http(s) URL get no signal for a malformed base.
- Source: eduardo/go-security-audit §1, §3 ("Paths", "reject URLs whose scheme is not http/https") · eduardo/go-defensive-coding
- Recommendation: reject (or `path.Clean`) `.`/`..` segments in `JoinPath`; optionally add a validating variant that requires an
  `http`/`https` scheme and a non-empty host (additive API) rather than changing the current functions. Consider delegating to
  `(*url.URL).JoinPath`, noting that stdlib cleans dot segments but keeps a trailing slash on the last element.
- Breaking: no (additive) or behavior change (if the existing functions start rejecting) · Needs approval: yes (behavior change of exported functions)

### C6-003 — `stringutils.RemoveMarkdownCodeBlock` mangles content that has several fenced blocks and breaks its documented "whole content" rule
- Area: B (Correctness) · Severity: MEDIUM · Effort: S
- Location: stringutils/normalize.go:30-32 (lazy `(.*?)` with `(?s)` and `$` anchor), README stringutils/README.md:75, 79
- Problem: the regexp is anchored at the first opening fence and at the last closing fence of the whole string, and the lazy group
  can span intermediate fences. README promises: "If there is any content before the opening fence or after the closing fence,
  the string is returned as-is", "Nested or multiple fences within the content are not altered".
- Evidence:

  ```text
  in  = "```json\nA\n```\n\nSome text\n\n```json\nB\n```"
  out = "A\n```\n\nSome text\n\n```json\nB"
  ```

  The input is two separate blocks with prose in between, not one wrapper; the output is neither the original nor valid content.
- Impact: LLM answers with an explanation between two code blocks are corrupted silently; a following `json.Unmarshal` fails with an
  unrelated error (the intended use in README "LLM gateway").
- Source: eduardo/go-defensive-coding §1 (silent corruption) · eduardo/go-test-quality ("edge cases")
- Recommendation: after matching, reject a body that itself contains a line starting with ```` ``` ```` (return `input`), or parse line by line:
  first line is a fence, last line is a bare fence, no inner fence line. Add the case to the table test.
- Breaking: no (fixes behavior to match the README) · Needs approval: no

### C6-004 — `algorithms.NewExponentialBackoff` returns a `BackOff` that has not been `Reset`, so its first delay ignores `InitialInterval`
- Area: B (Correctness) · Severity: MEDIUM · Effort: S
- Location: algorithms/backoff.go:33-41
- Problem: `backoff.NewExponentialBackOff()` calls `Reset()` with the default `InitialInterval` (500 ms) (cenkalti/backoff v4.3.0
  `exponential.go`, `NewExponentialBackOff`). The factory then overwrites `InitialInterval` but never calls `Reset()`, so
  `currentInterval` stays at 500 ms until someone resets. `backoff.Retry` does reset (v4.3.0 `retry.go:86`), but the package is
  also advertised for "custom loops" that call `NextBackOff()` directly (AGENTS.md §1; README Overview).
- Evidence (probe, `InitialInterval=10s, MaxInterval=1m, Multiplier=2, MaxRetries=3`):

  ```text
  first NextBackOff without Reset = 276.236948ms
  after Reset                     = 10.509612659s
  ```

  The existing test (`algorithms/backoff_test.go:40-61`) sets all intervals to 1 ms, so it cannot see the difference.
- Impact: a custom loop retries almost immediately instead of waiting the configured initial interval, hammering the dependency.
- Source: eduardo/go-defensive-coding §7 (initialisation safety) · eduardo/go-test-quality ("edge cases")
- Recommendation: call `expBackoff.Reset()` after setting the fields (one line). Add a test that asserts the first delay is within
  `InitialInterval ± RandomizationFactor` with a non-default `InitialInterval`.
- Breaking: no · Needs approval: no

### C6-005 — `uint64(retry.MaxAttempts)` and zero-valued topology retry fields turn a bad config into unbounded or zero-delay retries (consumer of `algorithms`)
- Area: D/B · Severity: MEDIUM · Effort: S
- Location: messaging/messaging.go:375-380 → algorithms/backoff.go:28-31; messaging/types.go:30-35. Owner of the fix: P2.C5 (cross-reference); the guard belongs in `algorithms`
- Problem: `MaxAttempts` is an `int` read from a JSON topology file (unvalidated, DN-25). A negative value converts to a huge `uint64`,
  which `NewExponentialBackoff` (`MaxRetries < 1` check only catches 0) accepts. Missing `initialDelay`/`maxDelay`/`backoffMultiplier`
  keys give zero values, which the factory passes straight through.
- Evidence (probe): `MaxRetries: uint64(-1)` with 1 ms intervals → 100000 retries observed before the probe stopped (it never reached `Stop`).
  Zero intervals: `ExponentialBackoffConfig{MaxRetries: 5}` yields `0s, 0s, 0s` between retries after the first (see C6-012).
- Impact: a topology file with `"maxAttempts": -1` makes `executeWithRetry` retry effectively forever; an incomplete retry block makes it
  retry in a tight loop.
- Source: eduardo/go-defensive-coding §5 (int→uint conversions wrap; `gosec` G115) and §7
- Recommendation: validate `RetryConfig` when the topology loads (C5) and make `algorithms` defend itself: clamp or substitute defaults for
  non-positive intervals and multiplier < 1, and cap `MaxRetries` to a sane upper bound or document it.
- Breaking: no · Needs approval: no

### C6-006 — `slices.Chunk` returns sub-slices with spare capacity, so `append` on one chunk overwrites the next one
- Area: B/D (Defensive coding) · Severity: MEDIUM · Effort: S
- Location: slices/chunks.go:16 (README slices/README.md:68-69 documents shared elements only)
- Problem: `items[i:end]` keeps the capacity of the original slice. Go's own `slices.Chunk` (go1.23+, `src/slices/iter.go:93-110`)
  clips every chunk with `s[i:end:end]` for exactly this reason.
- Evidence:

  ```text
  items = [1 2 3 4]; c := Chunk(items, 2); c[0] = append(c[0], 99)
  items after = [1 2 99 4]; c[1] = [99 4]; cap(c[0]) = 4
  ```

- Impact: batch-processing code that appends to a chunk (a common pattern) corrupts the following batch and the caller's backing array, with no panic or error.
- Source: eduardo/go-defensive-coding §3 · eduardo/go-data-structures §2 · stdlib `slices.Chunk`
- Recommendation: `chunks = append(chunks, items[i:end:end])`. Element sharing (documented) is unchanged, so this is compatible with the README contract.
  Add the probe above as a test.
- Breaking: no (callers that relied on appending into the next chunk would be relying on a bug) · Needs approval: no

### C6-007 — `stringutils.NormalizeText` compiles its regexp on every call
- Area: F (Performance) · Severity: MEDIUM · Effort: S
- Location: stringutils/normalize.go:18
- Problem: `regexp.MustCompile` inside the function; the README (stringutils/README.md:110) says the "compiled regular expressions ... are
  package-level variables initialised once", which is true for `codeBlockRegex` only.
- Evidence (benchmark, `"Men's Clothing & Accessories"`, `-benchmem`, 3 runs):

  ```text
  current (compile per call)      1333-1414 ns/op  984 B/op  18 allocs/op
  package-level regexp             687-775 ns/op   169 B/op   7 allocs/op
  single-pass ASCII loop (Builder) 127-205 ns/op    64 B/op   2 allocs/op
  ```

  The loop version returned identical output to the current function in a 10 s fuzz run (4.6e5 execs, no mismatch), so it is a safe replacement.
- Impact: ~10x slower and ~15x more garbage than necessary on a function meant for key normalization in loops (ingestion).
- Source: eduardo/go-performance-review §9 ("`regexp.Compile` inside function → compile once at package level") · eduardo/go-performance-review §1
- Recommendation: at minimum hoist the regexp to a package-level `var`; preferably replace by the loop (no regexp). Fix the README sentence either way.
- Breaking: no · Needs approval: no

### C6-008 — `validators` is 9.7% covered; three of four validators have no test

- Location: validators/validators_test.go (one test, `ValidateDateRange("bad", ...)`)
- Problem: `IsValidDatePointer`, `IsAlphanumericWithSpaces`, `IsWithinRange` and the success and ordering branches of `ValidateDateRange` are untested. These

### C6-009 — A failing validation costs ~600x a passing one because every error captures a stack trace
- Area: F (Performance) · Severity: MEDIUM · Effort: M (design lives in `errorkit`, owner P2.C1)
- Location: validators/validators.go:35-54 and every `errorkit.NewError` call (errorkit/error.go:52-77, `MaxStackDepth = 32`)
- Problem: validators are called per request on attacker-controlled input; each rejection builds an `*AppError` with ULID, timestamp and a stack.
- Evidence (benchmark, `IsAlphanumericWithSpaces`, 3 runs):

  ```text
  valid input   "hello world 123"  ~15 ns/op       0 B/op   0 allocs/op
  invalid input "hello-world"     ~9,500 ns/op  5,059 B/op  27 allocs/op
  ```

- Impact: an attacker who sends invalid values makes the validation layer ~600x more expensive per request than valid traffic (amplification, not a bug on its own).
- Source: eduardo/go-performance-review §1, §5 (profile first; this is measured) · AGENTS.md §2.1
- Recommendation: handle in `errorkit` (C1): a cheap constructor/option without stack capture for validation codes, or document the cost in the validators README.
  Nothing to change in `validators` beyond that.
- Breaking: no · Needs approval: yes (changes the errorkit contract "stack trace on every error")

### C6-012 — `algorithms`: zero-valued config hot-loops, the hidden 15-minute `MaxElapsedTime` is undocumented, and the README misdescribes `MaxRetries = 0`
- Area: G (docs/API) · Severity: LOW · Effort: S
- Location: algorithms/backoff.go:29-41; README algorithms/README.md:58-59, 69-72, 131-133 (DN-26)
- Problem (three parts):
  1. README says `MaxRetries = 0` wraps to `MaxUint64` (unbounded); the code clamps it to 1 (one attempt), as the test comment states. The README is wrong (the code is safer).
  2. `Config{MaxRetries: 5}` with other fields zero produces delays of 0 (`0s, 0s, 0s, -1ns` observed after the first), i.e. a retry loop with no waiting; the README only says
     "not meaningful".
  3. The constructor keeps the library default `MaxElapsedTime = 15 min`. In v4.3.0 `NextBackOff` returns `Stop` once `elapsed + next > MaxElapsedTime`, so a large `MaxRetries`
     with long intervals stops early, contradicting "exactly `MaxRetries` attempts" (README:69-72).
- Evidence: probe output above; cenkalti/backoff v4.3.0 `exponential.go` (`DefaultMaxElapsedTime`, `NextBackOff`).
- Impact: surprising retry counts and tight loops; documentation inaccuracies.
- Source: eduardo/go-documentation §1 · eduardo/go-defensive-coding §7
- Recommendation: fix README; apply defaults for non-positive intervals/multiplier (see C6-005); set `expBackoff.MaxElapsedTime = 0` or expose it, and document. Setting it to 0 changes behavior for
  existing callers with long schedules, so decide explicitly.
- Breaking: no (docs) / behavior change if `MaxElapsedTime` changes · Needs approval: yes for the `MaxElapsedTime` change only

### C6-014 — `NormalizeText` is lossy and not injective; the "non-ASCII is removed" statement has an exception

### C6-018 — `marshal` repeats the same encoder block twice, and `ioutils.WriteJSON` a third time
- Area: B (DRY) · Severity: LOW · Effort: S
- Location: marshal/json.go:10-40; ioutils/printer.go:18-28
- Problem: `NoEscape` and `NoEscapeBytes` have identical bodies. `NoEscape` could be `b, err := NoEscapeBytes(v); return string(b), err`. `ioutils.WriteJSON` is the same logic against an `io.Writer`; `marshal` could expose it and `ioutils` reuse it.
- Evidence: source comparison above (same `SetEscapeHTML(false)` encoder, same `ERR_INTERNAL` error). Fuzz run (10 s, 3.7e5 execs): `NoEscapeBytesNoNewline` output was always valid JSON and round-tripped.

- Source: go-design-principles (DRY, rule of three applies here) · eduardo/go-coding-standards
- Recommendation: factor the shared encoder; keep exported names. Do not make `marshal` depend on `ioutils`, only the other way.

### C6-020 — `slices`: no preallocation, `min` not used, name shadows the standard library, `Chunk(size<=0)` drops all items silently
- Area: B/F/G · Severity: LOW · Effort: S
- Location: slices/chunks.go:6-18, slices/string.go:5-24, package name
- Problem:
  - `Chunk` appends to a nil outer slice and uses a manual clamp (chunks.go:13-15); JetBrains `min_max` applies (`end := min(i+size, len(items))`); the outer slice size is known: `make([][]T, 0, (len(items)+size-1)/size)`.
  - `MergeUniqueStrings` creates `seen` without a capacity hint (`make(map[string]struct{}, len(a)+len(b))`) (go-data-structures §3).
  - `Chunk` with `size <= 0` returns `nil`, i.e. a batch loop with a mis-configured size processes nothing and gets no error; stdlib `slices.Chunk` panics instead. Documented, but a defensive-coding smell.
  - The package is called `slices`, the same identifier as the standard library package, so a file that needs both must alias one (AGENTS.md §0 lists only `postgres`, `mongo`, `grpc`). Renaming is breaking.
  - `MergeUniqueStrings` is not generic (`MergeUnique[T comparable]` would cover more cases).
- Evidence: source; probe `Chunk([]int{1,2,3}, 0)` → `nil`; JetBrains list for slices/chunks.go includes `min_max`.
- Impact: minor allocation overhead; naming friction; silent no-op on bad input.
- Source: eduardo/go-data-structures §3, §8 · eduardo/go-naming §2 · JetBrains `min_max` · eduardo/go-defensive-coding
- Recommendation: preallocate, use `min`, add a note to AGENTS.md §0 for the `slices` name collision, document the size contract more prominently. Generic variant is additive. No rename.
- Breaking: no · Needs approval: yes only for a new generic exported function

## Strengths

- Every public failure path in scope returns `*errorkit.AppError` with a specific code and wraps the cause (`WithWrapped`): `envs`, `urlkit`, `validators`, `marshal`, `ioutils` all follow AGENTS §2.1.
- `algorithms` guards the `uint64` underflow (`MaxRetries < 1`) and has a test documenting it; 100% coverage; the `BackOff` is created per call (no shared mutable state).
- `ioutils` really is dev-only today: no production or test package imports it; the doc comment and README say so; the dev helpers carry `nosemgrep` justifications.
- `ioutils.SaveJSON` correctly reports a `Close` error when the encode succeeded (named result), matching eduardo/go-defensive-coding §6.
- `urlkit.JoinPath` percent-encodes `?`/`#` inside segments and keeps the base query; `BuildURL` encodes parameters through `url.Values`; none of the eight packages panics on any fuzzed input (about 1.0e7 total executions across targets).
- `MustBuildURL` is the only panic in scope and carries a justified `nosemgrep` comment.
- Stateless and race-free by construction (only package-level state is a compiled regexp); `go vet` is clean for all eight packages; staticcheck default checks report nothing here (QF1001 shows only in the golangci-lint run, see C6-015).
- Table-driven tests with `t.Parallel()` and a trailing-newline contract test in `marshal`; `slices` and `stringutils` at 100% statement coverage.

   `ozzo-validation` is not a dependency of the module, so I could not run it. Needs confirmation by a consumer or by reading ozzo's source.

3. `AppError.Error()`/`Pretty()` output for a wrapped error: C6-011 shows the raw value in the reason; I did not check whether the wrapped `env.ParseError` is printed a second time by `Pretty()`.
